# ADR 0057: Test grid object in the project file: one tagged group with a test id, resolved into ordinary derived operations, a Lasered register, format 46

**Status:** Proposed 2026-11-12, `needs-customer` (document model and file format). Built on the customer's decisions of 2026-11-12: Frage 200 (one grid object, editable any time, resolving into ordinary operations; once Lasered a change gives a new id; Lasered set only by `0029`), 201 B (no "remove operations"; delete or move off the page removes them; recreate from Materials with the same id), 204 A (regeneration overwrites hand edits), 206 A (the grid only moves); test ids 5 characters `0-9A-Z`, unique against every id in the store including deleted ones; the id and labels always burned; gap constant 2 mm. **Replaces** [ADR 0054](0054-laser-settings-and-test-grids-in-the-project-file.md) §4 and §5 (the folded grid row `op_grid`, `grid_cell` numbers, `test_grid_worked` as a stored mark) and amends §6 (format) and [ADR 0046](0046-laser-operations-record.md) §3 and §4 (delete and copy of derived operations); notes go on both on acceptance. ADR 0054 §1 to §3 (settings, link, refresh) stay. The test record is [ADR 0058](0058-material-records-shared-across-lasers.md). Builds on [ADR 0056](0056-laser-operation-tools-in-the-project-file.md) (`interval_mm`, `op_options`, format 44). Spec: [`0112`](../../specs/0112-test-grid-and-materials/specification.md) criteria 1 to 15, 28, 29, 32. Feature notes: [`0112` adrs.md](../../specs/0112-test-grid-and-materials/adrs.md).

## Context

ADR 0054 made the grid one folded row whose cells ran with numbers stored on the items. The customer now wants one grid object that becomes 26 ordinary operation rows for a 5 x 5 grid (one for all text, one per cell), each editable by hand, overwritten by the next grid change, removed with the grid. The grid carries a test id that is burned into the sheet and names a test record in the material library; once the sheet is lasered, any change must give a new id so the old record stays true to the sheet.

## Options

**How the grid's operations are kept**

- **A. Ordinary ADR 0046 operation nodes with one ownership register `op_grid_part` naming the grid and the part (chosen).** Show, Output, rename, trash, order, Cuts last, settings, the nearest rule and undo are the `0101` and `0028` code paths unchanged; the register tells regeneration what to overwrite, tells the kind buttons not to reuse the row (ADR 0056 §3), and lets the delete sweep remove the rows with the grid.
- **B. No ownership register; regeneration finds the rows by their membership keys.** A hand edit that ticks another object, or a merge, makes the match ambiguous. Rejected.
- **C. Keep the folded row and expand it in the UI only.** Not ordinary rows; hand edits would need a second settings store. Rejected by the customer's decision.

**Where the test id lives**

- **A. Inside the grid's atomic recipe map (chosen).** An id always names exactly one recipe; a merge never pairs one peer's id with another's recipe.
- **B. Its own register.** Two peers changing a Lasered grid at once could keep one's id with the other's recipe. Rejected.

**Old format-43 grids**

- **A. Migrate at open, one `migrate_format` commit (ADR 0042 §9) (chosen).** Readers know one grid shape.
- **B. Read the old shape lazily and convert at the first edit.** Two read and run paths kept forever. Rejected.

## Decision

1. **The grid object** is an ordinary group on the laser page (as ADR 0054) with:
   - `x.curvyo.laser.test_grid`, one atomic map, the **recipe**: `id` (5 characters `0-9A-Z`), `kind` (`cut`, `score`, `engrave`), `columns` and `rows` (`{ param, min, max, count }`, `param` one of `power`, `speed`, `passes`, and for Engrave `interval`; the two differ; `count` 2 to 12), `fixed` (the parameters on no axis, each once: `power_pct`, `speed_mm_min`, `passes`, `interval_mm`), `cell_mm` (3 to 50), `crosshatch` (a boolean present in every recipe; `true` only for Engrave, `true` on Cut or Score is damage; amended 2026-11-13), `material` (`{ id, name }`, absent until picked). Value ranges as ADR 0054 §1 and ADR 0056 §5. The recipe is the same serde type as the test record's recipe (ADR 0058 §2): one type in `curvyo-laser-core/src/test_recipe.rs` with its stored form in `test_recipe_json.rs` (amended 2026-11-13), one golden shape.
   - `x.curvyo.laser.test_grid_lasered`: the Unix milliseconds of the output, written only by `0029` and by the internal test hook (decision 5); absent = Not lasered.
   - Items: cells tagged `x.curvyo.laser.grid_cell` = `{ column, row }` (no numbers any more), label texts tagged `grid_label` = `id`, `column_title`, `row_title`, `column_value` or `row_value`. Gap 2 mm and text height 3 mm are constants in the layout, never stored. A tag counts only under a group with a readable recipe; elsewhere it is inert and kept.
2. **Derived operations.** Each is an ADR 0046 operation node with `op_grid_part`, an atomic map: `{ grid: "<encoded group id>", part: "labels" }` or `{ grid, part: "cell", column, row }`. A 5 x 5 grid has 26: the labels operation (kind Engrave, one `member.` key per label item, `op_settings` linked to the material's Engrave set for the page's laser, else own 20 % and 3000 mm/min, Proposal) and one per cell (the grid's kind, one `member.<cell id>` key, own numbers from the recipe in `op_settings`, Crosshatch in `op_options` for Engrave). Names "<column value> · <row value> · <id>" and "<id> labels" (P5). They are ordinary rows; a hand edit writes them like any operation.
   **Regeneration** (every committed bar change, Frage 204 A): in the same commit, the pure function `curvyo-laser-core/src/test_grid_ops.rs` ("the derived operations a recipe resolves into") gives the wanted parts; existing rows are rewritten in place by part (node id kept; name, Show, Output, `op_settings`, `op_options` and membership overwritten), missing parts are added after the grid's last row (a new grid: at the end of each kind's section), surplus rows and items are deleted. Items are re-laid out the same way. One undo step restores the old rows exactly.
3. **Lifetime** (amends ADR 0046 §3, §4):
   - **Delete** of the group (delete, cut, ungroup) and **moving it off the laser page** delete, in the same commit, every operation whose `op_grid_part.grid` is the group. A derived row whose grid a merge removed runs nothing (its keys are dead) and is deleted by the next local step's sweep (the ADR 0054 §5 amendment of 2026-11-12, applied by `op_grid_part`). The test record stays (ADR 0058).
   - **Copy, Duplicate, Paste:** the copy is a new grid with a new test id, no Lasered register and its own derived rows; the ADR 0046 §4 copy rule skips derived rows.
   - **Recreate from Materials** ("Place on <page>"): writes a new group from the test record's recipe and id, with `test_grid_lasered` from the record's state, and regenerates its rows; one step.
4. **New test id** (Frage 200). A test id is made in core (`curvyo-laser-core/src/test_id.rs`, "makes and checks 5-character test ids") from caller random bytes, rejection-sampled into `0-9A-Z`, and refused while it is in the taken set the session passes: every live test id of the loaded store, the retired ids (ADR 0058 §4) and every grid id in the open project. When the grid is Lasered and a commit changes its recipe, or edits one of its derived rows' settings, options or membership by hand (rename, Show, Output and order do not count, Proposal), that same commit writes a new `id`, deletes `test_grid_lasered` and rewrites the `id` label item; the cell rows keep the hand edit. A grid that is not Lasered keeps its id. A concurrent output on one peer and an edit on another can leave the edited recipe with the old id and the Lasered mark; the next edit then gives the new id (accepted, as the customer accepted double ids across unsynced computers).
5. **The Lasered hook.** `0029` writes `test_grid_lasered` and the record's state in its output commit. Until then a Rust-only session method (`#[doc(hidden)]`, not bound to wasm, so no UI or script reaches it) writes both for the acceptance tests. No button, no flag, no feature.
6. **Reads and damage.** A recipe that does not read (not a map, a missing or bad id, an unknown key, a value out of range, both axes on one parameter) makes the group a plain group: its rows stay as ordinary operations (their `op_grid_part` names a non-grid and is ignored), nothing is regenerated, nothing is repaired on read. A `test_grid_lasered` that is not a non-negative integer reads Not lasered. An `op_grid_part` that is not a readable map is ignored (the row is ordinary).
7. **`format_version` 46.** A build of 45 would read the new recipe as damaged, keep 26 rows that its copy shares with the original and its delete leaves behind, silently. ADR 0033 §7 refuses that by a bump. **Migration from 43 and 44** (session, after open, one `migrate_format` commit, no undo step, the file on disk unchanged until saved): each group with a format-43 recipe gets the new recipe (columns power, rows speed, `fixed.passes` 1, its cell size and kind, a new id), a derived row per cell carrying the cell's stored `grid_cell` numbers (so a hand-moved cell keeps its place and its numbers), and one labels row over the old label items with the old label settings; the `op_grid` row is deleted. Items are not re-laid out, so the `id` label appears at the first bar change (which is also when a material and so a test arrive, ADR 0058 §3). `test_grid_worked` stays on the group, inert, until the first test record of that grid is made, which takes it as its best cell and deletes it in that commit (`0112` criterion 29). The validator keeps accepting `op_grid` and the old tags in files below 46. Two peers migrating the same shared document offline get two ids; the second sync shows both grids' rows (development build, compatibility waived by the customer 2026-10-29).

   **Amended 2026-11-13 (Frage 214 B, nothing deployed): the migration from 43 to 45 is dropped.** Such files open with the old `op_grid` row as an ordinary operation without a grid object (§6), written back unchanged; no `migrate_format` step exists.
8. **Goldens** in `curvyo-document-core/tests/fixtures/`: `test_grid_v46.curvyo` (a 5 x 5 Cut grid with material, 26 rows, one hand-edited cell row, a second Engrave grid with Crosshatch and Lasered), `test_grid_damaged_v46.curvyo` (a bad id, both axes on power, a count of 13, a non-integer Lasered, an `op_grid_part` that is text; each opens as described in decision 6 and saves back unchanged), `test_grid_orphan_rows_v46.curvyo` (rows whose group is gone). The four format-43 goldens of ADR 0054 open by the migration and their run result is unchanged (`laser_settings_v43`, `test_grid_hand_edited_v43` with its moved cell and deleted label, `test_grid_orphan_row_v43`, `laser_settings_damaged_v43`).

## Consequences

- A 12 x 12 grid is 145 operations in the list; the Operations tab, the delete sweep and the nearest-rule caches must stay within the budgets of the feature notes at that size.
- Every bar change rewrites up to 145 rows and 169 items in one commit; hand edits are lost by design (Frage 204 A), one undo step brings them back.
- The burned id and the library depend on each other only by the id text: a project opened on another computer shows the grid and runs it; its test is shown only where the material is loaded.
- Migration writes at open, unlike ADR 0054's "nothing written on open"; it is not an undo step and not saved until the maker saves.
- Published keys: `test_grid` (new shape), `test_grid_lasered`, `grid_cell` (new shape), `grid_label` values, `op_grid_part`. `op_grid` and `test_grid_worked` are read only by the migration and the first test. Renaming one is a format change.
- Rejected and why: rows found by keys (B, ambiguous after hand edits), the folded row (C, not the customer's decision), the id in its own register (B, merge pairs an id with a foreign recipe), lazy conversion (B, two paths forever).

## Notes

- 2026-11-13 (architect, build review of `0112`): **Who joins the lifetime rules.** document-core does not depend on laser-core and cannot read a recipe, so for the delete sweep, copy and off-page removal a grid is any group carrying a `test_grid` register; whether the recipe reads is the session's call, which never regenerates or copies a damaged one. The rows of a deleted damaged grid go with it, which is what decision 6 plus the orphan sweep give anyway. The move and Duplicate commands do not call the grid commands themselves: the session joins `remove_test_grid_rows` (box centre off its laser page) and `copy_test_grid` (a duplicated grid without rows, new id) to the same step after the command (`continue_step`), so decision 3 holds in one undo step. A copy's test record is written at its next bar commit or material pick, like a hand-edited Lasered grid's new id (decision 4), not in the copy step **(Proposal)**.
- 2026-11-13: **The Lasered hook** of decision 5 also exists on `Document` (`#[doc(hidden)] mark_test_grid_lasered_for_tests`) with the label `mark_test_grid_lasered`, named "Mark lasered" so the history-name guard covers it; `0029` reuses or renames it with its output step.
