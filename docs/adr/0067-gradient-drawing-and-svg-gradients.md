# ADR 0067: Gradient drawing and SVG gradients: per-vertex gradient coordinates and one stop table in the artwork pipeline, grey stops on laser pages, `linearGradient` and `radialGradient` in `curvyo-svg-core`

**Status:** Accepted 2026-11-18 (customer merged PR #389; proposed 2026-11-18 by the architect). No customer decision needed (rendering and import/export mapping inside an accepted story; the SVG behaviour is the customer's Frage 236). Decisions marked **(Proposal)** are vetoable at the demo. Uses the model of [ADR 0066](0066-gradient-fill-in-the-document-model.md); amends nothing accepted. Keeps ADR 0001 §4/§5 (one draw list, typed arrays across the wasm boundary), ADR 0017 §5 (render-core stays pixel-free) and ADR 0018 (`curvyo-svg-core` depends on no Curvyo crate). Spec: [`0124`](../../specs/0124-gradient-fill/specification.md) criteria 9 to 14, 21, 24.

**In plain words (for the customer).** The graphics card computes the gradient for every screen pixel from the shape's stops, so it is smooth at every zoom, hard edges stay hard and nothing is redrawn while you pan. On a laser page Curvyo hands the card grey stops instead of colours. SVG files keep real gradients in both directions.

## Context

Today the draw list is triangles with one flat colour per vertex, drawn in one pipeline layer by layer, plus image quads drawn by a textured pipeline (ADR 0017 §5); the host is `wgpu` on `Backends::GL`, WebGL2 on WebKitGTK being the weakest stack. A gradient must be exact per pixel (hard edges, radial circles, any zoom), cost at most 2 ms per frame for 1,000 gradient shapes (24 b), support any number of stops (24 e), and keep stacking with colours, patterns and images. SVG import today turns a gradient into its middle colour (`paint.rs`, `gradient_middle`).

## Options

**Drawing**

| Option | Why it won or lost |
|---|---|
| A. On the CPU: cut the tessellated interior at every stop's iso-line and colour the vertices | Exact for linear only between cuts; radial needs rings re-cut per zoom; 256 stops multiply triangles; a boolean cut per shape on every edit. Lost on cost and exactness. |
| B. Each gradient shape its own layer, drawn by a gradient pipeline with per-shape uniforms (like images) | Exact, but 1,000 shapes are 1,000 draw calls and uniform updates per frame on WebKitGTK's GL, the budget 24 b's 2 ms is not credible. Lost. |
| **C. One artwork pipeline: a second vertex stream with gradient coordinates and a stop-table texture; solid vertices carry "no gradient" (chosen)** | Exact per pixel (an affine map commutes with linear interpolation, so per-vertex `u, v` interpolate exactly; `t` and the stop lookup run per fragment); no extra draw call, no layer change, stacking unchanged. Cost: one more vertex attribute for all artwork vertices and one float texture. |

**SVG model:** gradient types of `curvyo-svg-core`'s own (chosen; ADR 0018 forbids a Curvyo dependency, and the reader already resolves styles into its own types) against reading Curvyo's model in svg-core (forbidden edge).

## Decision

1. **Draw list** (`curvyo-render-core`, new module `gradient_fill.rs`, "the gradient data of the artwork"). A leaf whose fill paints a gradient is tessellated exactly as its Colour fill (its fill rule, holes, the open path closed by a straight line, a text's glyph outlines) in its own place in the layer order. `DrawList` gains `gradients: Vec<GradientSpan>` (`vertices: Range<usize>`, `to_gradient: [f32; 6]` the ADR 0066 §4 map, `radial: bool`, `stops: Range<u32>`) and `gradient_stops: Vec<StopTexel>` (offset and premultiplied RGBA as `f32`). `DrawList::gradient_attributes() -> Vec<[f32; 4]>` gives per vertex `(u, v, first stop, signed count)`, zero for solid vertices, so the host stays logic-free. A gradient vertex's colour is white with the leaf's shown opacity as alpha; the shader multiplies. `Vertex` is unchanged.
2. **Host** (`curvyo-editor-wasm`, `gpu_pipeline.rs`). The artwork pipeline takes the attributes as vertex buffer 1 and binds the stop table: one `Rgba32Float` texture, 2,048 texels wide (the WebGL2 minimum maximum size), two texels per stop, rows as needed, read with `textureLoad` (no filtering needed, so no float-linear extension). Fragment: count 0 returns the vertex colour; else `t = u` or `length(u, v)`, clamped (pad), binary search over the stops (at most 32 steps; 8 for 256 stops), premultiplied lerp, un-premultiplied for the existing `ALPHA_BLENDING`, times the vertex alpha. No dither noise is added (Proposal): 8-bit output quantises as Inkscape does. The texture is re-uploaded only when `gradient_stops` differs from the uploaded one; the attribute buffer goes with the vertex buffer it belongs to. **Nothing about frame scheduling changes**: no frame is skipped and no new per-frame rebuild is added; spans are in document space, so pan and zoom reuse them like every artwork vertex.
3. **Laser page grey** (criterion 10). For a leaf on a laser page, render-core writes each stop as `over_white_grey` (ADR 0066 §4), opaque. Because the grey of an over-white composite is linear in the premultiplied channels, interpolating grey stops equals the grey of the interpolated colour: the canvas shows exactly the lightness `0123` engraves. Page thumbnails of a laser page use the same draw list.
4. **PNG** (criterion 11). The only PNG Curvyo writes is the page thumbnail of the container (`pageThumbnail.ts`), drawn by the same pipeline; it gets the gradient by construction. There is no separate PNG export to change (criterion 11 says so).
5. **Hit test** (criterion 9). Interior picking in `curvyo-ui-core` treats a gradient fill as painting where `colour_at(point)` (ADR 0066 §4) has alpha above 0 inside the fill region.
6. **SVG export** (criterion 13). `curvyo-svg-core`'s export model gains a gradient paint (`SvgGradient`: linear `x1 y1 x2 y2` or radial `cx cy r` with an optional `gradientTransform` matrix, stops as offset plus RGBA8); a new writer module writes one `linearGradient` or `radialGradient` per filled element into `defs`, ids `gradient-1`, `gradient-2`, … in document order, `gradientUnits="userSpaceOnUse"`, stops directly inside (`offset`, `stop-color="#rrggbb"`, `stop-opacity` with three decimals, enough to recover the byte), numbers by the existing `write_number`. The session's export mapping (`session/svg_export.rs`) turns the `PlacedGradient` into exported coordinates. Because ADR 0066 stores the gradient already in the leaf's frame, a rotation needs no `gradientTransform` (a similarity keeps perpendicular iso-lines and circles); only an **elliptical radial** writes `gradientTransform="matrix(…)"` with `fx fy` equal to `cx cy` (criterion 13 says the same). A text gets `fill` on its `<text>`; a linked clone exported as `<use>` inherits its original's gradient through the use transform, which is what userSpaceOnUse means; no `fill-opacity` is written for a gradient.
7. **SVG import** (criterion 14). `paint.rs` returns a third `PaintValue::Gradient(SvgGradient)`; a new reader module `gradient.rs` ("reads one gradient paint server through its `href` chain") resolves it: `href` and `xlink:href` chains of at most 16 links (an existing constant; a cycle ends the chain); each attribute (`x1`…`r`, `fx`, `fy`, `gradientUnits`, `gradientTransform`, `spreadMethod`) from the nearest link that has it, the stops from the nearest link that has any; `objectBoundingBox` through the element's box in its user space, `userSpaceOnUse` in it; the leaf's CTM and `gradientTransform` composed into one affine to document mm; stops as SVG says (offset number or percent, clamped to [0, 1], each at least the previous; `stop-color` and `stop-opacity` from attributes or `style`, `rgba()` alpha times `stop-opacity`, the element's `fill-opacity` multiplied in), a first stop above 0 or a last below 1 completed by a stop of the end colour, one stop read as two stops of that colour, no stop read as no fill. `reflect` and `repeat` are read as pad, `fx fy` away from the centre as the centre, mesh and other paint servers as no fill; each case is counted for the existing import notice. The mapping in `curvyo-ui-core` builds the ADR 0066 model with `gradient_map` (skew and unequal scale give the ellipse). `gradient_middle` and its tests go. Goldens: the export and `svg_real` sets of criteria 13 and 14, each read back.
8. **Budgets** (criterion 24, thread CPU time, `curvyo-editor-wasm/tests/cpu_time/`, native; the GPU part is checked once in the browser check on WebKitGTK). Confirmed as written: (a) a handle drag on one of 1,000 gradient shapes of 4 stops builds its frame within 16 ms; (b) 1,000 gradient shapes build within the 1,000 Colour shapes' frame plus 2 ms; (c) the Gradient block within 16 ms with 16 stops; (d) opening 10,000 gradient shapes within 10,000 Colour shapes plus 5 % (amended 2026-11-18, Proposal: no longer than 10,000 Pattern shapes and within 10,000 Colour shapes plus 30 %, each file built alike, every style register written once in one insert; measured 1.24 to 1.26 times Colour and 0.95 to 0.97 times Pattern, release, best of three, after the architect review found that the earlier files wrote the gradient's stops twice and Colour no colour; plus 5 % is not met: a gradient shape stores two more registers than a Colour one); (e) 256 stops within 2 ms more than 4 per frame, and without error.

## Consequences

- Every artwork vertex gains 16 bytes in a second stream (about 1.6 MB more at 100,000 vertices); stacking, layers and the overlay are untouched.
- `Rgba32Float` with `textureLoad` is core WebGL2. If the browser check shows a GL stack that refuses it, the fallback is option B for that adapter, decided then, not built now (`CLAUDE.md` §5).
- `curvyo-svg-core` still depends on no Curvyo crate; its gradient type is plain data and its writer is a pure function, so exports stay byte-identical.
- Rejected and why: CPU bands (A, inexact for radial, cost grows with stops), one draw call per shape (B, budget), svg-core reading Curvyo's model (ADR 0018).
