# ADR 0066: Gradient fill in the document model: `fill_paint = "gradient"`, the registers `fill_gradient` and `fill_gradient_stops`, box-fraction geometry, one evaluation in `curvyo-document-core`, format next free at merge

**Status:** Accepted 2026-11-18 (customer merged PR #389; proposed 2026-11-18 by the architect), `needs-customer` (document model, file format; `CLAUDE.md` §3). Decisions marked **(Proposal)** are the architect's and vetoable at the demo; the behaviour itself is the customer's (Frage 227 C of `0123`, Frage 232 to 236 of `0124`). Accepted with the customer's merge of the `0124` story PR, as ADR 0065 was. Extends the style schema of [ADR 0029](0029-live-pattern-fill.md) §1 with a third fill paint; no accepted ADR text changes. Spec: [`0124`](../../specs/0124-gradient-fill/specification.md) criteria 2, 4, 5, 15 to 19, 22 to 25. Drawing and SVG: [ADR 0067](0067-gradient-drawing-and-svg-gradients.md). Read as lightness by `0123`: [ADR 0068](0068-raster-dot-values-and-dithering.md).

**In plain words (for the customer).** A shape with a gradient stores three small things: "the fill is a gradient", where its line or circle sits inside the shape's box (as fractions, so it stretches with the box), and the list of colour stops. Nothing drawn is stored. Every part of Curvyo that needs a gradient colour (the canvas, clicking, SVG, the laser) asks one function, so they always agree. Files with gradients need the new version of Curvyo.

## Context

The gradient is a new fill paint beside Colour and Pattern (`0071`), with any number of stops (Frage 232 B), linear or radial with an elliptical ratio from SVG, on closed shapes, open paths and text. What is hard to change later: the stored shape of the paint, how the geometry follows the shape (box fractions, transforms, clones), and where the one colour evaluation lives, because `curvyo-render-core` (canvas), `curvyo-ui-core` (hit test, SVG mapping) and `curvyo-laser-core` (`0123`) must give the same colour. `render-core` and `laser-core` both depend on `document-core` and on nothing else they share (ADR 0011, note of 2026-11-02).

## Options

**Storage**

| Option | Why it won or lost |
|---|---|
| A. One atomic register with kind, geometry and stops | One rule, like `fill_pattern`. But a handle drag rewrites every stop (256 stops: about 6 KB per step in the log), and a stop edit on one peer and a drag on another lose one of them. Lost on merge behaviour. |
| **B. Two atomic registers: `fill_gradient` (kind and geometry) and `fill_gradient_stops` (the list) (chosen, Proposal)** | Drags write a few numbers; stop edits and drags merge without loss (ADR 0009 §2, register granularity); every combination of the two registers is valid by construction (any stop list fits any kind); the paint is not: `fill_paint = "gradient"` needs both registers, so choosing Gradient writes both with it and no write removes them (decision 2). Cost: two keys instead of one. |
| C. A Loro movable list container, one entry per stop | Per-stop merge looks attractive, but two peers adding stops at the same place interleave and the order invariant (positions non-decreasing) can break after a merge with no edit to repair it. Lost. |
| D. One text register in a compact or JSON syntax | A second parser and a string format to freeze, where the style codec already reads Loro lists (`stroke_dash`, colours). Lost as one register; its text form was taken for the two registers of B on 2026-11-18 (decision 1). |

**Geometry:** points as fractions of the shape's box (chosen, the spec's words, readable in a file and in the panel) against a 2 x 3 matrix from a unit gradient space into the box (general, but every edit and every reader would invert it). Points can express every affine image of a gradient (decision 5), so the matrix buys nothing.

**Where the evaluation lives**

| Option | Why it won or lost |
|---|---|
| **A. Model, codec, evaluation and affine mapping in `curvyo-document-core` (chosen)** | The one crate below both `render-core` and `laser-core`; it already holds `Color`, the style codec, `kurbo` for boxes, and builds for wasm32. No new crate, no dependency. |
| B. Evaluation in `render-core` | `laser-core` must not depend on a render crate (ADR 0011 extension rule). Lost. |
| C. A new crate `curvyo-paint-core` | Three consumers but one tiny module group with document-core's types only; `CLAUDE.md` §5 asks for an ADR and a reason a module does not give. Lost. |
| D. `curvyo-geometry-core` | `render-core` does not depend on it (ADR 0029 §7). Lost. |

## Decision

1. **Keys** (in the object's meta map, all three in `ALL_STYLE_KEYS`, so copy, duplicate, Paste style, Object to path, clone `own_style` (ADR 0016) and Unlink carry them like every style key):
   ```text
   fill_paint          : "colour" | "pattern" | "gradient"     absent = "colour"
   fill_gradient       : "linear X1 Y1 X2 Y2"
                       | "radial CX CY RX RY" | "radial CX CY RX RY RATIO"     absent = none
   fill_gradient_stops : "#RRGGBB[AA] OFFSET;#RRGGBB[AA] OFFSET;..."         absent = none
   number              : -?(0|[1-9][0-9]*)(.[0-9]+)?([eE][-+]?[0-9]+)?
   ```
   Each register is one string (amended 2026-11-18, before format 49 shipped, for criterion 24 d: the first draft's Loro map and list of lists made a file of 10,000 gradients 900 kB and 453 ms to open, against 843 kB and about 355 ms now; module `gradient_text.rs`, "the compact text the two gradient registers store"). Fields are separated by exactly one space, stops by `;`, nothing before or after. A number is written as the shorter of its shortest plain and exponent forms, both of which read back to the same `f64`, so every value round-trips exactly. `X`, `Y` are finite numbers, fractions of the box (0 to 1 inside it, any finite value beyond); `RATIO` is a finite number above 0, the second radius over the first, absent = 1 (not written for a circle), only on `radial`. A stop is `#` plus 6 or 8 hex digits (read in either case, written upper case, as the Colour row shows it; the alpha digits are written only when not `FF`) and an offset in [0, 1]. The list has at least 2 stops, the first offset is 0, the last is 1, offsets are non-decreasing (equal offsets are a hard edge). **No upper limit** on the number of stops (Frage 232 B); the container's size limits bound it. The fill paints a gradient iff `fill_enabled`, `fill_paint = "gradient"` and both registers read. The names avoid the legacy `fill_kind` and `fill_stops`, which `legacy_fill.rs` keeps ignoring (criterion 23); writing any fill key still runs `legacy_fill::forget`.
2. **Writes.** Choosing Gradient on a shape without a stored gradient writes `fill_paint` and both registers in one commit (`Fill: Gradient`, the defaults of criterion 2: linear from (0, 0.5) to (1, 0.5), stops Start = the Colour with its opacity as alpha, End `#FFFFFFFF`). Choosing Gradient on a shape whose gradient was kept writes `fill_paint` **and both registers** in the same commit (amended 2026-11-18, architect review B2), so a merge that keeps this `fill_paint` keeps registers of the same write; and no write removes a register: a clone's own-style reset (Original style, Own style again, Spread colours, tiling) clears every other style key and leaves the two registers (`gradient_codec::KEPT_ON_RESET`). Together a `fill_paint` of `"gradient"` that wins a merge always finds both registers, and decision 7's refusal is never reached by a merge (test `gradient_format.rs` `a_gradient_repick_racing_a_clone_style_reset_leaves_an_openable_file`). Switching away writes only `fill_paint`; both registers stay, so Gradient comes back unchanged (the `0071` rule). Kind switch, handle drag, Angle, Radius and Reverse write `fill_gradient` (Reverse also the stops); stop colour, position, add and remove write `fill_gradient_stops`. A drag is a style preview until release (ADR 0029 §11). History names as criterion 18.
3. **Typed model** (`gradient_model.rs`, "the types of a gradient fill"): `GradientFill { geometry: GradientGeometry, stops: GradientStops }`; `GradientGeometry::Linear { start: BoxPoint, end: BoxPoint } | Radial { centre: BoxPoint, radius: BoxPoint, ratio: AxisRatio }`; `BoxPoint { x: BoxFraction, y: BoxFraction }`; `GradientStops(Arc<[GradientStop]>)` (cheap to clone into the 10,000 snapshots of budget 24 d; its constructor is the only way in and checks the invariants of decision 1); `GradientStop { colour: Color, alpha: u8, offset: StopOffset }`. Newtypes, no bare `f64`. `Fill` gains `gradient: Option<GradientFill>` and `FillPaint` the value `Gradient`. `fill_opacity` stays the Colour's opacity and does not apply to a gradient: each stop has its alpha (Proposal; an SVG `fill-opacity` is multiplied into the stops on import, ADR 0067 §7). Node and layer opacity apply as to every paint.
4. **Frame and evaluation** (`gradient_eval.rs`, "the colour of a gradient fill at a point"). The fractions resolve against the box of the leaf's outlines in the leaf's own frame, the frame of ADR 0029 §4 (the object's `rotation` register; a text object's text box; an open path its box), in mm; a linked clone resolves against its root original's box and maps the result by its clone matrix, with or without own style (criterion 17), so a mirrored clone shows a mirrored shade. The result is a `PlacedGradient`: an affine map from document mm into gradient space (linear: `t = u`; radial and elliptical: `t = sqrt(u² + v²)`, the ellipse folded into the map) plus the stops. Colour at `t`: clamped to [0, 1] (pad), the two neighbouring stops (on a hard edge the later stop wins, as SVG), premultiplied linear interpolation per channel in sRGB (criterion 5's Proposal). Two forms of one rule: `colour_at(point) -> PremultipliedRgba8` for exact outputs, with `t` quantised to 1/65,536 and the channel blend in integers (round half up), and the `f32` data the GPU needs (ADR 0067 §1). Geometry uses only `+ - * / sqrt` in `f64` (ADR 0064 §2), so native and wasm agree bit for bit. **Grey** for a laser page and `0123`: `over_white_grey(c) = (13933 R + 46871 G + 4732 B + 32768) >> 16` on the colour composited over white (the 0.2126 / 0.7152 / 0.0722 weights in 16-bit fixed point, summing to 65,536); one function, used by `render-core` and `laser-core`.
5. **Transforms** (`gradient_map.rs`, "the image of a gradient under an affine map"). A command that rewrites a leaf's geometry by an affine map `A` (scale, mirror, skew of a path; Object to path of a rotated primitive; the clone matrix) writes the exact image of its gradient in the same commit: linear through the affine `t` function (the new start is `A(start)`; the new end lies on the new gradient direction, so the iso-lines stay the images of the old ones, also under skew); radial through the singular value decomposition of `A` times the ellipse's axes (new centre, new radius point on the first axis, new ratio). The new mm points are re-expressed as fractions of the new box; nothing is written when they are unchanged. A map the frame absorbs (a move; a primitive's `rotation` register) writes nothing. **Node edits** that change the box write nothing: the fractions re-fit (criterion 15). A degenerate `A` (zero area) leaves the gradient as it is.
6. **Operations** (criterion 19). A result of Boolean, Combine, Split, Break apart, Offset, Fracture, Object to path that keeps the first input's fill keeps its gradient **with the picture unchanged**: the input's placed geometry is re-expressed as fractions of each result's box (`GradientFill::rebased`, Proposal; "re-based" in the spec read as "the shade stays where it was", so broken-apart pieces continue one shade). Paste style copies the fractions as they are into the target's box (criterion 16). Spread colours (ADR 0016) never touches the gradient keys.
7. **Damage.** Lenient reads (a merged document never panics): a register that does not read is absent, and a Gradient paint without both registers paints no fill. **Open validation** (`style_validation.rs`, beside `pattern_codec::keys_are_valid`) refuses the file for: an unknown `fill_paint` value, a register that is not a string, an unknown `kind`, a wrong number of fields or a separator other than one space (`;` between stops), a fraction that is not a number of the grammar or not finite, `ratio` on `linear` or not above 0, a stop that is not a colour and an offset, a colour that is not `#` plus 6 or 8 hex digits, fewer than 2 stops, offsets out of [0, 1], unordered, or not starting at 0 and ending at 1, and `fill_paint = "gradient"` without both registers. This is the rule every style key has today (ADR 0029 §2); criterion 22 states it.
8. **Format.** `CURRENT_FORMAT_VERSION` takes the **next free number at merge** (after 48; 49 if nothing merges first): an older build would draw no fill, or the Colour, where the gradient is, so it must refuse the file (ADR 0033 §7). **Migration: none** (Curvyo is not deployed). Goldens in `curvyo-document-core/tests/fixtures/`: `gradient_fill_v<N>.curvyo` (criterion 22's set) and one damaged file per refusal reason: `gradient_fill_damaged_colour_v<N>`, `_fraction_v<N>` (`"abc"`), `_one_stop_v<N>`, `_unordered_v<N>`, `_paint_without_gradient_v<N>`.
9. **Crates.** `curvyo-document-core` gains nine modules, each under 500 lines with a one-sentence doc: `gradient_model.rs` (the types), `gradient_codec.rs` ("the stored form of a gradient fill"), `gradient_text.rs` (its compact text, added 2026-11-18), `gradient_eval.rs` (the colour at a point), `gradient_map.rs` (the image under an affine map), `gradient_frame.rs` (the box a gradient is placed in), `gradient_measure.rs` (Angle and Radius in mm), `gradient_stops.rs` (the stop list edits) and `gradient_commands.rs` (the gradient commands); the last four were added while building (2026-11-18). No new crate, no dependency, no trait, no `unsafe`.

## Consequences

- One colour rule for canvas, hit test, SVG and laser; a change of interpolation (linear light, Oklab: out of scope) is one module and a format question, because `0123`'s dots depend on it.
- Published keys: `fill_paint` value `gradient`, `fill_gradient` (the words `linear` and `radial` and the field order of decision 1), `fill_gradient_stops`. Renaming one or changing the text grammar is a format change.
- Every geometry-rewriting command must call decision 5; a missed command shows as a gradient that stays put while the shape mirrors. The tester's criterion 15 cases cover scale, mirror, skew and rotate on a path and on each primitive kind.
- A stop list of 100,000 entries opens and draws (no limit); it costs its bytes in every snapshot clone only once (`Arc`).
- Rejected and why: one register (A, merge loss on drag versus stop edit), a movable list (C, order breaks on merge), one text register (D, a second parser; its text form now serves the two registers of B), the evaluation in render-core or a new crate (laser-core cannot reach the one, the other is a module).

## Amendments

- 2026-11-18 (implementer, Proposal, before format 49 shipped; no migration): both registers store one compact text each instead of a Loro map and a list of lists (decision 1, §7); still two registers, so a drag and a stop edit merge without loss (decision 2). Measured on 10,000 squares of 4 stops (release, thread CPU, best of three): file 900 kB to 843 kB (Colour 593 kB, Pattern 982 kB), open 453 ms to about 355 ms (Colour about 257 ms, Pattern about 395 ms). Criterion 24 d is amended accordingly (ADR 0067 §8).
