# ADR 0096: Pen window: a second Tauri webview with its own wasm session, kept equal to the main window through a local update bridge in `curvyo-app`; the main window owns the file

**Status:** Accepted 2026-11-27 (customer, Frage 415 A; proposed by the architect the same day); was `needs-customer` (document session and sync, `CLAUDE.md` §3). Frage 409 A (customer, 2026-11-26) already fixes what the maker sees: the same document live, selection shared, tool and view per window, optional Follow view. This ADR decides how; the customer chooses between the options below, default A. No new crate, no new dependency, no `unsafe`, no document `format_version` change. Spec: [`0158`](../../specs/0158-pen-display/specification.md) slice 2 (Ready 2026-11-27 in two parts: 2a "Pen window", criteria 1 to 20, and 2b "Pen layout and Follow view", criteria 1 to 9; the decisions below cite the draft criteria 1 to 5, mapped in the amendment of 2026-11-27, which also settles the build rules of 2a), built after slice 1 ([ADR 0095](0095-pencil-stroke-pipeline-pen-samples-to-a-fitted-centre-line-with-a-width-profile.md)). Builds on [ADR 0001](0001-ui-framework-and-canvas-rendering.md) (the document lives in wasm in the webview), [ADR 0009](0009-concurrent-editing-semantics.md) (peer-scoped undo, ephemeral state), [ADR 0031](0031-sync-engine-relay-protocol-and-transport.md) (relay sync, presence), [ADR 0079](0079-recovery-copies.md) (recovery copies) and [ADR 0094](0094-native-pen-input-on-linux-through-gdk-events-of-the-webview.md) (pen reader per webview). Choices marked **(Proposal)** are the architect's.

**In plain words (for the customer).** The pen window is a second Curvyo window with its own copy of the open project. Both copies stay equal all the time: every step you finish in one window appears in the other a frame later, the same way two computers stay equal in shared editing, only inside your computer and with nothing sent anywhere. The big window stays the owner of the file: saving, autosave and recovery happen there. Ctrl+Z in a window undoes that window's own last step. Pictures sit in memory twice.

## Context

Verified on `story/pen-pencil` (2026-11-27):
- `tauri.conf.json` declares one window `main`. `svg_export.rs`, `job_export.rs` and `connector.rs` call `get_webview_window("main")`; `project.rs`, `import_dialog.rs`, `native_file_lists.rs` and `pen_input.rs` use a `MAIN_WINDOW` constant. `pen_input.rs` attaches to `main` only, although ADR 0094 decision 1 says every webview window.
- The session (`curvyo-editor-wasm::WasmSession`) holds the `Document`, one view, one tool state, one `Gpu` and one artwork memo. A Tauri window is its own WebKitWebView with its own JavaScript realm; Tauri creates windows with no opener relation between their pages.
- `Document::export_updates(since)` and `import_updates(bytes)` (`document-core/src/history/updates.rs`) exchange Loro updates between replicas; `import_updates` checks the result like an opened file. `WasmSession::open(peer, bytes)` opens a packed container with a caller-given peer id; `Session::pack` packs the document with history and assets. The asset store is not part of Loro (ADR 0079 context); relay sync sends assets as their own message kind.
- `curvyo-ui-core::presence::PresencePayload` already carries pointer, selection (`Vec<NodeId>`), tool and drag offset, never document content.
- Undo is peer-scoped (ADR 0009 §1) and already runs with relay-synced peers in one document.
- Recovery copies are one per session key (ADR 0079 §2); `frontend/src/platform/host.ts` has no window API.
- The wasm bundle of this checkout is 32 MB (a development build; the release size is not measured here).

## Options

| Option | Why it won or lost |
|---|---|
| **A. A second webview window with its own wasm session and its own Loro peer id; the two documents are kept equal by exchanging updates, assets and presence through a hub in `curvyo-app` (chosen)** | Tool, view, pointer and GPU are per window for free, because each window has its own `Session`; undo per window falls out of ADR 0009; the update exchange, its checks and the presence shape exist and are tested with the relay; the hub uses the per-webview `tauri::ipc::Channel` already verified in slice 0. Costs: a second wasm instance and a second copy of the document and its pictures. |
| A2. As A, but the pages talk directly (`BroadcastChannel`) | Works between tabs of one browser; between two Tauri webviews on WebKitGTK (separate web processes) it is not verified, and nothing else in the app relies on it. Kept as the route for a browser-build pen window if that is ever wanted. |
| B. One session owning two views and two GPU surfaces | A wasm instance and its memory belong to one realm; it can neither receive the DOM events of another top-level webview nor configure a canvas there. It would need the pen window as a `window.open` popup of the main page sharing its realm, which depends on wry's new-window handling on Linux (not verified), and a session rebuilt for several views: `Session` keeps one view, one tool machine, one pointer, one `Gpu` and one artwork memo across dozens of modules. Undo would be one stack for both windows, contrary to slice 2 criterion 1, and a busy main window would stall the pen. |
| C. The document moves into the native process | Reverses ADR 0001 (document in wasm), drops the browser build, puts an IPC round trip into every edit and every frame's read; a rewrite of the session. |

## Decision

1. **Two sessions.** "Open pen window" in the main window creates a `WebviewWindow` labelled `pen` (same bundle, `?window=pen`), which renders the fixed Pen layout (Frage 413 A). Its page asks the main page, through the hub, for the current project, receives the bytes of `Session::pack`, and opens them with `WasmSession::open(fresh peer id, bytes)`. Main and pen are two replicas of one Loro document with distinct peer ids.
2. **Hub.** New `curvyo-app/src/pen_window.rs` (one responsibility: creating the pen window and forwarding bridge messages between the two webviews). Commands: `pen_window_open()`, `bridge_watch(channel)` (each page registers its channel, keyed by the calling webview's label) and `bridge_send(raw bytes)`, which forwards the body unchanged to the other window's channel as raw bytes. The hub does not read, store or log the messages. `host.ts` gains `windowRole()` (`main` or `pen`), `openPenWindow()` and `bridge.watch` / `bridge.send`; the browser build answers "not available" and hides the command **(Proposal)**.
3. **Messages.** A pure codec in new `curvyo-ui-core/src/window_bridge.rs` (one responsibility: the message shape between the two windows of one project): `Updates(bytes)` from `export_updates` since the version the other side last confirmed, `Asset(hash, bytes)` once per asset the other side lacks (the asset comparison as relay sync does it), `Presence(PresencePayload + view)` on change, `Project(bytes)` (a full pack, for the first load and after the main window opens another project or New), `Save` (pen to main) and `Closing`. Nothing is sealed: the bytes stay inside the app process and never leave the machine. The session glue is new `curvyo-editor-wasm/src/session/window_link.rs`: once per frame it sends what changed and imports what arrived through `import_updates`, so an import that fails its checks is refused as a relay import is.
4. **Shared and per window.** Shared: the document (through updates and assets) and the selection: each window applies the other's received selection as its own, last message wins, ids resolved lazily (ADR 0009 §2). Per window: tool and tool options, view, panels, pointer, in-flight drags (a stroke or drag in progress shows in the other window when it is committed, not before **(Proposal)**). Follow view is a pen-window setting: while on, each window sends its view on change and the other adopts it (criterion 2); independently, the main window draws the frame of the pen window's visible rectangle from the pen's view messages (criterion 5).
5. **The file belongs to the main window.** Path, Save, Save as, the unsaved-changes state, Close checks and the recovery copy (ADR 0079) stay in the main session only. The pen session has no path, no recovery writer and no save; its Ctrl+S sends `Save` to the main window. An import of pen updates marks the main session unsaved like a local step. Because every finished step reaches the main replica within a frame, the main recovery copy holds the pen window's work too.
6. **Undo.** Each window keeps its own peer-scoped stack (ADR 0009 §1): Ctrl+Z in a window undoes that window's last step, remapped over the other's edits (criterion 1). The History tab names the pen window's steps "Pen window" **(Proposal)**.
7. **Lifecycle.** Closing the pen window ends its session; nothing to save. Closing the main window closes the pen window first (the main window owns the project); quitting the app likewise. The main window opening another project or New sends `Project` and the pen window reopens on it. The pen window's size, its last position where the compositor honours it, its Follow flag and whether it was open are kept in the app's config folder (`pen_window.json`, internal record `format_version` 1 with a golden test, `CLAUDE.md` §5) and offered again at the next start (criterion 3); no window-state plugin.
8. **Pen input.** `pen_input.rs` attaches its GDK handler to each webview window when it is created, not only `main`; each page's own `pen_watch` channel receives only its own samples (ADR 0094 decisions 1, 4). The pen window feeds ADR 0095's `pen_samples` in its own session.
9. **Commands bound to `main`.** The Pen layout calls none of them (no import, export, open, save or connector); they stay as they are. Any command the pen window calls takes the calling `WebviewWindow` argument instead of a label.
10. **With relay sync on.** Only the main session holds the relay link and the keys. The pen window's steps are in the main replica within a frame and leave with the main session's next sync export, sealed by the main device in envelopes whose sender is the main session's peer id (ADR 0031 decision 4); the Loro operations inside keep the pen peer id, so the main session announces that id beside its own in its presence hello and collaborators' History tabs name those steps by the same label **(Proposal)**; remote changes arrive in the main replica and reach the pen window through the bridge. Presence of collaborators is not forwarded to the pen window in slice 2 **(Proposal)**.
11. **Measured in slice 2** on the customer's machine with a 10,000-object project and with a project of 200 MB of pictures: memory of the second webview, time from "Open pen window" to the first frame (target at most 3 s **(Proposal)**), time from a finished stroke in one window to its frame in the other (criterion 1's 200 ms).

## Consequences

- No change to the document model, the file format or the relay protocol; the second window is a second replica, a case the document already handles for relay peers.
- Memory: a second wasm instance and a second copy of the document and its pictures. A project near the 512 MiB asset limit doubles that in RAM; decision 11 measures it, and a lazy asset fetch through the hub is the named fallback.
- Steps authored under the pen window's peer id inside envelopes sent by the main session are assumed to pass the receivers' import checks like the main session's own steps (an envelope's sender and its operations' peer ids differ for the first time); slice 2 tests it against the local relay before the PR, and the presence hello change of decision 10 is the one sync-visible change.
- The pen reader and the pen-sample entry point need no change for a second window beyond decision 8.
- A browser-build pen window (option A2) stays possible later on the same codec.

**A1. Criteria map.** Decision 4's "criterion 2" is 2b criterion 5, its "criterion 5" is 2b criterion 6; decision 6's "criterion 1" is 2a criterion 6; decision 7's "criterion 3" is 2a criterion 16 and 2b criteria 4, 5; decision 11's 200 ms is 2a criteria 2 and 20.

**A2. Close order (replaces "closing the main window closes the pen window first").** The window-event handler acts on `main` only; a `CloseRequested` of `pen` is never held and asks nothing (criterion 10). A held close of `main` lets the main page ask; while it asks the pen window shows "Waiting for the main window" (A6); Cancel keeps both windows open (criterion 11 as written); Discard or a successful Save end in `quit_app`, which destroys `pen` and then exits. A close of `main` that is not held destroys `pen` and lets `main` close; without this the app would keep running with the pen window alone. macOS `request_quit` follows the same path.

**A3. Offered again (replaces "whether it was open ... offered again at the next start").** "Offered" means the command "Open pen window" is available again; the pen window never opens by itself at app start and `pen_window.json` does not record whether it was open (the product owner's Proposal, confirmed).

**A4. `pen_window.json`.** In `app_config_dir()`, the folder of `machine-choice.json` and `test-grid-choice.json`, read and written by the hub with the existing `curvyo_storage_io::{read_optional, ensure_parent_dir, write_atomic}`; no new storage-io function. Shape and placement are pure in new `curvyo-ui-core::pen_window_place` (one responsibility: the remembered size and position of the pen window and where it opens). Format 1: `{"format_version": 1, "width": u32, "height": u32, "x": i32 | null, "y": i32 | null}` in physical pixels of the desktop, unknown fields refused; a damaged, newer or missing file reads as none (defaults about 960 × 600 logical px), a read never rewrites. `opening(saved, screens, main_screen)` gives the size always and the position only when the saved rectangle's centre lies on a connected screen, otherwise centred on the main window's screen (criterion 16). The window is built hidden, sized and placed, then shown. The host keeps the last `Moved`/`Resized` values, writes 500 ms after the last one **(Proposal)** and on the pen window's close; `x`/`y` are null where the platform reports no position (Wayland). Golden file `curvyo-ui-core/tests/fixtures/pen_window/pen_window_v1.json` (read and write byte-equal) plus damaged, newer and out-of-screen cases (`CLAUDE.md` §5). **2b:** format 2 adds `"follow_view": bool, "canvas_only": bool`, written by the pen page through a pen-only command `pen_window_flags`; format 1 reads as both false and its golden stays as a read test. **A5. Wire.** Hub commands in `curvyo-app/src/pen_window.rs`: `pen_window_open()` (main only: focuses an existing `pen`, else builds `index.html?window=pen`, applies A4, attaches the pen reader, A9), `pen_window_close()` (main only: Close of the project, criterion 12, and A2), `bridge_watch(on_message: Channel)` (either window, keyed by the caller's label, a new call replaces the old channel) and `bridge_send` with the bundle as the raw body, a synchronous command so forwarding keeps call order, sent to the other label's channel as `InvokeResponseBody::Raw`, dropped when there is no other window. When `pen` is destroyed or its web process ends, the hub sends main the fixed bundle `window_bridge::PEER_GONE` and forgets pen's channel. No Tauri events are used for the link. One **bundle** per direction per frame, only when non-empty (`curvyo-ui-core::window_bridge`; both pages run the same build, a version byte is still checked): `seq: u64` (+1 per bundle), then in order `Asset(hash, bytes)*`, `Updates { bytes, needs }?` (`needs` = the sender's referenced asset hashes, sent only when that set changed), `Selection(ids)?`, then controls: `Project(bytes)`, `NeedProject`, `NeedAssets(hashes)`, `Hold`, `Release`, `Save`. `Closing` of decision 3 is replaced by the hub's `PEER_GONE`. 2b adds `View`. **Per frame**, at its start, each session runs the order `sync_frame_start` uses: (1) export its commits since `link.exported` with the assets the other side has not got (a sent-hash set seeded from the pack, scanned only when `asset_bytes()` grew, as `sync_export` does); (2) import the queued bundles in `seq` order; (3) `link.exported = version()`. The main session calls `sync_export()` right after a successful import of pen updates, before `sync_frame_start`, because `sync_apply_remote` would otherwise mark the pen's operations exported without sending them. **Selection:** sent when the local selection differs from the last one both sides know; a received one is applied, unknown ids dropped (the `drop_gone_from_selection` rule), and becomes the known one, so there is no echo. **Waiting for a picture:** an update whose `needs` names an asset missing here waits, with every later update, and `NeedAssets` goes back; the updates are imported in order once the assets arrive (criterion 3).

**A6. Refusal, reload and holding.** A refused import (`Malformed`, `Pending`, `EpochMismatch`), an undecodable bundle or a `seq` gap stops importing, drops the queue and sets "out of sync" ("Out of sync, reloading", criterion 18). **A12. Width profiles on the link and in a shared project (added 2026-11-27 after the lead's question; read in code).** The relay rule is ADR 0053 "Compatibility with older sync peers" (2026-11-07): an older build would silently drop unknown path keys, so a document that ever held editable curves or width profiles is not shared, and creating either in a shared document is refused before mutation. It sits in three places: (a) **creation**: `Document::set_width_profiles` returns `WidthPointError::Shared` when `extended_edits_blocked()` (`is_shared()`, i.e. a live sync link or a keyring, or a workspace share record), and the width editor refuses with "Width profiles cannot be edited while the document is shared."; (b) **export**: `sync_export` and `upload_snapshot` send nothing once `has_extended_path_history()` holds (a monotone root marker), with the notice "Documents with editable curves or width profiles cannot be shared yet."; (c) **import**: `import_shared_updates` and `merge_snapshot` refuse a marker write. **The link carries every document register, width profiles and editable curves included**: same maker, same build, same format, no older peer. It does so because `window_link` imports with plain `Document::import_updates` (format, path-tree and epoch checks, no marker refusal) and never calls `sync_export`'s checks; the relay's checks are not touched. **In a relay-synced project** the pen session must refuse what main refuses, or a pen stroke would write the marker into main through the link and main would stop sending the whole document: the main session sends its blocked state (`extended_edits_blocked()`) in every `Project` and when it changes (new control `Shared(bool)`), the pen session applies it (`set_live_share`), and while main is shared it imports pen updates with `import_shared_updates`, so a marker that still arrives is refused and the pen reloads (A6). **What the maker sees today with the main window alone** (read in `session/pencil.rs`, not yet tested): the "Pencil stroke" batch writes the path and the stroke width Max, `set_width_profiles` is refused, the closure returns `None`, and the step is still committed: a uniform stroke at Max width, not selected, no notice. Only the profile is dropped, for the maker and the collaborators alike, and the stroke syncs. The pen window behaves exactly the same. That silent drop is a slice-1 defect for the product owner (a notice, or the stroke at the current width as for a stroke without pressure). **Required 2a tests:** a pressure stroke drawn in one session arrives in the other with an identical centre line and width profile (both directions, also after a reload); in a shared project a pen-window pressure stroke ends like the main window's, writes no marker, and main keeps syncing; a marker update from a pen session that ignored `Shared` is refused by main and reloads the pen.
