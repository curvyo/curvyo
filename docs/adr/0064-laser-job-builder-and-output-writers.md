# ADR 0064: Laser job builder, gate and output writers in `curvyo-laser-core`: one format-neutral move list for the file, the preview and the estimate; one writer module per output format, GRBL first

**Status:** Accepted 2026-11-17 (customer merged PR #371); amended 2026-11-17 after the customer's try of PR #371 (`ux-notes.md` §15 M9 to M16: no Output tab, one Start value, no Head position warn; decisions 1, 7, 8, 9, 10, 12, marked "Amended 2026-11-17 (try)"). Proposed 2026-11-16 (architect), amended 2026-11-16 after the customer's review of PR #370 ("GRBL is only one solution, there can be other formats; it must be easy to extend"). Not `needs-customer`: no new crate, no dependency, no platform, UI framework or format decision (the stored part, including the profile's `output_format`, is [ADR 0065](0065-laser-output-settings-and-air-assist.md)). Choices marked **(Proposal)** are the architect's, vetoable at the demo. Spec: [`0029`](../../specs/0029-laser-job-preview-and-output/specification.md) criteria 1 to 39, Fragen 219 to 226 answered 2026-11-16. Feature notes: [`0029` adrs.md](../../specs/0029-laser-job-preview-and-output/adrs.md). Builds on [ADR 0046](0046-laser-operations-record.md) (operations, nearest rule), [ADR 0052](0052-laser-fixture-jobs-in-the-project-file.md) and [ADR 0059](0059-fixture-sets-job-fixtures-and-pins-in-the-project-file.md) (fixture jobs), [ADR 0054](0054-laser-settings-and-test-grids-in-the-project-file.md) §2, §3 (effective numbers, refresh), [ADR 0056](0056-laser-operation-tools-in-the-project-file.md) (options, `motorised_z`), [ADR 0057](0057-test-grid-object-with-derived-operations.md) §5 (the Lasered hook), [ADR 0003](0003-geometry-kernel-booleans-offsetting-vcarving.md) (kernel). The file is the job [ADR 0035](0035-machine-connector-protocol.md) will later stream (GRBL there too, for now).

**Note (ADR 0069 §1, §13, with the `0123` story, 2026-11-19):** §4: raster output is the Image kind's (sweeps, `MoveKind::Sweep`, ADR 0069 §1); in every other kind the session hands an image on as the one closed ring of its frame and a gradient leaf as its outlines, so no pixel is read outside Image.


**Note ([`specs/0150` adrs.md](../../specs/0150-operation-always-has-numbers/adrs.md), proposed 2026-11-24, with the `0150` story):** §3 and §8: `NoSettings` no longer exists and blocks nothing (`NumbersRead::NoSettings`, `Cause::NoSettings` and " has no power and speed." go); `DamagedSettings` stays a warning; the frame's stand-in numbers serve fixture blocks only (decisions 6, 8).

## Context

`0029` turns a laser page into one job file and shows, before anything is written, the run on the page (Toolpath view with a scrub slider), its length and time, and a gate that names the machine and every number. GRBL G-code is the first output format; the customer expects others (Marlin, Ruida, LinuxCNC, ...) and wants adding one to be easy. Criterion 9 asks that view and file cannot differ; criterion 31 that two exports are byte-identical; criterion 36 sets CPU budgets. What must stay cheap to change: the core/platform boundary, determinism of the file, the single source of moves, and the seam where a format plugs in. What may change freely later: the time model, the order heuristic's speed, the formats themselves.

## Options

**Where the job lives**

- **A. New modules of `curvyo-laser-core`, one public module `job` (chosen).** It already owns the kinds, the run order, the settings rule, Cut-out contours, fixture parts and the profile; the job reads all of them. Pure, `#![forbid(unsafe_code)]`, wasm32 in CI already. No new crate, no new dependency (criterion 34).
- **B. A new crate for output formats.** Would depend on `curvyo-laser-core` for every input type, and there is one machine family and one format (`CLAUDE.md` §6). An ADR and a crate for no second user. Rejected; revisit when a plotter or CNC family arrives.
- **C. In the wasm session.** Core logic behind a UI crate, no golden tests without a session, breaks `CLAUDE.md` §6. Rejected.

**One source for file, view and estimate**

- **A. One format-neutral move list (chosen).** The builder produces the job's moves in integer micrometres with what any controller needs and nothing of a dialect; every writer, the Toolpath view, the summary and the scrub timeline read that list. Criterion 9 holds by construction, for every format.
- **B. A G-code text parsed back for the view.** Double work per frame, a parser in production, and the preview would be GRBL's. Rejected (the tester's parser stays test-only).

**How a format plugs in**

- **A. One closed enum `OutputFormat` in the profile and one entry point `write(format, &job) -> Vec<u8>` that matches on it; one writer module per format (chosen).** Adding a format is one module, one enum value and one `match` arm per format-specific function; the compiler lists every place a new value must be handled. Nothing generic exists before it is needed.
- **B. A `JobWriter` trait with one implementation.** `CLAUDE.md` §5: no trait without a second implementation. The `match` becomes a trait when the second format arrives only if the arms grow past a few lines each. Rejected for now.
- **C. A user-editable template (LightBurn's custom G-code, Inkscape plug-in style).** Text in, text out; no determinism guarantee, no golden test, a speculative option. Rejected.

**Caching (criterion 36 d)**

- **A. Plan per operation, cached by a fingerprint of its inputs and its entry point; numbers applied in a linear pass (chosen).** Power, speed, passes and Output changes never re-plan geometry.
- **B. Rebuild the whole job per revision.** 100 ms on a 1,000-item page at every typed number. Rejected.

## Decision

1. **Modules** (`curvyo-laser-core`, `pub mod job`; each module's doc says its one responsibility; ≤ 500 lines each):
   - `job_input.rs`: the input the session passes (types only): per running block (operation or fixture job, in run order) its kind, numbers, options and the leaves that run in it by the nearest rule, each leaf as page-space outlines (`Vec<OutlineTriple>` + closed) or an image frame, with node id and stacking order; Cut-out leaves grouped by their item. Text, clones, placed pages and transforms are resolved to page space by the session (it already does so for the Operations look and Cut-out); the core never shapes text.
   - `job_numbers.rs`: the numbers each block runs with (decision 3).
   - `job_order.rs`: inner first, then nearest (decision 5).
   - `job_hatch.rs`: the scan lines of one Engrave area (decision 6).
   - `job_plan.rs`: the ordered burn paths of one operation, by kind (`kind_run`, `cut_out_contours`, hatch, order).
   - `job_moves.rs`: the job's format-neutral moves (decision 7).
   - `job_timeline.rs`: lengths, the time estimate and the head position at a time.
   - `job_gate.rs`: the gate (decision 8).
   - `job_effects.rs`: what a successful export changes in the project (decision 11).
   - `job_fingerprint.rs`: the plan cache key, FNV-1a 64 over the inputs' bits, written out (no dependency).
   - `job_write.rs`: the one entry point `write(format: OutputFormat, job: &Job) -> Vec<u8>` and the format facts the UI needs (decision 12); a `match` per function, no logic of its own.
   - `job_write_grbl.rs`: the GRBL G-code bytes of a job.
   - `output_settings.rs`: reads the page's output registers of ADR 0065 (fixture material and Start; amended 2026-11-17 (try)).
   - `job_gate_rows.rs`: the run facts of the gate and the numbers line of a block (amended 2026-11-17 (try): also called for rows that do not run, decision 8).
   - `job_gate_text.rs`: the words of the gate: a check's three parts, the numbers line, the machine line (amended 2026-11-17 (try), decision 8).
   `OutputFormat` lives in `machine_profile.rs` beside `OriginCorner`, because it is a profile field (ADR 0065 §3). `curvyo-geometry-core` gains two public functions: `flatten_outline(anchors, closed, Tolerance)` (the existing bit-identical `flatten`, now exported) and `direction_of_degrees(f64) -> Vec2` (`libm` sin and cos, the crate's existing dependency). No `-io` crate changes: the app writes the bytes through the save dialog of the SVG export (`0024` criterion 4).
2. **Units and determinism** (every format). Curves are flattened at **0.0095 mm**, then every point is rounded to whole micrometres (`i64`); the 0.0005 mm rounding keeps the total deviation within criterion 17's 0.01 mm. The move list holds straight segments only; no writer adds arcs. Everything after rounding is integer except hatch intersections (f64 `+ - * /`, rounded to µm at once). Comparisons of distance are on squared `i64`; ties break by stacking order, then outline index, then node index. No `HashMap` iteration reaches output; scan directions come from `libm`. No clock, path, user, version or random value reaches a writer (criterion 24): a writer is a pure function of the job. **GRBL text** (`job_write_grbl.rs`): coordinates printed from µm as `<int>.<3 digits>` (never `-0.000`), S and F whole numbers, LF line ends, ASCII only (other characters in names become `_`, comment lines cut at 80 characters, Proposal).
3. **Effective numbers.** An operation's numbers are `resolve(read, kind, materials, profile_id).run()` of ADR 0054 §2 with the same loaded library the operation rows use, so gate and row agree (criterion 3). `NoSettings` blocks (4 a); `Damaged`, an Unknown kind or damaged `op_options` run nothing and warn once (criterion 33). The job carries per block: power in tenths of a percent, feed `min(speed, max_feed)` in mm/min (`RunSettings::over_feed` warns), passes; Engrave + Outline carries the hatch with `main` and the outlines with `outline`, each with its own passes (Proposal: hatch passes, then outline passes). How power becomes a controller value is the writer's: GRBL writes `S = (power_tenths × max_power + 500) / 1000` in integers, `max_power` being the profile's S-max. **Fixture jobs** run with the page's pick (ADR 0065 §1): the picked material's set of the job's kind for the page's profile id (power, speed, passes, interval); no pick, a material not loaded here, or no set for that laser and kind blocks (4 a, Frage 221 B; Proposal for "not loaded": block rather than guess). Fixture jobs have no `op_options`: defaults (bidirectional, 0 degrees, no crosshatch, no overscan, no Z).
4. **What a kind writes** (criteria 13 to 19): as the spec states; images in Engrave are dropped before planning (Frage 226 A), images in Cut and Score give their frame as a closed path. The fill rule is the document's one rule, nonzero over all outlines of the leaf; open outlines of a leaf with a closed one are closed by a line for hatching.
5. **Order inside one operation** (criterion 22, Frage 225 A). A path P must run before every closed path that contains it (closed in closed: `outline_nesting`; an open path is inside when all its nodes are inside, `contains_point_in_outlines`). Among the paths whose contained paths have all run, the next is the one with the start nearest to the head (closed: any node, kept in drawn direction; open: either end, reversed when its end is nearer). Hatch blocks of Engrave leaves take part in the nearest choice only (four entries: first or last line, either end; no nesting rule, Proposal: it protects cuts, not fills). The head starts at the machine origin's page point for the first block and at the previous block's exit for the next, so an operation's plan depends on its own inputs and its entry point only. The result is defined by the brute-force rule; a spatial index is allowed only if it gives the identical order (tested against brute force on random fixtures).
6. **Hatch** (criteria 14, 15). Lines in the frame turned by the Scan angle, Interval apart, the first half an Interval inside the area's box; each line cut against the leaf's polylines, spans by nonzero winding; bidirectional alternates direction per line, else each line runs the same way with a laser-off travel back; Crosshatch hatches the leaf again at +90 degrees right after (same block and pass). **Overscan run-out:** `overscan % × v² / (2 × 1,000 mm/s²)` with `v = feed / 60`, laser-off at the burn feed before and after each span (Proposal: 1,000 mm/s² because the profile has no acceleration). In Machine origin mode the run-out is clamped to the work area.
7. **The move list** (what any controller needs, nothing more). `Job { name, machine: ProfileValues, frame: Frame, start: Start, home: PointUm, blocks: Vec<Block>, moves: Vec<Move> }` (amended 2026-11-17 to the built shape: the writer reads Air assist, Laser mode, the output format and the feeds from `machine`, the page copy's values, instead of copied single fields; `home` is where the head starts and returns). `Move { to: (i64, i64) µm, kind: Burn { role } | Travel | RunOut | Z(µm), block }` in page µm; `Block` holds its ring, name, kind and the numbers of decision 3 (amended 2026-11-17 (try): `Ring::Operation(digit) | Ring::Fixture`, the digit being the operation row's number in the Operations tab as the session passes it in `job_input`, UX P26; the run order is the block's index, the core counts no run numbers); `Start` is one closed enum `MachineOrigin | HeadPosition | HomeThenOrigin` read from the one register of ADR 0065 §1 (amended 2026-11-17 (try); the first build's `Start { from, home_first }` and the Home first rule are gone); `Frame` is the origin corner and the page size. Passes repeat the operation's path list in the same order (Frage 223 A). A Z offset is a laser-off `Z(offset)` before the first pass and `Z(0)` after the last, only with `motorised_z`. Machine origin and Home, then machine origin start with a travel from the origin and end with a travel back to it (the two give the same moves; only the writer's first line differs); Head position starts at the first burn start (no first travel) and ends at that point. **Machine coordinates** are one format-neutral function `machine_point(frame, p)` in `job_moves.rs` that every writer calls (BL: `(x, H − y)`, TL: `(x, y)`, BR: `(W − x, H − y)`, TR: `(W − x, y)`, W and H the page size in µm; page Y grows down); the list itself stays in page µm for the preview. The plan never depends on the start mode or the format. **GRBL** writes: `$H` as the first line after the header with `HomeThenOrigin`, then exactly the Machine origin file (G90 from the machine origin, no work offset; amended 2026-11-17 (try)); `G21`, `G90` or `G91` for Head position (every move the exact µm difference of rounded points, the end the negated sum, so nothing drifts), `G17`; `M5` then `M4 S0` (profile Laser mode on) or `M3 S0`, and in M3 an `M5` before each travel; `G1 … F.. S..` carrying F and S where they change, `G0` travels, run-out as `G1 … S0` at the burn feed; Z as `G1 Z<offset> F<feed>` and `G1 Z0` (relative deltas in G91; GRBL refuses `G1` with no feed); `M8` before the first burn and `M9` at the end with `air_assist`; the comment header of criterion 24. Start Machine origin writes exactly the criterion 26 file; the goldens `home_first.gcode` and `start_head_position.gcode` keep their bytes (their fixtures change only the start value's spelling).
   **Amended 2026-11-24 (`0118` slice 2c, [`0118` adrs.md](../../specs/0118-machine-control/adrs.md) O4, O5).** `Start` gains `UserOrigin` (absolute `G90`, no `$H`). `Job` gains `shift: PointUm` (page µm, zero for every other start); `Job::machine_point(p) = frame.machine_point(p + shift)` and `Job::page_point(m)` are what the writers and the frame outline call, while `Frame` stays the pure bed mirror. The plan is built exactly as for Machine origin; `job_anchor.rs` takes the box of the burn points, its corner at the profile's origin corner is the anchor `A`, and `shift = frame.page_point(U) - A` puts it on the stored user origin `U`; `home = A`, so the file starts and ends on `U`. The plan still never depends on the start mode.
8. **Gate type** (`job_gate.rs`, format-neutral): `Gate { machine: MachineLine, mode: ModeLine, fixture: Vec<FixtureLine>, operations: Vec<OperationLine>, issues: Vec<Issue> }`; `Issue { cause: Cause, count: usize, targets: Targets }` with `Targets::Items(Vec<NodeId>) | Operation(NodeId)`; `Cause` is one enum whose variant order is the display order of criteria 4 and 5 (blocks first), then damaged settings (33) and the head-position warn (38) last; `Cause::severity()` and `Cause::text(count)` in core; `Gate::export_allowed()` and `first_block()` give the button and its tooltip. `MachineLine` ends with the format's name and `ModeLine` is the format's own line, both from `job_write.rs` (GRBL: "Dynamic power (M4)" or "Constant power (M3)", "S 0 to <max_power>"). An unknown `output_format` in the page copy makes the copy damaged: block (c), so nothing is ever written in a guessed format. Operation lines carry the `SettingsState` source words (live, stored, typed per field). The bed check (4 b) is on the burn moves' box with 10 µm tolerance, counted per leaf; off in Head position mode. GRBL has no check of its own; a format that has one (decision 12) adds its `Cause` variants here.

   **Amended 2026-11-17 (try)** (UX §15 M9 to M14; supersedes the paragraph above where they differ):
   - **One text-free list.** `Gate { machine: MachineFacts, runs: Vec<RunFacts>, issues: Vec<Issue> }`. `Cause` variants carry ids, kinds, counts and numbers, never a sentence (`NoSettings { op: NodeId }`, `TypedOverride { op, material, fields }`, ...). Amended 2026-11-17 (review, to the built code): the material causes (`FixtureNoSet`, `MaterialNotFound`, `NoSetForLaser`, `TypedOverride`) carry the material's **name**, not its record id. The name is the settings rule's: the live record's, or the one stored with the link when the record is not found (`MaterialNotFound`), so a lookup by id in the loaded library would have nothing to show for exactly the cause that needs it. Operation names stay out of the cause and come from the `Names` lookup, since an operation is always in the page. `RunFacts { block: NodeId, ring: Ring, time_s, numbers: Vec<NumbersLine>, no_settings }` per running block. The operation rows (line 2 ring and time) and the checks read this one list; the row's "No settings" and "–" and a check's "has no power and speed" come from the same `NoSettings` issue, so rows and checks cannot disagree.
   - **Words in one module.** `job_gate_text.rs` turns an issue into `CheckText { before, button, after }` with a `Names` lookup the session passes (operation names from the page's operations; material names are in the cause, see above); the button part is placed by the cause, not found by searching the sentence. It also formats the numbers line ("35 %, 6,000 mm/min, 1 ×, 0.25 mm", "typed") and the machine line. No sentence is built outside it.
   - **Machine line** (P30): "`<profile> · <format name>`", " · air assist" when on; "Machine profile damaged" for a damaged copy. `ModeLine` and `job_write::mode_line` are removed (no reader left; laser mode and the S range stay in the Machine block).
   - **Start.** `Cause::HeadPosition` (the warn) is removed. In Head position the bed check measures from the job's own box: the work area is placed with its origin corner on the matching corner of the burn moves' box, and the leaves outside it block as `OutsideBed` (criterion 38; Proposal). A damaged Start register (ADR 0065 §1) adds the block `StartDamaged` with `Targets::StartPick`, ranked after `MachineDamaged`; the job is built with Machine origin so the preview still draws, but nothing is written from a guessed start (as `output_format`; Proposal).
   - **Targets** gain `StartPick`; `Operations(ids)` selects, unfolds and scrolls the row in the same tab (P15), `FixturePick` expands the Fixture jobs section.
   - **The `0101` summary count lines** (not assigned, runs while hidden, Output off) are the gate's `NotAssigned`, `HiddenRuns` and `OutputOff` issues from `GateFacts`, built by the session from the same operations index; the Operations view no longer counts them itself (P28). Its "Runs N operations, M items." line is the total's second line. The select buttons stay as `0101` accepted them (lead decision, 2026-11-17): `GateFacts` carries the item lists of the summary (`session/operations/items.rs`), so `NotAssigned`, `HiddenRuns` and `OutputOff` target `Items` (the Output off line names its operations and selects the items in them, `GateFacts::output_off_items`), and "M items" of the total's work line selects the running items (`select_operation_items("running")`).
   **Amended 2026-11-24 (`0118` slice 2c, [`0118` adrs.md](../../specs/0118-machine-control/adrs.md) O7).** With Start User origin the bed check measures the placed job: `bed_offset` returns the job's `shift`, so `OutsideBed` blocks as for Machine origin; `Cause::OutsideBed` gains `over_um: Option<i64>`, set only with User origin (the largest overshoot of the placed burn box over the four bed edges), and the text adds "by <n> mm". A Start `user_origin` with no readable point is `StartDamaged`.
9. **Cache, laziness and budgets** (criteria 12, 36; thread CPU time in `curvyo-editor-wasm/tests/cpu_time/`, which already has the clock; no dev-dependency in `curvyo-laser-core`). The session builds the job only while the Toolpath view is pressed or the Operations tab of a laser page is shown (amended 2026-11-17 (try): the rows' times and the output group live there; (e) reads "the Operations tab with the output group opens in 100 ms"), at most once per frame, keyed by its `Arc<DocumentRead>`, the library generation and the page (as `LeafCache`); each operation's plan is reused while its fingerprint and entry point are equal. Writing runs only on Export. Confirmed limits: (a) 1,000 Cut items of 20 nodes plan in 100 ms; (b) 200 x 200 mm Engrave at 0.1 mm in 150 ms; (c) with Crosshatch 300 ms; (d) gate and summary after an edit that keeps every plan valid (numbers, material, Output, the page switches) in 16 ms on 50 operations and 1,000 items; an edit of geometry re-plans the touched operation and the later ones whose entry moved, inside (a); (e) the Operations tab with the output group and a cached job in 100 ms; (f) a slider move on 1,000 Cut items redraws in 16 ms; pan and zoom with the view pressed in 16 ms.
10. **Preview path.** The session keeps, per job, a document-space draw cache of the moves (polyline runs per kind, the numbered ring per block, arrowhead per burn path) plus the timeline's cumulative length and time per move. A new render-core module `toolpath_look.rs` ("draws a cached toolpath up to a head position") emits the frame's draw list from that cache and the view transform; sub-pixel runs may merge in the draw only, never in the job. The slider position is a **fraction of the estimated time** (Proposal: Play is then the run in time, 10 s whole); the head is found by binary search over cumulative time and the move it falls in is split, so a slider move never rebuilds the job (36 f). Play's ticking is the frontend's `requestAnimationFrame`; the core gets positions only. Toggle and position are session state. Nothing of the preview knows the format. Amended 2026-11-17 (try): a ring's label is its block's `Ring` (the row's digit, or the fixture glyph for the fixture jobs of one kind); the readout is time only ("<elapsed> of <total>", criterion 37), the timeline's lengths feed the total and the tests, not the bar.

   **View JSON ownership (amended 2026-11-17 (try)).** `session/output/` owns the job cache and is the only reader of `Gate`; it answers three narrow reads and builds no other tab's JSON: `row_runs()` (per operation id: ring digit and time; read by `session/operations/view_json.rs` for line 2 and the row's accessible name), `fixture_runs()` (the fixture pick and one run line per kind; read by the Fixture jobs section's view) and `output_group_view()` (machine line, Start, checks, total, Export; `output_group_json`, the only JSON `session/output/view_json.rs` builds). Line 3 of every row (Output on or off, running or not) comes from the operations view itself through `job_numbers` + `job_gate_rows::numbers_lines`, the same functions the job runs, so it needs no job and shows on rows that do not run (criterion 3 holds by construction). The Output tab view (`OutputView`, `output_view_json`, runs heading, mode line, the run rows' material and source word, `HOME_FIRST_TOOLTIP`) and `PanelTab::Output` / `PanelContent::Output` in `curvyo-ui-core` are removed.

   **Amended 2026-11-17 (review, to the built code).** The reads are built once per job, not per frame: `PageJob` (`session/output/job_cache.rs`) holds `tab: OnceLock<TabFacts>`, and `job_with_facts` fills it on the first read of a job. `TabFacts` (`session/output/view_json.rs`) holds the rows' runs (ring digit and time, from `Gate::runs`), every row's line 3 (the numbers a running block was built with, any other row read with `block_numbers`, the same function; `None` for an Unknown kind or damaged settings), the operation `Names` the checks use and the `0101` summary of the total's work line. `session/operations/view_json.rs` reads `runs` and `numbers` from it (`row_numbers` only on a page without a job), so a frame of the Operations tab resolves no row's numbers again (budget (d), (e)). The fixture read is `fixture_output_view()` in `session/output/fixture_pick.rs` (the pick, one run line per kind and the header's time), embedded by the Fixture jobs section's view as its `output`; there is no separate `fixture_runs()` or `row_runs()` entry point.
11. **Export and undo** (criteria 27 to 30). `export_job` returns the bytes of `write(format, &job)`, the default name with the format's extension, the format's file type and a token for the exported job; the frontend saves it. Only on a successful write does `export_job_done(token, now_ms)` run: (1) one history step `export_job` "Export job file" switching off every fixture job of the job (pins' Centre mark and Diameters jobs included) and writing `refresh(.., guard: false)` of every linked operation in the job; (2) a second commit with the reserved label `mark_test_grid_lasered` (made a reserved non-step label, like `refresh_material_numbers`; the hidden test hook of ADR 0057 §5 writes the same commit) setting `test_grid_lasered = now_ms` on every grid with at least one derived operation that wrote a move; (3) the matching test records' `lasered` in the material library, written without a journal entry. Undo takes back (1) only; Lasered stays (spec Proposal). The ids come from the token's job, so an edit during the dialog changes nothing of what is recorded; a gone id is skipped. Cancel or a write failure calls nothing. A record write failure shows the library's write notice; the document part stands.
12. **Output formats** (criterion 39). `OutputFormat` is a closed enum with one value, `Grbl` (spelling `"grbl"`, name "GRBL"). `job_write.rs` holds, as one `match` each: `write(format, &job) -> Vec<u8>`, `name(format)`, `extension(format)` (GRBL `"gcode"`), `file_type(format)` (GRBL "GRBL G-code", the save dialog's filter) (amended 2026-11-17 (try): `mode_line` is removed, nothing reads it any more); `ALL: &[OutputFormat]` lets the Machine block show a pick only when it holds more than one value (ADR 0065 §3). The dialect's bits stay in its writer and its profile fields: for GRBL the S range (`max_power`), M3 or M4 (`laser_mode`), M8 and M9, `$H`, G90 or G91 and the comment header; the builder, gate, preview and timeline never read `max_power` or `laser_mode`. **Adding a format** is, and is only:
    1. one enum value and its spelling in `curvyo-laser-core/src/machine_profile.rs`, with a profile record format and project `format_version` bump (ADR 0065 §3: older builds must not write such a profile as GRBL);
    2. one writer module `curvyo-laser-core/src/job_write_<format>.rs` and its arm in each `match` of `job_write.rs`; profile fields only that format reads go into `ProfileValues` with the same bumps;
    3. golden files in `curvyo-laser-core/tests/fixtures/output/<format>/`, written from the same `job_input` fixtures as `output/grbl/`, plus a test-only reader of that format;
    4. gate hooks: in `job_gate.rs` the `Cause` variants and one `match` on the format for anything it cannot do (for example no relative moves blocks Start Head position, no home command blocks Home, then machine origin), their words in `job_gate_text.rs`;
    5. in the frontend, the Machine block's read-only "Output: GRBL" line becomes the pick of ux-notes 8 (once, with the second value).
    The move list, the order, the hatch, the gate's other rules, the Toolpath view, the timeline and the export flow do not change.
