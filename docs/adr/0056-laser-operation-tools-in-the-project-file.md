# ADR 0056: Laser operation tools in the project file: group assignment with existing keys, clone-member keys read as legacy, Interval in `op_settings`, operation-only settings in `op_options`, a motorised Z axis in the profile, format 44, profile record format 4

**Status:** Accepted (PR #350), `needs-customer` decided with the customer's merge of 0111 (document model, file format, machine profile record). Built on the customer's decisions of 2026-11-12 (Frage 197 A, 198, 205 B; the material set holds power, speed, passes and interval only; Z offset only with a motorised Z axis) and Frage 212 and 213 with their defaults (A, A). On acceptance, notes go on [ADR 0046](0046-laser-operations-record.md) §2 and §7 (clone-member keys legacy, group assignment), [ADR 0054](0054-laser-settings-and-test-grids-in-the-project-file.md) §1 and §2 (`interval_mm`), [ADR 0038](0038-machine-profile-records.md) §2 and [ADR 0039](0039-machine-profile-copy-in-the-project-file.md) §1 and §5 (`motorised_z`). Spec: [`0111`](../../specs/0111-laser-operation-tools/specification.md). Feature notes: [`0111` adrs.md](../../specs/0111-laser-operation-tools/adrs.md). First of three redesign ADR sets: 0057 and 0058 (`0112`), 0059 and 0060 (`0113`) build on it.

## Context

`0111` moves the kind buttons to the Select bar, gives a group one operation without a member list, takes clone members out of operations, and adds settings that belong to the operation and never to a material: Interval (a material number from `0112` on), Crosshatch, Bidirectional fill, Scan angle, Overscanning and Z offset. Z offset exists only on a laser with a motorised Z axis, a new machine capability. What must stay cheap to change: the stored shape of an operation and of the profile record (both published).

## Options

**Group assignment (Frage 198)**

- **A. Existing `member.` keys: the group's key, plus the key on each node inside the group that holds an assignment of its own (chosen).** The nearest rule of ADR 0046 §7 stays exactly as it is; the tick state is derived. No new key form, no format change for this part.
- **B. A new "whole group" key (`member.<group>!`) that overrides members' own keys.** Changes the nearest rule for every reader, including `0029`. Rejected.
- **C. Keep the member list.** The customer removed it. Rejected.

**Where the operation-only settings live**

- **A. A second atomic register `op_options` beside `op_settings` (chosen).** No material code path reads or writes it, so criterion 23 holds by construction; an option toggled on one replica and a material refresh on another merge without losing either; an operation with "No settings" can still carry a Crosshatch.
- **B. A sub-map inside `op_settings` (the lead's first idea).** One register for everything, but the refresh at save (ADR 0054 §3) and a concurrent toggle would keep one whole value and drop the other, and `op_settings` absent ("No settings") could not carry options without a new partial shape. Rejected.
- **C. One register per option.** Fine-grained merge, but five more damage paths and no single "settings the maker chose" value. Rejected.

**Interval** goes into `op_settings.main`, not `op_options`, because `0112` makes it a material number: it must sit inside the atomic link (ADR 0054 option A).

## Decision

1. **Group assignment** (amends ADR 0046 §2 by adding a write rule; no key form changes). Assigning a group G to an operation O writes, in one commit, `member.<G>` and `member.<D>` on O for every node D inside G (any depth, own nodes of the page; placements included) that holds at least one `member.` key on any operation. Unassigning G from O removes `member.<G>` and O's keys of every node inside G. Memberships those nodes hold in other operations stay. The tick (checked, mixed, unchecked) is derived from G's leaves by the nearest rule; "mixed" assigns the rest by the same rule. Inner rows of placed pages are not nodes of G: a group assignment does not reach them (their own key still wins), and the tick reads mixed (Proposal). The rule is pure, `curvyo-laser-core/src/operation_group.rs` ("the keys a group assignment writes and the group's tick state"), over the membership index the session already caches (`0101` adrs).
2. **Clone-member keys are legacy (Frage 212 A, amends ADR 0046 §2 and §7).** A key whose path holds more than one id (`member.<clone>/<member>`) is read as a legacy key: kept, saved back unchanged, ignored by the nearest rule, the tick and every count. No command writes one; the assign command refuses a path. The chain of a leaf inside a clone ends at the clone and then the clone's outer chain, so the leaf runs with the clone's operations. The delete sweep (ADR 0046 §3) and the off-page sweep (§4) keep removing a key whose path names a dead or moved node. Inner rows of placed pages stay as built (Frage 213 A).
3. **Kind button reuse (Frage 205 B).** "Last operation of a kind" is a pure rule in `curvyo-laser-core/src/operation_naming.rs`: the operation of that kind lowest in the list that is not Unknown, not Damaged and not derived from a test grid (`op_grid` of ADR 0054, `op_grid_part` of ADR 0057). Shift always creates. The press writes one commit with the existing assign label.
4. **Session-only state, never in the file:** the entered group (read-only, `0111` criterion 11), the unfolded row, and the Operations view toggle per laser page. None is a history step.
5. **Interval in `op_settings`** (amends ADR 0054 §1 and §2). `main` of `engrave` and of the hatch of `engrave_outline` may hold `interval_mm`: 0.01 to 2.00 with at most two decimals, a newtype `Interval` in hundredths (`u16`) in `curvyo-laser-core/src/material.rs`; absent reads as 0.10 and is not damage (format-43 files). `overrides.main.interval_mm` is allowed. `interval_mm` in `outline`, or on any other kind, is damage. **Link rule:** the material number for Interval is the material set's interval when the set has one (record format 2, ADR 0058), else the stored `main.interval_mm`. Format-1 records have none, so in this slice a pick, a refresh and Reset to material keep the operation's interval and a typed interval writes `main` directly, never an override (`0111` criterion 19). From `0112` the ordinary link rules apply; no shape change follows.
6. **`op_options`, one atomic map on an operation node**, absent = all defaults:
   ```text
   op_options = { crosshatch: false, bidirectional: true, scan_angle_deg: 0.0,
                  overscan_pct: 2, z_offset_mm: 0.0 }      // every key optional
   ```
   `crosshatch`, `bidirectional` booleans; `scan_angle_deg` −90.0 to 90.0, one decimal (tenths, `i16`); `overscan_pct` an integer 0 to 50; `z_offset_mm` −20.0 to 20.0, one decimal (tenths, `i16`). A missing key reads as its default. The four hatch keys are allowed on `engrave` and `engrave_outline` only; `z_offset_mm` on every work kind. **Damage:** not a map, an unknown key, a wrong type, a value out of range or with too many decimals, a hatch key on another kind: the operation reads **Damaged settings**, runs nothing, is saved back unchanged and never repaired on read (the ADR 0054 §1 rule). A fixture job (ADR 0052) never reads it. Writes: the label `edit_operation_settings` ("Edit settings"), the whole map, one commit per field or toggle. Material commands (Use material, Reset, refresh, material edits) never touch it. Model: `curvyo-laser-core/src/operation_options.rs` ("the operation-only settings with their ranges and defaults"); `curvyo-document-core/src/operation.rs` gets the register constant, the plain-value read and the write; it interprets nothing (ADR 0033 §3).
7. **Motorised Z axis** (amends ADR 0038 §2 and ADR 0039 §1, §5). `ProfileValues` gains `motorised_z: bool` (default false; Generic laser false).
   - **Profile record format 4:** `"motorised_z": false` after `laser_mode`, always written. Formats 1 to 3 read it as false and are not rewritten on read; the key in a format 1 to 3 record is an unknown key and damages it; a record above 4 is skipped with its notice (ADR 0038 §3). Any write upgrades to 4.
   - **Page copy:** `mfg_profile.motorised_z` (boolean, absent = false, a non-boolean reads false and is shown as damaged as the other fields, ADR 0039 §3). Pick, Reset and field edits write it with the map; "Differs from profile" compares it exactly.
   - **Use:** with it false, Z offset is not shown and nothing of it runs; a stored `z_offset_mm` is kept, saved back unchanged and shown again when it returns (`0111` criterion 21). `0029` reads `motorised_z` from the copy, never from the library.
8. **`format_version` 44.** A build of 43 reads `main.interval_mm` as an unknown key and shows every engrave with an interval as Damaged settings, and its field edit of `mfg_profile` rewrites the whole map from its own type and drops `motorised_z` silently. ADR 0033 §7 refuses both by a bump. **Migration: none.** A format-43 file opens with defaults for the new values and is not rewritten on open.
9. **Goldens.** `curvyo-document-core/tests/fixtures/`: `operation_tools_v44.curvyo` (an Engrave with interval and every option set, an Engrave + Outline linked to a material with its own interval, a Cut with a Z offset under a copy with `motorised_z` false, a second manufacturing whose copy has it true, a group assigned by decision 1 with one member holding its own key in another operation); `operation_options_damaged_v44.curvyo` (options not a map, an unknown key, scan angle 90.1, overscan 51, crosshatch on a Cut, `interval_mm` on a Cut, interval 0.005; each reads Damaged settings and saves back unchanged). `operations_v39.curvyo` and `operations_clone_member_v39.curvyo` still open; their clone-member keys run nothing and save back unchanged. `curvyo-laser-core/tests/fixtures/machine_profiles/`: `format4_motorised_z.json` (reads, writes back byte for byte), `format3_motorised_z_key.json` (damaged), `newer_format.json` moves to format 5; every older golden still reads.

## Consequences

- An operation now has three registers that decide what runs (`op_settings`, `op_options`, membership); a damaged `op_options` stops the run like a damaged `op_settings`, so a laser never runs a hatch nobody chose.
- A group assignment writes up to one key per inner node that already has its own; a group of 1,000 leaves with none writes one key. Budgets in the feature notes.
- Old clone-member keys stay in files indefinitely (until the node on their path is deleted). Nothing reads them; a codec test pins that they are kept.
- Profile records are written as format 4 on the next write; a build of format 3 then skips them with "newer version", as intended (ADR 0038 §3).
- Published keys: `op_options` and its five sub-keys, `main.interval_mm`, `overrides.main.interval_mm`, `mfg_profile.motorised_z`, the record key `motorised_z`. Renaming one is a format change.
- Rejected and why: a whole-group key (B, changes the nearest rule for every reader), options inside `op_settings` (B, merge loss and no options on "No settings"), per-option registers (C, five damage paths).
