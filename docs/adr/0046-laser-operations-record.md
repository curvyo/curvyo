# ADR 0046: Laser operations record: operation nodes under the manufacturing, assignments keyed by node id or path, run order in the laser core

**Status:** Accepted 2026-11-10 (customer accepted PR #305; document model and file format). Frage 167 to 170 answered by the customer 2026-11-09: 167 B (a member of a clone takes its own assignment, addressed by path), 168 A, 169 A (an assignment whose object is deleted is dropped silently; no "Missing item" row), 170 A. On acceptance it amends [ADR 0033](0033-manufacturing-data-in-the-project-file.md) §1, §3 and §7 by a note on its Status line (operations are child nodes of the manufacturing; `cuts_last` is an `x.*` register; `format_version` 39 for the shape). It replaces nothing. [ADR 0041](0041-membership-lifecycle.md) is the membership lifecycle of `0097` and is not touched. Feature notes: [`0101` adrs.md](../../specs/0101-laser-operations/adrs.md). 2026-11-10, after the customer's review of PR #305: the per-operation colour is dropped (`op_color` removed; an operation has no colour; the look follows from its kind, see `0101` `adrs.md` decision 8). Format 39 is not merged, so there is no migration and no compatibility to keep.

**Note (ADR 0056, proposed 2026-11-12):** §2 and §7: a group assignment also writes the keys of the group's inner nodes, and a key with a path of more than one id (`member.<clone>/<member>`) is legacy: kept, ignored, never written (0056 §1, §2).

## Context

A laser page (ADR 0042 output page, owned by its manufacturing, ADR 0032 §4) needs an ordered list of operations (Cut, Score, Engrave, Engrave + Outline, Cut-out). An item of the output page (an own object, a group, a linked clone, a member of a clone, a placed page, or a member row of a placed page) may be in any number of them. The list order is the run order, and the Cuts last switch keeps cutting after marking. The rules that matter for the file:

- An assignment whose object is deleted goes with it, in the same step. Nothing is shown as missing (Frage 169 A). Undo of the deletion brings the object and its assignment back exactly.
- Two peers reordering or assigning at once merge without losing either edit (ADR 0009 §3).
- A clone is a separate copy with its own placement and style (ADR 0016), but its members are the original's nodes. A member's own id therefore cannot be the key of an assignment made on the clone (Frage 167 B).
- The run order and the nearest-assignment rule are pure logic and run on the host and in wasm (`CLAUDE.md` §6).

What must stay cheap to change later: the stored shape of the operation and the form of a membership key (both are published with the file, ADR 0033 §3).

### Options: where the list is stored

- **A. Operation nodes as ordered children of the manufacturing node, membership on the operation node (chosen).** The tree's child order is the list order; Loro's tree moves merge deterministically; each operation is a node with per-register merge and the existing revive (ADR 0014) on undo.
- **B. One atomic list register holding all operations and their memberships.** Two peers changing different items write one value, and one edit is lost. Rejected.
- **C. Registers under `x.curvyo.laser.*` keyed by operation id, with an order key per operation.** No format bump. But the order then needs a tie-break rule written by the extension, and deletion, revive and "keep unknown" become bespoke code. Rejected: the bump costs one number, and the bespoke code would be the riskiest part of the feature.
- **D. Membership on the target node (`op.<operation id>` on each assigned node).** Deleting a target deletes its membership with it, which is the desired result under Frage 169 A; but deleting an operation writes to every target, and a clone member would need a key on the original's node, shared with the original's own assignment. Rejected.

## Decision

1. **An operation is a tree node, a child of the manufacturing node, `shape` = `operation`** (the `shape` tag that placements and fixtures already use). Its registers: `name` (existing key; the default is set at creation from the kind, numbered per kind, e.g. `Cut 2`, and is renamed in place); `op_kind` (string: `cut`, `score`, `engrave`, `engrave_outline`, `cut_out`); `op_show` and `op_output` (booleans, absent = true); `op_margin` (finite number of mm, at least 0, absent = 0; used by Cut-out only). An operation has no colour and no cut or engrave settings (power, speed: `0028`, a later step). `curvyo-document-core` validates plain types only and treats the kind as an opaque string (ADR 0033 §3); `curvyo-laser-core` interprets it.
   The list order is the child order. A reorder is one tree move; a Cuts last switch is one commit of several moves. Every operation node sits in the manufacturing subtree, so the skip predicate of ADR 0032 already keeps it out of every drawing walk. No new skip rule.
   An operation node whose `op_kind` is absent or not a string, or whose kind string is not one of the five, reads as **Unknown operation**: kept, saved back unchanged, runs nothing, is counted in no summary line, and can only be renamed or deleted (R-MFG-010).
2. **A membership is one register on the operation node: key `member.<key>`, value `true`.** Absent means not a member; removing a membership deletes the key. Merges per key (ADR 0009 §3). The key forms:
   - **Own object, group, placed page or inner row of a placed page:** `<key>` is the node id in the `history::lineage` text form (`encode_node`). A placed page's own assignment is keyed by its placement node. An inner row is keyed by the **source object's** id, so the row applies in every placement of that source (criterion 11, shared by design).
   - **A clone, or a member of a clone:** `<key>` is the **path** of node ids from the outermost clone down to the target, joined by `/`. The clone's own key is its one-id path, so it is the same form as the node-id case. A clone member is `<clone id>/<member id>`; a member of a clone inside a clone is the full chain. The separator never occurs in an encoded id; a codec test asserts it.
   - **Why a path for clone members (Frage 167 B).** The member's id is the original's node, so a key by member id alone would be the same key as an assignment on the original's member, and would apply to two different objects. The path names the member through the clone.
   - **Paths follow ids, not positions.** Moving, restyling, reordering or regrouping the original's members keeps their keys valid. A key whose path no longer names a live node is ignored (rule 3).
   - **The clone's original changes shape.** (a) An edit that keeps ids keeps the keys. (b) Deleting any node on a path removes, in the same commit, every key whose path contains it (rule 3); so ungrouping or deleting a group of the original drops the member keys under it, and undo restores them. (c) A clone that stops being a clone (its original deleted, turned into paths by the ADR 0045 repair) loses its member keys in the same commit; its own key follows its node id if the repair keeps the id (the implementer checks this with the repair test). (d) A key left by a merge with a path that is no longer live is ignored on read and never repaired on read (ADR 0033 §4); the next delete of the operation removes it.
   - **Clone rows and members are read-only in the tree.** The key lives on the operation, so the clone's stored data is unchanged by an assignment.
3. **Deleted targets (Frage 169 A).** Deleting a node removes, in the same commit, every `member.` key whose path contains that node: an own object, a group (and its members, deleted with it), a clone, a clone's member, a placement, or a source object of an inner row. A source object's inner-row key is not removed when a placed page of it is deleted, because the object itself is not deleted. Undo of the deletion (one step, ADR 0014) restores the nodes and the removed keys exactly, since the removal is part of the same step. Reads ignore keys whose path is not live (merge leftovers); reads never write. No "Missing item" row, count or notice exists.
   *Cost (2026-11-10, CI on PR #305):* the sweep runs in every commit, and a scan of the drawing's roots costs one meta read per root. A document that holds no membership key skips it: the document keeps a flag, `member_keys_may_exist`, which a new document starts without, a file sets once at open (one scan), a key write or a remote or revived import sets, and a sweep that finds no key clears. A 5,000-node template load went from 22.6 s to 2.9 s CPU (test `acceptance_0046` c33, limit 10 s).
4. **Copies, clones and removal from the laser page.** Ctrl copy, Duplicate and Paste add a key for the copy to every operation that holds the original, in the commit that creates the copy. A linked clone is a new target and starts with no keys (criterion 14). An item moved off its laser page (ADR 0045, `0106`) removes its keys, and the keys of its clone members, in the same commit.
5. **The Cuts last switch is `x.curvyo.laser.cuts_last`**, a boolean on the manufacturing node, process data under ADR 0033 §3. Absent reads as on. No command writes it at creation. It is not a format field.
6. **`format_version` 39 is needed.** A new node shape under the manufacturing is not known to build 38, and build 38 would keep it only by accident: its repair and delete paths treat unknown children as data they may drop on save. That is the case ADR 0033 §7 refuses by a bump; the same rule bumped 37 (ADR 0042) and 38 (ADR 0045) for a new shape. Migration: none. A format 38 file has no operation nodes and opens unchanged, and nothing is written on open. The goldens are regenerated by the implementer without the removed colour register (no compatibility to keep, the format is unmerged). Goldens in `curvyo-document-core/tests/fixtures/`: `operations_v39.curvyo` (with clone member keys), `operations_unknown_kind_v39.curvyo`, and `operations_dangling_v39.curvyo` (a key whose path is not live: opens, shows nothing, saves back unchanged).
   Rejected: no bump by option C; it would avoid the number and buy the bespoke order code.
7. **Run rules, pure, in `curvyo-laser-core`** (ADR 0034 §1 and §2, no new crate, no trait):
   - **Sequence.** With Cuts last on, the run sequence is a stable partition of the stored list: the marking kinds (`score`, `engrave`, `engrave_outline`) in list order, then the cutting kinds (`cut`, `cut_out`) in list order. With it off, the list order. An unknown operation keeps its place and runs nothing. The partition is a read rule: a merge that leaves cutting above marking is shown in the run order and nothing is rewritten.
   - **Nearest rule.** For a leaf, walk its chain of keys from the leaf itself up to the output page. For a clone member the chain is its path's prefixes, longest first (the member, the groups between it and the clone, the clone), then the output page's ancestors of the clone. For an inner row it is the source object and its drawing groups, then the placement. The first key on the chain with any membership (any operation, known or unknown, Output on or off) decides the leaf's operations. A leaf inside a placed page whose source leaf is hidden on its drawing page (Frage 149 A) uses only its own key. Operations are returned in run sequence order. An unknown operation stops the rule and runs nothing, so a leaf never falls back to a parent's operation it was not assigned to.
   - **Runs.** A leaf runs with each returned operation whose Output is on and whose kind is known.
   - **Geometry per kind** (criteria 19 to 23): Cut and Score take every outline as a line, open stays open. Engrave and Engrave + Outline take a leaf as an area when it has at least one closed outline (open outlines closed by a straight line, `0054`), and as a line when all its outlines are open. Cut-out takes, per target (the node or path where the rule stopped, Frage 168 A), the outer boundary of the union of its leaves' closed outlines (geometry-core `boolean`, open leaves closed by a line), grown by `op_margin` through geometry-core `offset` with the outset join of spec `0038`. A zero margin skips the offset. Images: Cut takes the frame as a line, Score nothing, Engrave and Engrave + Outline are counted as raster (pixels by `0029`), Cut-out uses the frame. Tolerances are passed in from the caller, never hard-coded in the core.
   - **Summary.** Over the output-capable leaves (guides, dimensions and fixtures excluded, criterion 10): running leaves, not-assigned leaves, runs-while-hidden leaves, and leaves with an Output-off operation. Each leaf is in exactly one of the first three; the last may overlap the first.
8. **Reads.** `curvyo-document-core` gives, per output-page leaf, its chain of keys (node ids, and paths for clone members, nearest first) and the membership keys of the manufacturing's operations. Nothing in document-core decides a rule.

## Consequences

- Every output-page reader must keep the skip predicate of ADR 0032; operation nodes are covered by it, and a missed walk would draw an operation. The unknown-operation golden guards the round trip.
- Membership keys are published file keys: `member.`, the path form with `/`, and the five kind strings are the surface for the `0029` output. Renaming one is a format change.
- Every deletion scans the operations' keys for its nodes. Cost is one pass over the keys of the manufacturing per delete, which the budgets of `0101` do not measure; a larger file would show it.
- A deletion can drop an assignment for good if the maker does not undo: that is the Frage 169 A choice. The UI shows no warning, as the customer chose.
- Format 39 means a build of 38 refuses a file with an operation. Accepted: old-file compatibility is waived for this development build (customer, 2026-10-29).
- Counts and the run order are recomputed from the caches described in `0101` `adrs.md` (two caches: the chains change with the drawing, the membership index with the operations). A full drawing read per assignment would cost about 15 ms for 1,000 objects (spec `0050` adrs, decision 3, measured 10,000 objects in 150 ms), which the 16 ms budget of `0101` criterion 29 does not allow.
- What waits: power, speed and material per operation (`0028`), the order inside one cutting operation and the G-code (`0029`), fixture operations (`0103`), other machine kinds, and clones of clones beyond one level in the UI (the key form already allows them).
