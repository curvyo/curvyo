# ADR 0064: Laser job builder, gate and GRBL writer in `curvyo-laser-core`: one move list for the file, the preview and the estimate

**Status:** Proposed 2026-11-16 (architect). Not `needs-customer`: no new crate, no dependency, no platform, UI framework or format decision (the stored part is [ADR 0065](0065-laser-output-settings-and-air-assist.md)). Choices marked **(Proposal)** are the architect's, vetoable at the demo. Spec: [`0029`](../../specs/0029-laser-job-preview-and-output/specification.md) criteria 1 to 38, Fragen 219 to 226 answered 2026-11-16. Feature notes: [`0029` adrs.md](../../specs/0029-laser-job-preview-and-output/adrs.md). Builds on [ADR 0046](0046-laser-operations-record.md) (operations, nearest rule), [ADR 0052](0052-laser-fixture-jobs-in-the-project-file.md) and [ADR 0059](0059-fixture-sets-job-fixtures-and-pins-in-the-project-file.md) (fixture jobs), [ADR 0054](0054-laser-settings-and-test-grids-in-the-project-file.md) §2, §3 (effective numbers, refresh), [ADR 0056](0056-laser-operation-tools-in-the-project-file.md) (options, `motorised_z`), [ADR 0057](0057-test-grid-object-with-derived-operations.md) §5 (the Lasered hook), [ADR 0003](0003-geometry-kernel-booleans-offsetting-vcarving.md) (kernel). The file is the job text [ADR 0035](0035-machine-connector-protocol.md) will later stream.

## Context

`0029` turns a laser page into one GRBL file and shows, before anything is written, the run on the page (Toolpath view with a scrub slider), its length and time, and a gate that names the machine and every number. Criterion 9 asks that view and file cannot differ; criterion 31 that two exports are byte-identical; criterion 36 sets CPU budgets. What must stay cheap to change: the core/platform boundary, determinism of the file, and the single source of moves. What may change freely later: the time model, the order heuristic's speed, other dialects.

## Options

**Where the job lives**

- **A. New modules of `curvyo-laser-core`, one public module `job` (chosen).** It already owns the kinds, the run order, the settings rule, Cut-out contours, fixture parts and the profile; the job reads all of them. Pure, `#![forbid(unsafe_code)]`, wasm32 in CI already. No new crate, no new dependency (criterion 34).
- **B. A new crate `curvyo-gcode-core`.** Would depend on `curvyo-laser-core` for every input type, and there is one machine family and one dialect (`CLAUDE.md` §6: no machine abstraction before the second family). An ADR and a crate for no second user. Rejected; revisit when a plotter or CNC dialect arrives.
- **C. In the wasm session.** Core logic behind a UI crate, no golden tests without a session, breaks `CLAUDE.md` §6. Rejected.

**One source for file, view and estimate**

- **A. One move list (chosen).** The builder produces the job's moves in integer micrometres; the writer, the Toolpath view, the summary and the scrub timeline all read that list. Criterion 9 holds by construction.
- **B. A G-code text parsed back for the view.** Double work per frame and a parser in production. Rejected (the tester's parser stays test-only).

**Caching (criterion 36 d)**

- **A. Plan per operation, cached by a fingerprint of its inputs and its entry point; numbers applied in a linear pass (chosen).** Power, speed, passes and Output changes never re-plan geometry.
- **B. Rebuild the whole job per revision.** 100 ms on a 1,000-item page at every typed number. Rejected.

## Decision

1. **Modules** (`curvyo-laser-core`, `pub mod job`; each module's doc says its one responsibility; ≤ 500 lines each):
   - `job_input.rs`: the input the session passes (types only): per running block (operation or fixture job, in run order) its kind, numbers, options and the leaves that run in it by the nearest rule, each leaf as page-space outlines (`Vec<OutlineTriple>` + closed) or an image frame, with node id and stacking order; Cut-out leaves grouped by their item. Text, clones, placed pages and transforms are resolved to page space by the session (it already does so for the Operations look and Cut-out); the core never shapes text.
   - `job_numbers.rs`: the numbers each block writes (decision 3).
   - `job_order.rs`: inner first, then nearest (decision 5).
   - `job_hatch.rs`: the scan lines of one Engrave area (decision 6).
   - `job_plan.rs`: the ordered burn paths of one operation, by kind (`kind_run`, `cut_out_contours`, hatch, order).
   - `job_moves.rs`: the job's moves (passes, travels, run-out, Z, start, end, machine frame).
   - `job_timeline.rs`: lengths, the time estimate and the head position at a time.
   - `job_gate.rs`: the gate (decision 8).
   - `job_effects.rs`: what a successful export changes in the project (decision 11).
   - `job_fingerprint.rs`: the plan cache key, FNV-1a 64 over the inputs' bits, written out (no dependency).
   - `gcode_grbl.rs`: the GRBL text of a move list.
   - `output_settings.rs`: reads the page's output registers of ADR 0065.
   `curvyo-geometry-core` gains two public functions: `flatten_outline(anchors, closed, Tolerance)` (the existing bit-identical `flatten`, now exported) and `direction_of_degrees(f64) -> Vec2` (`libm` sin and cos, the crate's existing dependency). No `-io` crate changes: the app writes the text through the save dialog of the SVG export (`0024` criterion 4).
2. **Units and determinism.** Curves are flattened at **0.0095 mm**, then every point is rounded to whole micrometres (`i64`); the 0.0005 mm rounding keeps the total deviation within criterion 17's 0.01 mm. Everything after rounding is integer except hatch intersections (f64 `+ - * /`, rounded to µm at once). Comparisons of distance are on squared `i64`; ties break by stacking order, then outline index, then node index. No `HashMap` iteration reaches output; scan directions come from `libm`. Text: coordinates printed from µm as `<int>.<3 digits>` (never `-0.000`), S and F whole numbers, LF line ends, ASCII only (other characters in names become `_`, comment lines cut at 80 characters, Proposal). No clock, path, user, version or random value enters the file (criterion 24).
3. **Effective numbers.** An operation's numbers are `resolve(read, kind, materials, profile_id).run()` of ADR 0054 §2 with the same loaded library the operation rows use, so gate and row agree (criterion 3). `NoSettings` blocks (4 a); `Damaged`, an Unknown kind or damaged `op_options` run nothing and warn once (criterion 33). The written feed is `min(speed, max_feed)` (`RunSettings::over_feed` warns); S = `(power_tenths × s_max + 500) / 1000` in integers; Engrave + Outline writes the hatch with `main` and the outlines with `outline`, each with its own passes (Proposal: hatch passes, then outline passes). **Fixture jobs** run with the page's pick (ADR 0065 §1): the picked material's set of the job's kind for the page's profile id (power, speed, passes, interval); no pick, a material not loaded here, or no set for that laser and kind blocks (4 a, Frage 221 B; Proposal for "not loaded": block rather than guess). Fixture jobs have no `op_options`: defaults (bidirectional, 0 degrees, no crosshatch, no overscan, no Z).
4. **What a kind writes** (criteria 13 to 19): as the spec states; images in Engrave are dropped before planning (Frage 226 A), images in Cut and Score give their frame as a closed path. The fill rule is the document's one rule, nonzero over all outlines of the leaf; open outlines of a leaf with a closed one are closed by a line for hatching.
5. **Order inside one operation** (criterion 22, Frage 225 A). A path P must run before every closed path that contains it (closed in closed: `outline_nesting`; an open path is inside when all its nodes are inside, `contains_point_in_outlines`). Among the paths whose contained paths have all run, the next is the one with the start nearest to the head (closed: any node, kept in drawn direction; open: either end, reversed when its end is nearer). Hatch blocks of Engrave leaves take part in the nearest choice only (four entries: first or last line, either end; no nesting rule, Proposal: it protects cuts, not fills). The head starts at the machine origin's page point for the first block and at the previous block's exit for the next, so an operation's plan depends on its own inputs and its entry point only. The result is defined by the brute-force rule; a spatial index is allowed only if it gives the identical order (tested against brute force on random fixtures).
6. **Hatch** (criteria 14, 15). Lines in the frame turned by the Scan angle, Interval apart, the first half an Interval inside the area's box; each line cut against the leaf's polylines, spans by nonzero winding; bidirectional alternates direction per line, else each line runs the same way with a laser-off travel back; Crosshatch hatches the leaf again at +90 degrees right after (same block and pass). **Overscan run-out:** `overscan % × v² / (2 × 1,000 mm/s²)` with `v = feed / 60`, written as laser-off `G1 … S0` at the burn feed before and after each span (Proposal: 1,000 mm/s² because the profile has no acceleration). In Machine origin mode the run-out is clamped to the work area.
7. **Moves.** `Move { to: (i64, i64) µm, kind: Burn { role } | Travel | RunOut | Z(µm), block }` in page µm; the machine frame is applied by the writer from the origin corner (BL: `(x, H − y)`, TL: `(x, y)`, BR: `(W − x, H − y)`, TR: `(W − x, y)`, W and H the page size in µm; page Y grows down). Passes repeat the operation's path list in the same order (Frage 223 A). Z offset: laser-off `G1 Z<offset> F<feed>` before the first pass and `G1 Z0` after the last (relative deltas in G91), only with `motorised_z`. **Start** (criterion 38, ADR 0065 §2): Machine origin starts with a travel from (0, 0) and ends with `G0 X0 Y0`; Head position writes `G91`, places the head at the first burn start (no first travel), every move as the exact µm difference of rounded points, and the end as the negated sum, so nothing drifts; Home first writes `$H` and forces Machine origin. The plan never depends on the start mode, so both switches off writes exactly the criterion 26 file.
8. **Gate type** (`job_gate.rs`): `Gate { machine: MachineLine, mode: ModeLine, fixture: Vec<FixtureLine>, operations: Vec<OperationLine>, issues: Vec<Issue> }`; `Issue { cause: Cause, count: usize, targets: Targets }` with `Targets::Items(Vec<NodeId>) | Operation(NodeId)`; `Cause` is one enum whose variant order is the display order of criteria 4 and 5 (blocks first), then damaged settings (33) and the head-position warn (38) last; `Cause::severity()` and `Cause::text(count)` in core; `Gate::export_allowed()` and `first_block()` give the button and its tooltip. Operation lines carry the `SettingsState` source words (live, stored, typed per field). The bed check (4 b) is on the burn moves' box with 10 µm tolerance, counted per leaf; off in Head position mode.
9. **Cache, laziness and budgets** (criteria 12, 36; thread CPU time in `curvyo-editor-wasm/tests/cpu_time/`, which already has the clock; no dev-dependency in `curvyo-laser-core`). The session builds the job only while the Toolpath view is pressed or the Output tab is shown, at most once per frame, keyed by its `Arc<DocumentRead>`, the library generation and the page (as `LeafCache`); each operation's plan is reused while its fingerprint and entry point are equal. Confirmed limits: (a) 1,000 Cut items of 20 nodes plan in 100 ms; (b) 200 x 200 mm Engrave at 0.1 mm in 150 ms; (c) with Crosshatch 300 ms; (d) gate and summary after an edit that keeps every plan valid (numbers, material, Output, the page switches) in 16 ms on 50 operations and 1,000 items; an edit of geometry re-plans the touched operation and the later ones whose entry moved, inside (a); (e) the Output tab with a cached job in 100 ms; (f) a slider move on 1,000 Cut items redraws in 16 ms; pan and zoom with the view pressed in 16 ms.
10. **Preview path.** The session keeps, per job, a document-space draw cache of the moves (polyline runs per kind, the numbered ring per block, arrowhead per burn path) plus the timeline's cumulative length and time per move. A new render-core module `toolpath_look.rs` ("draws a cached toolpath up to a head position") emits the frame's draw list from that cache and the view transform; sub-pixel runs may merge in the draw only, never in the job. The slider position is a **fraction of the estimated time** (Proposal: Play is then the run in time, 10 s whole); the head is found by binary search over cumulative time and the move it falls in is split, so a slider move never rebuilds the job (36 f). Play's ticking is the frontend's `requestAnimationFrame`; the core gets positions only. Toggle and position are session state.
11. **Export and undo** (criteria 27 to 30). `export_gcode` returns the text, the default name and a token for the exported job; the frontend saves it. Only on a successful write does `export_gcode_done(token, now_ms)` run: (1) one history step `export_gcode` "Export G-code" switching off every fixture job of the job (pins' Centre mark and Diameters jobs included) and writing `refresh(.., guard: false)` of every linked operation in the job; (2) a second commit with the reserved label `mark_test_grid_lasered` (made a reserved non-step label, like `refresh_material_numbers`; the hidden test hook of ADR 0057 §5 writes the same commit) setting `test_grid_lasered = now_ms` on every grid with at least one derived operation that wrote a move; (3) the matching test records' `lasered` in the material library, written without a journal entry. Undo takes back (1) only; Lasered stays (spec Proposal). The ids come from the token's job, so an edit during the dialog changes nothing of what is recorded; a gone id is skipped. Cancel or a write failure calls nothing. A record write failure shows the library's write notice; the document part stands.

## Consequences

- One move list is the contract between the writer, the view, the summary and later `0064`'s streaming; a new dialect is a second writer over the same list.
- `curvyo-laser-core` grows by about 12 modules; it stays the laser family's single core crate. `curvyo-geometry-core` gains two public functions (architect review at build).
- The time estimate ignores acceleration and homing; "About" says so. An acceleration field later changes `job_timeline.rs` and the run-out constant only.
- Goldens of criterion 31 live in `curvyo-laser-core/tests/fixtures/gcode/`, built from `job_input` fixtures with no session.
- The reserved label list gains `mark_test_grid_lasered`; `curvyo-ui-core/src/history_names.rs` gains "Export G-code" and drops "Mark lasered".
