# ADR 0094: Native pen input on Linux: `curvyo-app` reads GDK events of the webview widget and sends per-frame sample batches over a Tauri channel

**Status:** Proposed 2026-11-27 (architect). The route itself is the customer's Frage 408 A (2026-11-26: the app reads the pen natively; slice 0 measures it); the choices below lie inside that answer, so this ADR is not `needs-customer`. It becomes Accepted when the slice-0 probe has met decision 8's checks on the Kamvas 13 under X11 and under Wayland. No new crate, no new dependency, no `unsafe`, no document `format_version` change. Spec: [`0158`](../../specs/0158-pen-display/specification.md) slice 0 (criteria 1 to 5) and slice 1. Builds on [ADR 0001](0001-ui-framework-and-canvas-rendering.md) (Tauri 2, WebKitGTK on Linux, the frontend forwards input) and [ADR 0011](0011-workspace-and-crate-layout.md) (app is glue, `*-core` stays pure).

**In plain words (for the customer).** On Linux the webview drops pen pressure (WebKit bug 268458), but the window toolkit underneath it (GTK) still sees it. Curvyo listens to the same input events GTK hands to the webview, picks out the pen ones, and sends their position, pressure, tilt and buttons to the page once per screen frame. The webview keeps getting every event as before. This works the same under X11 and Wayland because GTK does the device work in both. Windows and macOS keep using the browser's own pen events, which carry pressure; the drawing code sees one kind of sample either way.

## Context

Verified on this branch (2026-11-27) against `Cargo.lock` and the crate sources: `tauri` 2.12.7, `wry` 0.57.0, `tao` 0.37.1, `webkit2gtk` 2.0.2 (WebKitGTK 4.1 API, system 2.54.2), `gtk`/`gdk` 0.18.2 (GTK 3, system 3.24.52). `curvyo-app` already depends on `gtk = "0.18"` on Linux (import dialog) and already attaches GDK signal handlers to the webview through `WebviewWindow::with_webview` → `PlatformWebview::inner()` (a `webkit2gtk::WebView`, a `gtk::Widget`) in `native_file_lists::watch_drags`, returning "proceed" so WebKitGTK still handles each drag. The wasm pointer API (`curvyo-editor-wasm::wasm_api::pointer_down/hover/up`) takes canvas-relative CSS px and modifiers, no pressure; nothing in the workspace reads pressure. `tao` has no pen pressure on Linux (only macOS `TouchpadPressure`). The workspace sets `unsafe_code = "deny"`.

A spike crate in the scratchpad (not merged) compiled against `gtk =0.18.2`, default features, `#![forbid(unsafe_code)]`, offline: `connect_event` on a `gtk::Widget` returning `glib::Propagation::Proceed`; `Event::source_device().source()` (`InputSource::Pen`/`Eraser`), `Event::device_tool().tool_type()`, `Event::axis(AxisUse::Pressure | Xtilt | Ytilt)`, `coords`, `time`, `state`, `button`; `add_events(PROXIMITY_IN_MASK | PROXIMITY_OUT_MASK)`; `gdk::Window::set_event_compression(false)` after realize; `add_tick_callback` with `FrameClock`. All safe API. `GestureStylus` exists in `gtk` 0.18 only behind its `v3_24` feature, which nothing in the tree enables.

## Options

**How the app reads the pen**

| Option | Why it won or lost |
|---|---|
| **A. A GDK `event` handler on the WebKitWebView widget (chosen)** | GDK 3 reads XInput2 on X11 and `zwp_tablet_v2` on Wayland and gives one event shape with normalised axes; positions are already window-local; same pattern as `native_file_lists`; no new dependency, no `unsafe`, no device permissions. |
| B. `gtk::GestureStylus` on the webview | Same GDK data underneath; needs the `v3_24` feature on `gtk`; a gesture has claim state that can take an event sequence away from WebKit's own handling; nothing gained over A. |
| C. libinput/evdev directly (`input` crate) in a new `-io` crate | Needs read access to `/dev/input/event*` (`input` group or a udev rule); reports tablet coordinates, which on Wayland cannot be mapped to the window (no global window position); a new crate, a new dependency with FFI, and it also bypasses the user's driver mapping (Huion driver, OpenTabletDriver). |
| D. XInput2 and the Wayland tablet protocol directly | Two implementations of what GDK already does; `x11-dl` and Wayland FFI need `unsafe`; on Wayland the tablet objects belong to GDK's own connection and seat. |

**How samples reach the page**

| Option | Why it won or lost |
|---|---|
| **A. A `tauri::ipc::Channel` the page passes to a `pen_watch` command, one message per frame (chosen)** | Ordered (per-message index), addressed to the calling webview only; a frame batch (a few hundred bytes of JSON) stays under Tauri's 8 KiB direct-eval threshold, so no fetch round trip. |
| B. A Tauri event (`emit`) | Goes to every listener of every webview (the pen window of slice 2 would need filtering); no ordering promise across messages. |
| C. One message per GDK event | 200 or more `eval`s per second into the web process while drawing; the canvas only uses samples once per frame anyway. |

**What the frontend uses while native samples exist**

| Option | Why it won or lost |
|---|---|
| **A. DOM Pointer Events route the gesture (target element, start, end, modifiers, cursor); native samples are the only source of position, pressure and tilt inside a canvas gesture (chosen)** | Panels, buttons and overlays keep working with the pen as a mouse; the canvas reads one stream for geometry, so no per-sample matching. |
| B. Native samples are the only source for everything | The page would have to redo DOM hit-testing, focus and capture from coordinates. |
| C. Pair each Pointer Event with the nearest native sample and copy its pressure | Matching two streams with different rates and clocks; WebKit delivers fewer moves than the pen reports, so many native samples have no partner. |

## Decision

1. **Reader.** `curvyo-app/src/pen_input.rs` (`#[cfg(target_os = "linux")]`, one responsibility: turning the webview's GDK pen events into sample batches). In `setup`, as `watch_drags` does, `with_webview` on each webview window connects one `event` handler that always returns `Propagation::Proceed`, so WebKitGTK sees every event unchanged. It keeps motion, button press/release and proximity in/out events whose source device is `Pen` or `Eraser`, or whose event has a pressure axis (GDK 3 on X11 guesses the source from the device name, so a virtual driver device may read as `Mouse`); all others are ignored. No `unsafe`, no new dependency.
2. **Event compression.** GDK 3 merges queued motion events to one per frame by default, which drops pen samples. After realize the reader turns compression off on the webview's `gdk::Window`. This also gives WebKitGTK every motion event; slice 0 measures the cost (decision 8). If the cost is too high, compression stays on and the reader keeps what GDK gives; this is the one switch decision 8 settles.
3. **Sample.** A new `curvyo-ui-core::pen_sample` module (one responsibility: the input record of a pen or pointer) holds `PenSample` (`Serialize`, `Deserialize`, flat fields): `x`, `y` as `ScreenPx` (made public; CSS px relative to the webview's viewport, the space of `PointerEvent.clientX/Y`; the reader translates from the event's `GdkWindow` to the webview widget; GTK logical px equal CSS px because Curvyo never sets a WebKit page zoom); `pressure: Pressure` (newtype, 0 to 1, clamped on construction; GDK 3 already maps the device's axis range to 0 to 1 on both backends; absent axis gives `None`); `tilt: Option<Tilt>` (x, y each -1 to 1 as fractions of 90 degrees, GDK's normalised value; Pointer Events' degrees divided by 90); `tool: PenTool::{Tip, Eraser}` (from the device source or the `DeviceTool` type); `phase: Hover | Contact | Out` (Contact from the button-1 press to its release, read from the event type and then `BUTTON1_MASK` in the state; Out on proximity out); `barrel: u8` (bit 0 = button 2, bit 1 = button 3, from the modifier state); `time_ms: f64` on the source's own clock (GDK event time in ms, unwrapped past `u32` wrap since `pen_watch`; on other platforms `PointerEvent.timeStamp`), only differences within a stroke are meaningful. The pressure curve and width mapping of slice 1 live beside it in `curvyo-ui-core` (the old branch's `pencil_pressure.rs` is the starting point); the reader never shapes values.
4. **Batch and send.** Samples collect in a per-webview buffer on the GTK main thread. The first sample of a burst adds a tick callback on the webview widget; each frame-clock tick sends the buffer as one `PenBatch { samples }` over the channel and empties it; an empty tick removes the callback (no idle wakeups). Commands: `pen_watch(channel) -> bool` (true on Linux, the reader feeds this webview's channel; false elsewhere, so the page uses Pointer Events) and `pen_unwatch()`. A batch never holds more than 256 samples (the oldest are dropped and counted, for the probe).
5. **Frontend.** One adapter `frontend/src/platform/penSamples.ts` gives the canvas `PenSample` batches from either source: the channel when `pen_watch` answered true, otherwise each Pointer Event of type `pen` with its `getCoalescedEvents()`. The canvas gesture starts and ends on DOM Pointer Events as today; between them it consumes only native samples when the route is native (options table 3, A); on `pointerup` it takes the samples of the next batch up to the first non-Contact sample, waiting at most one frame. A mouse or a pen while no native sample has arrived in this gesture keeps today's Pointer Event path unchanged.
6. **Platforms.** Windows (WebView2) and macOS (WKWebView) expose pressure and tilt in Pointer Events; they get no native reader (`pen_watch` answers false). The browser build has no host and uses the same Pointer Event adapter. No `cfg` in core crates; every `*-core` crate stays wasm32-buildable.
7. **Privacy.** Samples stay in memory between the GTK handler and the page; nothing about the device is stored, logged or sent (spec slice 0 criterion 4). The device name is shown only on the probe page, never persisted.
8. **Slice 0 measures, on the Kamvas 13 under X11 and under Wayland, with the customer's driver:** (a) pressure arrives natively in 0 to 1 and changes with force, while the webview's own `PointerEvent.pressure` stays 0 or 0.5 (shows bug 268458 is what we work around); (b) tilt and its range at full lean, eraser end as `Eraser`, barrel buttons as bits, proximity in and out; (c) samples per second during a fast stroke with compression on and off, target at least 120 (two per 60 Hz frame) **(Proposal)**; (d) delay: the probe stamps each native batch and each Pointer Event with `performance.now()` on arrival and shows the median and 95th percentile of native minus webview for the same motion, target median at most one frame later **(Proposal)**; also the event age in the app (`glib::monotonic_time()` against the GDK time, both CLOCK_MONOTONIC ms on Xorg and on common compositors, to be confirmed); (e) native `x, y` equal `clientX, clientY` within 1 px on the main screen and the Kamvas; (f) WebKit's frame time with compression off stays within budget; (g) whether GDK reports the pen as `Pen` under the chosen driver.
9. **Fallback (named, not designed).** If (c) or (f) fails: keep compression on and accept GDK's rate, or flush per event. If a session delivers no pressure through GDK (most likely a compositor without the tablet protocol, or a driver exposing a plain mouse): a libinput reader in a new `-io` crate (option C), its own ADR with the permission question. If the native route fails on both sessions: Frage 408 C (change the shell's webview) returns to the customer.

## Consequences

- Slice 1: the wasm pointer API gains a batch entry point taking `PenSample`s (pressure, tilt, tool, phase, time) for the active canvas gesture, beside today's `pointer_down/hover/up`, which stay for routing and the mouse; the Freehand Pencil fits all samples of a frame, not one per Pointer Event. The pressure curve and Min/Max width are pure functions in `curvyo-ui-core` on `Pressure`, tested without a device.
- Slice 2's pen window gets the reader for free: decision 1 attaches to every webview window and each window's page has its own channel.
- Turning event compression off (decision 2) is the one change WebKitGTK notices; it is per webview window and reversible in one line.
- GDK 3's source guess by device name and the compositor's tablet protocol support are outside our control; the probe page is the diagnosis tool for a maker whose pen shows no pressure.
- If Tauri moves Linux to GTK 4 (`gtk4-rs`), the reader is rewritten on `GtkEventControllerLegacy` or `GestureStylus`; the sample type and the frontend stay.
