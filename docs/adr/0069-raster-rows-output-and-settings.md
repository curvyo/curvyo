**Amended 2026-11-19 (architect, customer feedback on PR #394): decision 13.** Raster runs in operations of a new sixth kind **Image** (`op_kind` `image`); Engrave and Engrave + Outline return to vector hatch only. Decisions 2, 6, 7, 8 and 10 carry dated notes; the rows, output, preview, ticks and budgets are unchanged. Still project format 50 and material record format 3 (both unreleased, no migration).

**Amended again 2026-11-19 (customer answers Frage 270 B and 271 A with a clarification): decisions 13 and 14.** A material gets a fourth set, **Image**, per laser (decision 14, in material record format 3 in place); in every kind but Image a picture is strictly its frame rectangle, so Score scores it, Engrave hatches it and Engrave + Outline hatches and traces it (decision 13, "What each kind runs").

**In plain words (for the customer).** The job holds each raster row as a start, a direction and the burn strength of each dot, not one move per dot. The G-code writer, the Toolpath view and the time estimate all read the same rows. Pictures and gradients are engraved by their own operation kind, Image, with the material's own Image numbers; the image settings are seven more values of that operation; the Image test grid remembers its Dither and its best cell fills the Image numbers. In every other kind a picture is just its rectangle. Nothing about dots is saved in the project.

## Context

ADR 0064's move list is one `Move { to, kind, block }` per straight segment. A raster item at 0.1 mm over 200 x 200 mm has 2,000 rows and up to 2 million runs; one move per run is affordable, one per dot is not, and the 50 million dot limit (ADR 0068 §7) must fit wasm memory. Criterion 14 asks for rows of runs that every writer and the preview read through one function.

## Options

| Option | Why it won or lost |
|---|---|
| A. Each run as ordinary `Burn` moves with a power field | Simple for writers, but a worst-case dither at the 50 million limit is 25 million moves of about 40 bytes (1 GB). Lost on memory. |
| **B. A `Sweep` move per burned stretch of a row, pointing into the job's sweep table, which holds one level per dot (chosen)** | Memory is one bit per dot (one byte in Grey); writers, timeline and preview iterate runs from one function; the rest of the move list (travel, run-out, Z, passes, frame) is unchanged. |
| C. A separate raster stream beside the move list | Two orders to merge in every reader (timeline, slider, writer). Lost. |

## Decision

1. **Sweeps** (`job_raster_rows.rs`, "the sweeps of one raster item"). After ADR 0068 the levels of each row are cut into **sweeps**: from the first burned dot to the last, split where an unburned gap is longer than **5 mm** (confirmed), with leading and trailing unburned dots and empty rows dropped. `Job` gains `sweeps: Vec<Sweep>`; `MoveKind` gains `Sweep { role, node, sweep: u32 }` whose `to` is the sweep's end edge. `Sweep { start: PointUm (the first dot's leading edge), direction (unit, from the scan frame, in run order), interval_um, levels: Levels }` with `Levels::Binary(bits) | Grey(Vec<u8>)` stored **in run order** (a reversed row stores its levels reversed). One function `Sweep::runs()` yields `Run { from, to, level }` with the endpoints rounded to µm from `start + i·I·direction`; a run's burned length is `dots × I`, so criterion 40's length check holds within rounding. **Power** of a run (Grey): `lowest + (set − lowest)·level / 255` in tenths of a percent, rounded half up, with `lowest` capped at the set's power (Proposal); binary levels burn at the set's power. One function, `run_power`, used by every writer and the preview. *As built (2026-11-19):* `Sweep { start, end, levels }`: `start` is the first dot's leading edge and `end` the last dot's trailing edge, both in µm; the direction and the dot pitch follow from them and the dot count (`Sweep::point(i)`), so no direction or interval is stored per sweep. A picture of the dots takes its frame from the item's longest sweep, turned to run as the first, so the µm rounding of a short sweep never tilts it.
2. **Order and moves** (criteria 14 to 17). In a block's main role the vector hatch and lines run first in ADR 0064 §5 order, then the raster items in stacking order, bottom first, each from its first row on; then the outline role (Engrave + Outline: the image's frame or the gradient shape's outline with the Score set). This is "the dots first, then the outline" of criterion 2; criterion 14's "rows after the vector paths" is read as "after the vector hatch, before the outlines" (criterion 14 says so). Between sweeps the head travels to the next sweep's start at the maximum feed; for bidirectional rows of equal extent this is the one-Interval step of criterion 15, otherwise the straight line between the two ends. Bidirectional alternates the run direction per row; off, every row runs in the base direction. Overscanning adds the ADR 0064 §6 run-out before and after each sweep as `RunOut` moves. Crosshatch is ignored for raster items. Passes repeat the block's moves with the same sweeps (no new dither). *Amended 2026-11-19 (§13):* raster items exist only in an Image block, which holds nothing else: its raster items in stacking order, bottom first, and no outline role. An Engrave + Outline block is vector hatch then outlines again; an image there is its frame rectangle, hatched with the vectors and traced with the outlines (§13, Frage 271).
3. **GRBL** (criterion 19, `job_write_grbl.rs`). M4: one `G1` to each run's end with `S` from `run_power` by the ADR 0064 §3 formula, `S0` over unburned stretches inside the sweep, consecutive runs of the same `S` merged into one `G1`, `F` only where it changes. M3: per run `M3 S<n>`, `G1`, `M5`, and the unburned stretches as `G0`. Grey on M3 never reaches the writer (decision 6). The line count is runs plus sweeps plus travel; never one line per dot. `0029`'s `image_skipped.gcode` is replaced by `raster_threshold.gcode`; the other goldens of criterion 40 are added in `tests/fixtures/output/grbl/`.
4. **Time and slider** (criteria 21, 22). The timeline counts a `Sweep` as one burn move of its length at the burn feed (the head sweeps its short gaps at that feed), travel and run-out as today; "Burn" sums sweeps, "travel" the travel moves. The slider's binary search is unchanged; a head inside a sweep is interpolated along it and the drawn part ends at the head.
5. **Preview** (criterion 20; ADR 0064 §10). The job's draw cache gets, per raster item, its runs as polylines in the Engrave look and one **coverage pyramid** (burned dot counts per 4 x 4, 16 x 16, … dots, `u8` fractions, about 1/15 of the dot count in bytes), built once per job. `toolpath_look.rs` draws the runs while rows are at least one device pixel apart, else the pyramid level whose cell is at least one device pixel as quads whose alpha is the coverage (render-core stays pixel-free; pan and zoom never iterate dots, 37 e). One arrowhead per item at its first sweep. **While an Image setting is edited**, the Operations view draws the item from a preview grid of `k·I` with `k` the smallest whole number for which `k·I` is at least one device pixel, built by the same ADR 0068 functions and drawn as coverage quads, ready in 50 ms (37 d); the full grid (times, checks, Toolpath view, Export) is built in the next frame (ADR 0064 §9's one build per frame), within 37 c. *As built (2026-11-19):* each item's dots are one picture (`raster_picture.rs`, one texel per dot, blocks of `2^n` dots past 4,096 texels) drawn through the image pipeline. The Operations view's preview grid of `k·I` is capped at 300,000 dots per operation (`k` doubles until it fits) so an edit's frame stays within 50 ms at any zoom, and its plan cache shares the job's grey pyramids (one per asset, `PlanCache::sharing_pyramids`).
6. **Checks** (criteria 31 to 36; ADR 0064 §8). New `Cause` variants after `0029`'s, in this order: `GreyNeedsM4` (block, per operation), `TooManyDots { item, count }` (block), `CoarseImages` (warn: page pixel size above `2·I`), `OverlappingRasterItems` (warn: two frames of one operation overlap with area above 0; images by their parallelograms, gradient shapes by their outline boxes, Proposal), `ReducedImages` (warn: `is_reduced`), `UnreadableImages` (warn, skipped), `LowestPowerAbovePower` (warn: Grey with Lowest power above the set's Power; every burned dot then runs at the Power, criterion 32 b). Raster items count in `OutsideBed` by their frame. **No "has no interval" cause**: by ADR 0056 §5 an Engrave always has an Interval (absent reads 0.10, anything else is Damaged settings), so the block cannot occur and criterion 32 no longer has it. Texts in `job_gate_text.rs`. *Amended 2026-11-19 (§13):* every raster cause is raised for Image blocks only (`GreyNeedsM4`, `OverlappingRasterItems` and `LowestPowerAbovePower` per Image operation); an Engrave never raises one, since it holds no raster item.
7. **`op_options` keys** (criterion 13; amends ADR 0056 §6), allowed on `image` only (amended 2026-11-19, §13; first built on the Engrave kinds), each optional with its default:
   ```text
   dither: "threshold" | "ordered" | "floyd_steinberg" | "jarvis" | "atkinson" | "stucki" | "grey"   = "floyd_steinberg"
   threshold_pct: integer 0..100 = 50     brightness_pct: integer -100..100 = 0
   contrast_pct: integer -100..100 = 0    gamma: 0.10..4.00, two decimals = 1.00
   invert: bool = false                   lowest_power_pct: 0.0..100.0, one decimal = 0.0
   ```
   Names carry the unit suffix of ADR 0056 (`overscan_pct`, `scan_angle_deg`): `threshold_pct`, `brightness_pct`, `contrast_pct`, `lowest_power_pct` as criterion 13 now says (Proposal). Damage is ADR 0056 §6's (unknown value, out of range, too many decimals, on another kind, so any of the seven on an Engrave is now damage); material commands never touch them.
8. **Test grid** (criteria 44, 45; amends ADR 0057 §1 and ADR 0058 §2). The one recipe type (`test_recipe.rs`, `test_recipe_json.rs`) gains `fill: "solid" | "gradient"` (absent = solid) and `dither` (only with `gradient`; the six binary modes, `grey` or a value without `gradient` is damage). With Gradient every cell is a rectangle with the ADR 0066 Gradient fill (linear (0, 0.5) to (1, 0.5), `#000000FF` to `#FFFFFFFF`) and each derived cell operation carries `op_options.dither` and Crosshatch. Neither is an axis. **The recipe is also the material test record's recipe**, so the record format goes to **3** (format 2 records read as Solid; Recreate from Materials then brings Fill and Dither back) unless the customer answers Frage 237 with B. *Note (2026-11-19):* the remembered grid choice `test-grid-choice.json` (ADR 0058 §9) keeps its format 2 while its recipe gains `fill` and `dither`: a build before `0123` reads such a file as damaged and starts with an empty choice (a preference, nothing else is lost); Curvyo is not deployed, so no bump. *Amended 2026-11-19 (§13):* `fill` and `dither` move to the Image grid; see decision 13 (test grid). The record is format 3 whatever Frage 237's answer, since format 3 also holds the Image set (decision 14); 237 B would only keep `kind: "image"` and `dither` out of the stored test. *Closed 2026-11-19 (architect review A6): Frage 237 is built A; with format 3 needed anyway its premise (a format change for the recipe alone) is gone.*
9. **Nothing stored, caches** (criteria 38, 39). Plans stay per operation (ADR 0064 §9); the fingerprint gains the asset hash, the frame in µm, the `PlacedGradient` bits and the Image settings. The grey pyramid is per asset (ADR 0068 §3). Saving twice with an engraved image gives byte-identical files; two exports give identical bytes.
10. **Format** (criterion 41). Project `format_version`: the **next free number at merge** after `0124`'s: a build of the previous format reads the new `op_options` keys as damage (ADR 0056 §6) and the new recipe keys as a damaged recipe, and would hatch gradient shapes and drop images, so it must refuse the file (ADR 0033 §7). **Migration: none.** Goldens `raster_engraving_v<N>.curvyo` and `raster_engraving_damaged_v<N>.curvyo` (a `dither` of `"halftone"`, `gamma` 4.01, `dither` on a Cut) in `curvyo-document-core/tests/fixtures/`; material record goldens `format3_gradient_test.json` and `format2_reads_solid.json`. *Amended 2026-11-19 (§13):* the goldens are regenerated for the Image kind: `raster_engraving_v50.curvyo` holds its raster items in `image` operations carrying the seven keys and an Image test grid; `raster_engraving_damaged_v50.curvyo` adds `dither` on an Engrave and `crosshatch` on an Image; `format3_gradient_test.json` becomes `format3_image_test.json`; `format2_reads_solid.json` stays (a format-2 record holds no Image test). The material record goldens of decision 14 are added; the project golden's Image operation is linked to a material (its `op_settings` hold the Image set's numbers and interval).
11. **Budgets** (criterion 37 b, c, e, f; thread CPU, native) **confirmed**: GRBL writer 250 ms for 2 million runs; a job with that item and 50 Cut items within (a) of ADR 0068 §8 plus ADR 0064 §9 (a); pan and zoom 16 ms; checks 16 ms after an edit that keeps every plan.
12. **The edit frame and the job in ticks** (criteria 12, 37 d; added 2026-11-19). The sweeps of one raster item are kept per item and key (its rings, its geometry and the dot settings) beside the plans, and are built by a resumable row loop (`job_raster_work.rs`): `prepare_job(input, materials, cache, dots)` works up to about `dots` dots in run order and says whether every sweep the job needs is held, after which `build_job` builds no dot; building in steps gives the same job, bit for bit, as building at once (the same loop, rows never split). In the session the Operations tab, the output group and the Fixture jobs section read the *settled* job: the current one when it is built or its missing sweeps fit 300,000 dots (worked on the first read after the change), else the last job of the same page marked stale (row times "…", total "About …" and "Burn … · travel …", `0123` UX notes P35). The host calls `advance_job` once per animation frame while `job_pending` holds (300,000 dots, about 10 ms native) and reads the views again when it returns `true`. The Toolpath view, Play and Export always build the finished job at once. A job's first build on a page (no last job) is built at once as before. *As built (2026-11-19, review):* starting an item's work costs 1,000 dots of a tick's budget (many small items keep their ticks); a tick that reads a new pending input works only that share, and the job is built in a tick of its own after the last share; with the Toolpath view pressed the views read the full job; the stale words show only after the host's 300 ms mark (`show_stale_words`, UX notes P35), until then the last numbers stay. *Amended 2026-11-19 (architect review A9):* the first read after a change works a smaller share, 100,000 dots (`FIRST_READ_DOTS`), while each tick keeps 300,000, so the edit's own frame (which also reads the page and draws the preview) keeps its budget; a job of at most 100,000 missing dots is still ready at once. Measured in release, single-threaded, five runs of `raster_session_budget` (g), the 1,000-image edit frame: 33.5, 37.5, 34.2, 37.0 and 34.4 ms (median 34.4 ms; 40.1 ms with the 300,000 share; budget 50 ms, target 35 ms).

Button order and glyph are the UX notes' (default: after Engrave + Outline). A build of this branch before the kind reads `image` as Unknown (runs nothing); unreleased, so format 50 stays.

Supersedes the first amendment's "Engrave: an image runs nothing" and "Score (nothing)".
   - **Settings.** An Image operation reads the material's **Image set** (Speed, Power, Passes, Interval) through `operation_settings_rule.rs` (Frage 270 B; decision 14); `main.interval_mm` is allowed on `image` with ADR 0056 §5's rule (absent reads 0.10). No `outline` part.

## Consequences

- Every reader of `Move` handles `Sweep`; the compiler lists them (`match` without wildcard). A second output format implements `Sweep` in its writer as part of ADR 0064 §12.
- A raster job can still be slow to build at the dot limit (ADR 0068, Consequences); the preview grid keeps editing responsive, and §12 keeps the edit frame of the Operations tab within 50 ms while the job finishes in ticks.
- Published keys: the kind text `image`, the seven `op_options` keys and their values, the recipe's kind `image` and `dither`. Renaming one is a format change.
- Rejected for the Image kind (2026-11-19): raster inside Engrave with a per-operation switch (two behaviours behind one button, the customer asked for a kind); Image reading the Engrave set (Frage 270 A: pictures are often run faster or weaker than vector fills, so one Speed and Power per material did not serve; the customer chose B); an Image set falling back to the Engrave set when missing (two sources for one number, and the line would hide which ran; the kind's own set or the stored numbers, as every kind); a fourth record format for the set (format 3 is unreleased, so it is added in place); skipping images in the vector kinds (Frage 271 B, and the first amendment's "Engrave and Score run nothing": a frame rectangle is one rule for every vector kind and reuses the hatch and outline code).
- Published keys added by decision 14: the set key `image` and the kind text `image` in history entries and recipes of material record format 3.
- **Future, not built** (customer, 2026-11-19): Cut-out (and Cut) following the visible contour of an image with a transparent background instead of its frame.
