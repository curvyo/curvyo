# ADR 0065: Laser output settings in the project file and Air assist and output format in the machine profile: two page registers, `mfg_profile.air_assist` and `.output_format`, format 48, profile record format 6

**Status:** Proposed 2026-11-16 (architect), amended 2026-11-16 after the customer's review of PR #370 (`output_format`), amended 2026-11-17 after the customer's try of PR #371 (one Start pick: the registers `start_from` and `home_first` become one register `x.curvyo.laser.start`; `ux-notes.md` M14; §1, §2, §4, §6 and Consequences), `needs-customer` (document model and file format; persistence: machine profile record). Accepted with the customer's merge of the `0029` story PR, as ADR 0056 and 0060 were. Built on Frage 221 B (one fixture material pick on the page), 222 B (Air assist in the profile, off by default), 224 B with the homing addition (Start from and Home first stored on the page), all 2026-11-16, and the review of PR #370 ("GRBL is only one solution, there can be other formats; it must be easy to extend"). Amends [ADR 0038](0038-machine-profile-records.md) §2 and [ADR 0039](0039-machine-profile-copy-in-the-project-file.md) §1, §5 (`air_assist`, `output_format`); notes go on both on acceptance. Uses the process registers of [ADR 0033](0033-manufacturing-data-in-the-project-file.md) §3 as `cuts_last` does ([ADR 0046](0046-laser-operations-record.md) §3). The job itself is derived and stored nowhere ([ADR 0064](0064-laser-job-builder-and-output-writers.md)). Spec: [`0029`](../../specs/0029-laser-job-preview-and-output/specification.md) criteria 2, 25, 32, 38, 39.

## Context

The job, the toolpath, the gate and the summary are derived from the page (criterion 32), so the job needs no format. Three answers add stored values: which material the page's fixture jobs run with, how the job starts (Machine origin, Head position, or homing first and then the machine origin; first written as two values, since 2026-11-17 one), and whether the machine has air assist. The review adds a fourth: which file format the machine reads (GRBL now, others later; ADR 0064 §12). What must stay cheap to change: the stored shapes of the page and of the profile record (both published, both synced by ADR 0062).

## Options

**The page's choices** (first written as three: fixture material, Start from, Home first; since 2026-11-17 two: fixture material and Start, §2)

- **A. Process registers on the manufacturing node (chosen).** `x.curvyo.laser.fixture_material` and `.start` (first `.start_from` and `.home_first`), like `cuts_last`. Two peers changing the pick and Start keep both (ADR 0009 §3); document-core stays opaque (ADR 0033 §3).
- **B. One atomic map `x.curvyo.laser.output`.** One value per page, but a concurrent pick and switch keep one whole map and drop the other. Rejected.
- **C. In the machine profile.** Start is per job (the customer: chosen beside Export), the fixture pick is per page (Frage 221 B). Rejected.

**The fixture pick's shape**

- **A. The material id only (chosen, Proposal).** A material not loaded here blocks the fixture jobs (ADR 0064 §3); with library sync (ADR 0062) the record follows the maker.
- **B. Id plus stored numbers, as an operation's link (ADR 0054 §1).** A second refresh path for a one-line pick. Rejected for now; it is additive later.

**Air assist:** one more boolean in `ProfileValues`, the `motorised_z` precedent (ADR 0056 §7). No other option kept.

**The output format**

- **A. A closed enum `output_format` in the profile record and the page copy (chosen).** The format belongs to the machine, as Laser mode and S-max do; one value today, `"grbl"`.
- **B. A per-export choice beside Export.** A machine reads one format; a pick per export invites a wrong file. Rejected.
- **C. No field until a second format.** Each format would then need a migration that guesses "grbl" for every record; storing it now costs one key. Rejected.

## Decision

1. **Page registers** on the manufacturing node, written in history steps of their own (amended 2026-11-17 after the try: labels `set_fixture_material` "Pick fixture material", `set_start_machine_origin` / `set_start_head_position` / `set_start_home_then_origin` "Start: Machine origin" / "Start: Head position" / "Start: Home, then machine origin", one label per value; names in `curvyo-ui-core/src/history_names.rs`; the first build's `set_start_from_*` and `set_home_first_*` labels are removed):
   - `x.curvyo.laser.fixture_material`: a lowercase UUID text naming a material record; absent = no pick.
   - `x.curvyo.laser.start`: `"machine_origin"`, `"head_position"` or `"home_then_origin"`; absent = `machine_origin`.
   Read in `curvyo-laser-core/src/output_settings.rs`; a value of the wrong type or spelling reads as its default, counts one damaged value and is never rewritten on read. A damaged pick is no pick (it blocks running fixture jobs). **A damaged `start`** (Proposal, as `output_format` in §3) reads as Machine origin for the job and the preview (criterion 38's test), is flagged in the output group's view (`start_damaged`, the pick shows no checked option) and blocks Export with the check `StartDamaged` whose button opens the Start pick (ADR 0064 §8); any pick writes the register and clears it, even Machine origin. So a file is never written from a guessed start: a hand-edited or corrupted value could otherwise turn a relative job into an absolute one on the bed. **Who checks the spellings** (amended 2026-11-17, review): `curvyo-document-core` validates them on write (`Document::set_start` keeps its own list of the three spellings, `laser_output_commands.rs`, and refuses any other with `OperationError::BadStart`, so no build writes a damaged value), while `curvyo-laser-core`'s `Start::ALL` reads them; document-core does not depend on the laser core, so the two lists are kept equal by the session test that sets every value of `Start::ALL` (`session/output/tests/group_tests.rs`). A new value changes both and is a format change.
2. **One Start value** (amended 2026-11-17 after the try; replaces the Home first rule). The register holds the effective start; there is no derived value and no stored earlier choice. `Start` is one closed enum in `output_settings.rs` (`MachineOrigin`, `HeadPosition`, `HomeThenOrigin`), read by the output group and the job. **Home, then machine origin** writes the format's home command first (GRBL `$H`) and then runs exactly as Machine origin (ADR 0064 §7). A fourth value is a format change like an `output_format` value (§3): a project `format_version` bump, so an older build refuses the file instead of reading the value damaged.
   - **Rejected:** keeping the two registers and mapping them to three values (two stored keys for one choice, a state that does not exist, `home_first` with `head_position`, and the greyed Start from the customer found hard to read); a boolean `home` beside a two-value `start` (the same, smaller).
   - **No migration:** format 48 is unreleased (no file of it outside this branch), so its number stays and `start_from` / `home_first` are simply no longer written or read. A file of the PR #371 build that holds them opens with Start Machine origin; the two keys stay as unknown process registers (ADR 0033 §3) and are not rewritten on open.
3. **Air assist and output format** (amend ADR 0038 §2, ADR 0039 §1, §5). `ProfileValues` gains `air_assist: bool` (default false; Generic laser false) and `output_format: OutputFormat` (a closed enum in `machine_profile.rs`, one value `Grbl`, spelling `"grbl"`; default and Generic laser `Grbl`). The job builder reads `air_assist`; only `job_write.rs` reads `output_format` (ADR 0064 §12).
   - **Profile record format 6:** `"air_assist": false` after `motorised_z`, then `"output_format": "grbl"`, both always written. Format 5 records read `air_assist` as false and `output_format` as `grbl` and are not rewritten on read; either key in a format 5 record is an unknown key and damages it; an `output_format` spelling this build does not know damages a format 6 record (never read as GRBL); formats 1 to 4 stay skipped as older (ADR 0060 §3); above 6 is skipped as newer with its notice. Any write upgrades to 6. A device on an older build skips a synced format 6 record as newer and leaves it untouched (ADR 0062).
   - **Page copy:** `mfg_profile.air_assist` (boolean, absent = false, a non-boolean reads false and shows as damaged like the other fields) and `mfg_profile.output_format` (text, absent = `"grbl"`; another value or type shows as damaged, which blocks Export by criterion 4 c, so a newer build's format is never written as GRBL). Pick, Reset and field edits write both with the map; "Differs from profile" compares them exactly. The job and the writer read them from the copy, never from the library.
   - **UI:** while `OutputFormat::ALL` holds one value the Machine block shows the read-only line "Output: GRBL" and no history step exists; the pick and its step "Set output format" come with the second value.
   - **A new value is a format change:** it bumps the profile record format and the project `format_version`, so an older build skips such a record as newer and refuses such a file, instead of reading it damaged or writing it as GRBL. Profile fields only one format reads (GRBL: `max_power`, `laser_mode`) stay ordinary profile fields; a new format's own fields ride on the same bump.
4. **`format_version` 48.** A build of 47 rewrites the whole `mfg_profile` map from its own type on a field edit and would drop `air_assist` and `output_format` silently (ADR 0056 §8 reasoning); ADR 0033 §7 refuses that by a bump. The two page registers alone would not need one (a 47 build keeps unknown process registers), they ride on it. **Migration: none.** A format-47 file opens with the defaults and is not rewritten on open.
5. **Not stored:** the job, its moves, the gate, the summary, the Toolpath view toggle, the slider position, the export folder and name. An export stores only its effects (ADR 0064 §11): fixture job Output, refreshed stored numbers, `test_grid_lasered` (existing key of ADR 0057).
6. **Goldens.** `curvyo-document-core/tests/fixtures/`: `laser_output_v48.curvyo` (a fixture pick, `start` `"home_then_origin"`, a copy with `air_assist` true and `output_format` `"grbl"`, a second page with `start` `"head_position"`, a third with no registers and no `output_format`); `laser_output_damaged_v48.curvyo` (pick a number, `start` `"middle"`, a second page with `start` `true`, `air_assist` `"on"`, `output_format` `"marlin"`: each reads its default or damaged state, counts one damage and saves back unchanged); both are rewritten for the one register (amended 2026-11-17, unreleased format), every other golden keeps its bytes; the version 47 goldens still open. `curvyo-laser-core/tests/fixtures/machine_profiles/`: `format6_air_assist.json` (with `output_format`; reads, writes back byte for byte), `format5_air_assist_key.json` and `format5_output_format_key.json` (damaged), `format6_unknown_output_format.json` (damaged), `newer_format.json` moves to format 7, every format 5 golden still reads with `air_assist` false and `output_format` `grbl`.

## Consequences

- Published keys: `x.curvyo.laser.fixture_material`, `x.curvyo.laser.start` and its three spellings (amended 2026-11-17; `start_from` and `home_first` are never published), `mfg_profile.air_assist`, `mfg_profile.output_format` and its spelling `grbl`, the record keys `air_assist` and `output_format`. Renaming one, or adding an `output_format` value, is a format change.
- The `specs/README.md` format table gains row 48 for `0029` (the lead, with the story PR; the number is taken at merge).
- A live Home button (`0064`) needs no stored value; it reuses nothing of this ADR.
