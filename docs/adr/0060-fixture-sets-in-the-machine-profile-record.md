# ADR 0060: Fixture sets in the machine profile record: named `fixture_sets`, pins and grids, role jobs, record format 5

**Status:** Proposed 2026-11-12, `needs-customer` (persistence: machine profile record format). Built on Frage 207 B (named sets of the machine; the page keeps its own copy and its own On this page choices) and the decisions listed in [ADR 0059](0059-fixture-sets-job-fixtures-and-pins-in-the-project-file.md). **Amends** [ADR 0050](0050-laser-fixture-set-in-machine-profile.md) §1 to §5 and §8 and [ADR 0052](0052-laser-fixture-jobs-in-the-project-file.md) §7 (record format, copy, Differs, goldens); notes go on both and on [ADR 0039](0039-machine-profile-copy-in-the-project-file.md) §4 and §5 on acceptance. Builds on record format 4 of [ADR 0056](0056-laser-operation-tools-in-the-project-file.md) §7 (`motorised_z`). Spec: [`0113`](../../specs/0113-fixture-sets-and-pins/specification.md) criteria 9, 10, 14, 39 to 41. Feature notes: [`0113` adrs.md](../../specs/0113-fixture-sets-and-pins/adrs.md).

**Amended 2026-11-15** (lead, Proposal, vetoable; Curvyo is not deployed): records of formats 1 to 4 are skipped as "older format" and never read into sets or rewritten (§3, §4, §9).

**Amended 2026-11-16** (architect, after the customer tried the build: sets "should be persistent across all pages and instances" and lockable; record format 5 is unreleased, so it changes in place): the record is the **only home** of a set. Entries gain ids and locks and lose `active` (§1); the Fixtures tab edits the record directly from any page, as undo steps with the library journal (§5a, new); the copy, Save as, Update and Differs shrink (§5 to §7); goldens (§9). The page side (mirror, choices, alignment) is ADR 0059 decisions 1, 6, 10 as amended. Also amends ADR 0055 §9 (the journal holds machine records too) and ADR 0039 §4, §5 (Update, Reset and Differs act on the machine fields only).

## Context

The record holds one unnamed `fixtures` array (formats 2 to 4). The page now holds named sets, and the profile must carry them by name and order, never the page's On this page choices and never its job fixtures.

## Options

- **A. Replace `fixtures` by `fixture_sets`, an array of `{ name, fixtures }`, in record format 5 (chosen).** One record per profile (ADR 0038 option A); the entry shape of format 3 is reused inside each set.
- **B. Keep `fixtures` and add a `set` name per entry.** Order of sets is implicit, an empty set cannot exist. Rejected.
- **C. One file per set.** Several files per profile to keep consistent (ADR 0050 option B). Rejected.

## Decision

1. **Record format 5.** `"fixture_sets": [ { "name": "Bed", "fixtures": [ ... ] } ]` replaces `fixtures`, in the same place (after `connection`), always written (possibly `[]`). Each fixture entry is the format-3 entry (ADR 0052 §7) with:
   - kind `pin` (`params`: `diameter_mm`, `columns`, `rows`, `column_spacing_mm`, `row_spacing_mm`, `mark_mm`, no slots); a screw's `params` gain `columns`, `rows`, the two spacings and `mark_mm`; ranges as ADR 0059 §4; the matrix of a pin or a screw is a translation;
   - a job entry may hold `"role": "centre_mark" | "diameters"`; a pin or a screw holds exactly one job of each role, with the fixed tokens `pin.marks` / `screw.marks` and `pin.circle` / `screw.head` + `screw.thread`; a role on another kind, a missing or duplicate role job, or other tokens on a role job are damage. Further jobs on a pin or a screw are allowed only as the ones a format-3 screw had (kept and copied).
   - New tokens: `pin.circle`, `pin.marks`, `screw.marks`.
   - No `on_page` key and no job fixtures, ever: the writer builds the record from the page's sets only.
   - **Amended 2026-11-16:** a set is `{ "id", "name", "locked", "fixtures" }`; a fixture entry starts with `"id"` and gains `"locked"` after `name`; a job entry starts with `"id"`. Ids are lowercase UUID v4 from `new_record_id` (16 caller bytes, ADR 0038 §5), unique within the record across sets, fixtures and jobs; `locked` is always written (`false` or `true`). The entry **loses `active`**: On the bed is a choice of each page (ADR 0059 §1 amended, Frage 211 B). A missing or duplicate id, a missing `locked` and an `active` key are damage (strict, as §2). A locked set locks every fixture in it.
2. **Limits:** 16 sets, 64 fixtures in all sets together, 200 slots, 200 jobs, 400 targets, set and fixture names of 1 to 40 characters; the record text limit rises from 128 KiB to **256 KiB** (a maximal golden must read and fit). Damage anywhere in a set makes the whole record damaged (ADR 0050 §2), as do an empty set name and a key not listed here.
3. **Reading** (amended 2026-11-15). Only format 5 is read. A record of format 1 to 4 is skipped as **older** (`RecordError::Older`, the profile library counts it: "1 profile has an older format. It was left as it is.", Proposal), as a format-1 material record is (ADR 0058 §6); it is left on disk untouched and its id is skipped, so Save as profile takes a new id. In format 5 a `fixtures` key is damage. A record above 5 is skipped with its notice. Reads never write.
4. **Writing.** Always format 5. An older record is never written (it is skipped, §3).
5. ~~**Copy into a page**~~ **(superseded 2026-11-16 by ADR 0059 decisions 6 and 10: Pick builds the page's mirror with the record's ids, every set on; Reset leaves sets alone; Generic laser deletes the mirror without a notice.)** Original text: **Copy into a page** (amends ADR 0050 §4). Pick profile and Reset from profile delete the page's set nodes and write one set node per record set, in order, `set_on_page` on (`0113` criterion 9, Proposal), with fresh node ids for sets, fixtures, slots and jobs, `op_output` = `false`, and the target keys mapped by place (ADR 0052 §7); a screw or pin read without role jobs gets them (ADR 0059 §5). Job fixtures are not touched. Generic laser has no sets: picking it removes the sets and keeps the job fixtures; the pick notice says "Fixture sets removed (undo restores them)." One commit with the existing labels, one undo step.
5a. **Edits from the Fixtures tab write the record** (new 2026-11-16; amends ADR 0055 §9).
   - **Where:** on any laser page whose profile record is loaded and readable. Every content edit of a set or a set fixture (add, rename, remove, move a set; lock and unlock a set or a set fixture; add, remove, rename, move, resize, a parameter, a slot, a fixture job, a tick, a role-job Size) is one document step with its existing label. In that step the session commits the command on the page's mirror, aligns every other manufacturing of the project on the same profile (ADR 0059 §10 b), writes `mfg_fixture_sets_modified` = the new `modified`, and hands the host one record write: the loaded record with `fixture_sets` built from the mirror and a new `modified`. A drag writes once, at its release. Page choices (On this page, On the bed, eye, Output) are document steps only and never write the record.
   - **Read only:** while the page's profile is Generic laser, or its record is missing, damaged, older or newer here, the mirror is shown and every content edit is refused (hidden controls, `0113` criterion 46); the choices still work. **Save as profile** makes it editable (§6).
   - **Undo:** the journal of ADR 0055 §9 holds `{ record kind, id, before, after }` for machine records as for materials, in one 16 MiB budget; undo writes `before` back while the record's text is still `after`, else leaves it with "<profile> changed since, its sets were not undone."; limits (a) to (f) of ADR 0055 §9 apply word for word ((e): "<profile> sets can no longer be undone."; (f): a refused host write undoes the document part with "Could not save <profile>. The change was undone."). After a successful undo the mirror equals the record's contents, so the guarded alignment finds nothing to do. Amended 2026-11-16 (architect review): after every undo or redo of a set edit, done or refused, each page on the profile whose mirror's contents differ from the loaded record takes the record's sets (reserved commit, no undo step), whatever the two `modified` times say.
   - **Other instances:** another open project (window, tab) sees the edit at its next library reload. The host reloads the record of every open page's profile when the window gains focus and, in the browser, on a `storage` event of a `curvyo.machines/` key (Proposal); the session then aligns (ADR 0059 §10 a). Two instances editing between reloads: the later whole-record write wins (the "Record conflicts" debt, as material edits).
6. **Save as profile / Update profile** write the page's sets (names, order, fixtures, jobs with their `show`, roles and tokens) and never On this page, Output, locks or job fixtures.
   **Amended 2026-11-16:** **Save as profile** writes the page's mirror (ids and locks kept, so the page's choices stay attached) into the new record and points the page at it; this is also how a page opened on a computer without its profile becomes editable. **Update profile** writes the machine fields only and keeps the loaded record's `fixture_sets` as they are (they are already live).
7. ~~**Differs from profile**~~ **(dropped 2026-11-16: sets are the profile's, so they cannot differ; Differs compares the machine fields of ADR 0039 §5 only. `sets_differ` stays, as the alignment's content test of ADR 0059 §10, ignoring every page choice.)** Original text: **Differs from profile** (amends ADR 0050 §5, ADR 0052 §7): the page's sets compared in order by name and by their fixtures as ADR 0050 §5 and ADR 0052 §7 compare them, plus the new parameters and roles (lengths within `PRESET_MATCH_TOLERANCE`). On this page, Output, `fixture_locked` and job fixtures are ignored.
8. **Module.** `curvyo-laser-core/src/machine_profile_fixtures.rs` keeps the entry codec; the set layer goes into `machine_profile_sets.rs` ("reads and writes the named fixture sets of a profile record") so neither module passes 500 lines.
9. **Goldens** in `curvyo-laser-core/tests/fixtures/machine_profiles/`: `format5_fixture_sets.json` (two sets, one empty; a holder with slots and a job, a 4 x 1 screw grid, a 2 x 2 pin grid with role jobs; reads, writes back byte for byte), `format5_max_sets.json` (the limits of decision 2; reads, fits 256 KiB), `format5_damaged_role.json` (a third role job), `format5_damaged_pin.json` (a pin with text in `diameter_mm`), `format5_fixtures_key.json` (a format-5 record with `fixtures`: damaged), `newer_format.json` moves to format 6. The format-1 to -4 goldens (`format1_full_record.json`, `format2_*.json`, `format3_*.json`, `format4_motorised_z.json`) are all skipped as older and stay as pins of that rule (amended 2026-11-15).
   **Amended 2026-11-16:** every `format5_*.json` golden is regenerated with ids and `locked` and without `active`; `format5_fixture_sets.json` gains a locked set and a locked fixture; `format5_max_sets.json` must still fit 256 KiB with all ids; new damaged goldens `format5_duplicate_id.json`, `format5_missing_id.json`, `format5_active_key.json`; new `format5_align_newer.json` for ADR 0059 §9.

## Consequences

- A format-5 record is skipped by a build that reads up to format 4 ("newer version"), as ADR 0038 §3 intends.
- Records stay whole-record writes: two computers editing one profile's sets offline make a conflict copy, as before (ADR 0038).
- The page's On this page choices never travel through the profile; a second project on the same machine starts with every set on.
- (2026-11-16) Sets are edited far more often than profiles were, and every edit rewrites the whole record: two devices editing one profile's sets offline meet the newest-`modified`-wins merge of ADR 0062 §5 with a conflict copy and a notice more often. The ids per set, fixture and job make a later union-by-id merge (ADR 0004 §8) possible without a format change; the "Record conflicts" debt in `docs/technical-debt.md` names this (lead).
- (2026-11-16) Rejected: keeping a page copy edited by Update profile (the customer's finding: bound to the page).
- Rejected and why: a set name per entry (B, no order, no empty set), a file per set (C).
