# SVG import: bring an SVG drawing into a project as objects (SVG export follows in a later slice)

Status: Draft (2026-10-16: customer decisions applied; the first slice is the import, SVG export is a later slice, see "Later: export"; no open questions; the ADR 0018 needs review)
Priority: Must
Origin: Customer (MVP slice 11, confirmed 2026-10-02: "imports and exports plain SVG well enough that a project can move to and from Inkscape without hand-fixing geometry"; R-SYS-006). Customer decisions of 2026-10-16 (section "Decided (customer, 2026-10-16)") narrowed the first slice to the import: the customer does not save natively in SVG, so "import and then place where we want is enough"; there is no loss report. The page-size rules, the CSS subset, the Inkscape attributes and every item marked **Proposal** are the product owner's, vetoable at the demo.
**Requirement R-SYS-006 is met in two steps:** this slice (import) and the later export slice (section "Later: export"). The requirement is not met until both are done.
Depends on: `0023-groups`, `0050-layers-and-objects-panel` (layers, names, hidden, locked, opacity), `0054-combine-open-paths` (compound paths with open outlines), `0051-sidebar-and-no-menu` (the File tab), `0049-linked-clone` and `0056-mirror-and-negative-scale` (the `<use>` criterion makes linked clones and flips; without `0049` built, a `use` is a copy, criterion 47). It is the first importer, so it also does what ADR 0002 §10 asks of "the SVG import story".

## User value

As a maker who draws in Inkscape, or who gets SVG files from elsewhere (a box generator, a stock site, a customer), I want to bring an SVG into my project as ordinary objects, in view and selected, so that I can place it where I want and work on it without redrawing or repairing a file by hand.

As a maker I want a file that holds things Curvyo does not draw (text, images, filters) to open anyway with everything it can use, and not to be refused or buried in warnings.

**What the reference tools do, and what we do differently** (from their documentation and behaviour as far as I know; check against the version the customer uses):

- *Inkscape.* SVG is its file format, so nothing is lost by construction. It keeps a path as written and records node types in `sodipodi:nodetypes`, keeps stars, arcs and spirals as `sodipodi:type` paths, marks layers with `inkscape:groupmode="layer"`, locks with `sodipodi:insensitive`, and writes `fill-rule:evenodd` on most paths it draws. Files from Inkscape 0.91 and earlier assume 90 pixels per inch; 0.92 and later use 96 (Inkscape wiki, "CSS96"). It asks the maker about legacy files in a dialog.
- *Ink/Stitch.* Its embroidery settings live in the SVG as `inkstitch:`-prefixed attributes. Curvyo does not keep them: an import uses the SVG as a composition source and the other information disappears (BAG, below).
- *LightBurn.* Imports SVG (and many other formats), with a setting in Edit > Settings that chooses 72 or 96 dpi for SVG pixels; the forum threads show that a wrong choice is the most common "my SVG came in 25 % too small" case, mostly with Illustrator files. It has no list of what it dropped.
- *What is better here.* (1) A defined result for every readable file, never a refusal for a feature we do not have: the file imports and what is not supported is left out silently. (2) Page size is decided by rules that a maker can read, and an Illustrator or old Inkscape file is recognised, so no setting and no dialog is needed. (3) Inkscape clones (`<use>`) stay linked clones where the picture allows. (4) The imported content lands in view, selected, ready to place. The goal over time is to read as much as Inkscape does; until then the importer simply tries.

## Words used below

- **Supported subset:** what this spec says is read. Everything else is **ignored** silently (criterion 13).
- **Page:** the document rectangle (`0015`). A document has one.
- **User unit:** the unit of the numbers inside the SVG, before the viewBox maps them to the page.
- **Leaf:** a path, compound path, rectangle, ellipse, polygon or star. **Clone:** `0049`; its **matrix** M maps the original's geometry to the clone's.
- Lengths are compared with the tolerances of the earlier specs: 1e-6 mm for drawn outlines, 1e-9 mm for stored values.

## What exists today

Facts from the code on `main` and from the accepted specs (2026-10-14).

- **No SVG code exists.** `Open` takes a `.curvyo` project only (`0001`, `0051`). ADR 0002 §10 fixes the strategy: a documented subset, golden files, a named and listed loss, gradients not in the subset (amended 2026-10-08). The customer's decisions of 2026-10-16 replace the "listed loss" (no report) and defer the passthrough bag (`adrs.md`).
- **The model has no per-node transform.** A group has none (`0023` criterion 25); a primitive stores a frame and a `rotation`; a path stores anchors; only a clone (`0049`) has a matrix. So every SVG transform is applied to the geometry on import.
- **A style is resolved per leaf** (ADR 0002 §5): fill none or one colour plus opacity, stroke on or off with width in mm, colour, opacity, dash (a list in multiples of the stroke width, no phase), join (miter limit fixed at 4), cap, and markers (`0017`, `0018`). Opacity of a node composes per paint, not as a group (`0050` Question 5, A). There is one fill rule, nonzero (`0054`).
- **Compound paths** hold open and closed outlines, touching or crossing (`0054`, built after `0050`). Holes are outlines of opposite direction (`0016`, `0035`).
- **Clones** (`0049`, `0057`): a clone stores its original and a matrix of any affine kind, draws the root original's style and opacity, does not scale its stroke by the matrix, may have its own placement and its own style (`0057`), and may have a negative determinant (`0056`).
- **Layers** are top-level groups with a `layer` marker, a name, `visible`, `locked` and `opacity` (`0050`). Groups nest to 32 levels (`0023`). Other nodes carry the same four registers.
- **Primitives:** rectangle (four corner radii, circular, `0013`), ellipse and circle, polygon and star (3 to 1024 points, inner ratio, first-vertex angle). Every primitive has a `rotation`. A stretch converts a rotated primitive to a path (`0047`, `0056`).
- **Page:** 1 to 100,000 mm per side (`0015`), a display unit mm, cm or in, a background colour with alpha or none (`0040`).
- **The File tab** holds New, Open…, Save, Save as…, Close, Quit and the version line; `0051` leaves "Export and Import of drawings" to this spec. There is no menu on Linux and Windows. Messages go to the canvas notice slot (transient notices of 3 s) or sit 4 px under the button that caused them (`docs/design-system.md`).
- **Crates:** pure logic lives in `*-core` crates that build for wasm, with no file access; a platform crate reads and writes files (`CLAUDE.md` §6, ADR 0011). Golden files live in the crate's `tests/fixtures/` (`CLAUDE.md` §5).

### C. The page, the units and the viewBox

15. Given the root `<svg>` with `width`, `height` and `viewBox`, then the page is width × height converted to millimetres (px 25.4/96, pt 25.4/72, pc 25.4/6, mm, cm, in, and em as 16 px, ex as 8 px; a number without a unit is px), and the viewBox maps to that rectangle by `preserveAspectRatio` (default `xMidYMid meet`). Examples: `width="210mm" height="297mm" viewBox="0 0 210 297"`: page 210 × 297 mm, one user unit is 1 mm, so `<rect x="10" y="20" width="30" height="40"/>` becomes a rectangle from (10, 20) to (40, 60). `width="2in" height="1in" viewBox="0 0 200 100"`: page 50.8 × 25.4 mm, one user unit is 0.254 mm, and `<rect x="100" width="100" height="100"/>` is from (25.4, 0) to (50.8, 25.4). For **Open** these rules give the page; for **Import SVG…** the project's page is not changed and they give only the scale from the file's units to millimetres. A viewBox that does not start at 0 (`viewBox="10 10 100 100"`) puts its top-left corner on the page's top-left corner.
16. Given a root with `width` and `height` but **no viewBox**, then one user unit is one CSS pixel (25.4/96 mm = 0.264583 mm; the SVG rule) (no message). Example: `width="210mm" height="297mm"` and `<rect width="100" height="50"/>`: page 210 × 297 mm, the rectangle is 26.4583 × 13.2292 mm. Nothing is guessed from the numbers' size.
17. Given a root with a viewBox but no usable `width` and `height` (missing, `auto`, or a percentage), then the page is the viewBox size read as pixels. Example: `viewBox="0 0 100 50"` only: page 26.4583 × 13.2292 mm, one user unit 0.264583 mm. Given a root with neither size nor viewBox, then the page is the drawing's bounding box from (0, 0) to its right and bottom edge (the stroke excluded), in millimetres, **rounded up to whole millimetres** (at least 1 mm), and nothing is moved: `<rect x="10" y="10" width="100" height="50"/>` gives a page of 30 × 16 mm with the rectangle at (2.6458, 2.6458), 26.4583 × 13.2292 mm. An empty drawing with no size gets the size of a new document (`0015`).
18. Given a viewBox whose aspect ratio differs from width : height, then the whole `preserveAspectRatio` is honoured (all nine alignments, `meet` and `slice`, and `none`) by applying the viewBox-to-viewport map to the geometry. Example: `width="100mm" height="100mm" viewBox="0 0 200 100"` (meet, centred): scale 0.5, and `<rect width="200" height="100"/>` is from (0, 25) to (100, 75); with `preserveAspectRatio="none"`: from (0, 0) to (100, 100). No clip is applied for `slice` (content outside the page is kept).
19. **Pixel size of known generators.** Given a file whose root has no viewBox or a viewBox together with pixel sizes, and which names its program, then: (a) a comment `Generator: Adobe Illustrator` or the namespace `http://ns.adobe.com/AdobeIllustrator/10.0/` makes px mean 1/72 inch, because Illustrator writes points as px; (b) `inkscape:version` below 0.92 on the root without a viewBox makes the user unit 1/90 inch, the legacy of Inkscape 0.91 and earlier. Both cases are silent: no message, no setting and no dialog (customer, 2026-10-16, PIXEL-SIZE A). All other files use 96 per inch. Test: an Illustrator-made fixture of 595.28 × 841.89 px gives 210 × 297 mm; the same numbers from another program give 157.50 × 222.75 mm.
20. Given the rest of the root: (a) a page side below 1 mm or above 100,000 mm is clamped to that range and the drawing is not scaled; (b) `sodipodi:namedview` with `inkscape:document-units` of `mm`, `cm` or `in` sets the display unit (`0015`), any other value leaves mm; (c) `pagecolor` with `inkscape:pageopacity` sets the document background (`0040`): the colour with that opacity, or none when the opacity is 0 or the attribute is missing; (d) several `inkscape:page` elements (Inkscape 1.2): the first sets the page size only when the root gives none, content of all pages is kept on the one page; (e) a nested `<svg>` element is a group with the viewBox map of criterion 18 applied and `x`, `y`, `width`, `height` honoured, its overflow clip ignored. Items (a) to (d) concern the page of **Open**; Import SVG… changes no page property.

### D. Shapes and paths

21. Given a `<path>`, then the whole path-data grammar of SVG 1.1 and 2 is read: M m L l H h V v C c S s Q q T t A a Z z, implicit repeats (extra coordinate pairs after M are lines, after C more curves), commas, spaces and none where unambiguous (`M10-5`, `1.5.5` is 1.5 and .5, `1e-3`, `.5`, `-.5`), exponents, and arc flags written without separators (`a1 1 0 00 5 5`). S and T use the reflected control point (or the start point after a different command). Q and T are raised to cubic Béziers exactly. A Z followed by a drawing command without M starts a new subpath at the start of the one just closed. The result for each command is a segment of the model (lines and cubic Béziers).
22. Given an arc `A`, then it is converted to cubic Béziers of at most 45° each, exactly as the SVG implementation notes (F.6) define the centre, with radii that are too small scaled up, a zero radius becoming a line, equal end points dropping the arc, and the four flag combinations choosing the four arcs. Every point of the result lies within 0.001 mm of the true arc for radii up to 100 mm. Example: `M 10 0 A 10 10 0 0 1 0 10` in a millimetre drawing is the quarter circle about (0, 0) from (10, 0) to (0, 10) (sweep 1 is clockwise on the screen); the points of the result are 10 ± 0.001 mm from (0, 0), and with the same flags `0 0` the arc bulges the other way. A rotated ellipse arc (`A 20 10 30 …`) is tested the same way against a computed ellipse.
23. Given path data with an error (a letter that is not a command, a number where a flag belongs, a missing coordinate), then the path is imported up to the last complete command before the error, as SVG says to render it. A path that is empty or has no complete command is skipped. Example: `M 10 10 L 20 20 L 30` gives an open path of two nodes.
24. Given a path with several subpaths, then they become **one compound path** (`0054` criterion 27): subpath order is outline order, a subpath with `Z` is closed and without it is open, touching and crossing subpaths are kept as written. A path with one subpath is an ordinary path. A subpath of one `M` and nothing else, or of `M` plus a zero-length `Z`, is skipped (`0054` criterion 27). Nodes are never merged, removed or re-ordered: a closed subpath whose last point equals its first and which has `Z` keeps both nodes as written (no clean-up is made on import; a "merge coincident end nodes" action is a later command).
25. Given the nodes of an imported path, then each gets a kind: with `sodipodi:nodetypes` on the element and the right number of letters, `c` is Corner, `z` Symmetric, `s` and `a` Asymmetric; without it (or with a wrong count), a node whose two handles are collinear and of equal length is Symmetric, collinear and unequal Asymmetric, everything else Corner (tolerance 1e-6 relative). The kind changes nothing about the drawn outline.
26. Given a `<rect>`, then it is a rectangle: `x`, `y`, `width`, `height`, and `rx`, `ry` (one missing takes the other's value; each clamped to half the side). `rx = ry` (within 1e-9 mm) becomes the same radius at all four corners; `rx ≠ ry` becomes a path with the elliptical corners as arcs (criterion 22), with no message. A `width` or `height` of 0 or below, or a missing one, skips the element. Percent and unit lengths follow criterion 15 (percent of the viewBox).
27. Given `<circle>` and `<ellipse>`, then they are an ellipse (a circle when rx = ry) with centre and radii; a radius of 0 or below skips the element. `<line>` is an open path of two nodes; `<polyline>` an open path; `<polygon>` a closed path (no polygon or star primitive is guessed from its points, criterion 29 and D4; the primitives come from our own data and Inkscape's star data only; architect, 2026-10-14: the guess contradicted criterion 29 and has no round trip, because the export never writes a `<polygon>`). A `points` list with an odd number of numbers drops the last number.
28. Given a `<path>` with `sodipodi:type="star"` (Inkscape's star and polygon tool) that carries `sodipodi:sides`, `sodipodi:r1`, `sodipodi:r2`, `sodipodi:arg1`, `sodipodi:cx`, `sodipodi:cy` and `inkscape:flatsided`, then it is a polygon (flat-sided) or star primitive with those numbers, **but only if** the drawn `d` equals the outline of that primitive within 1e-3 mm; if the maker edited the path since (the shape no longer matches), it is an ordinary path. `inkscape:rounded` or `inkscape:randomized` other than 0 make it an ordinary path. `sodipodi:type` `arc` and `spiral` are ordinary paths from `d` (ellipse arcs are not in the model, `0021`).
29. Given any other `<path>`, then no primitive is guessed from its geometry: a closed path that looks like a circle or a rectangle stays a path (the maker converts nothing, loses nothing, and the node data stays as drawn).
30. Given a coordinate, radius or length that is not a finite number or that lands beyond ±10,000,000 mm after all transforms, then the element is skipped. An element with a negative or zero `stroke-width` keeps its fill and has no stroke.

### E. Transforms

31. Given `transform` on any element, then every transform of the element and its ancestors, with the viewBox map, is composed in SVG order and **applied to the geometry** of each leaf; groups carry none (`0023`). The syntax of `matrix`, `translate`, `scale`, `rotate(a)` and `rotate(a cx cy)`, `skewX`, `skewY`, in any list with commas or spaces, is read. A transform that cannot be read is treated as the identity. A transform with determinant 0 (for example `scale(0)`) skips the element. Example (millimetre drawing): `<g transform="translate(100 50)"><path transform="rotate(90)" d="M10 0 L20 0"/></g>` is an open path whose nodes are (100, 60) and (100, 70) (rotate maps (x, y) to (−y, x) here).
32. Given a path, then anchors and handle vectors are transformed by the matrix (handles as vectors, anchors as points); the open or closed state, node order and node kinds stay; a mirror (negative determinant) keeps the order of the anchors (the direction on screen is mirrored; `0056` criterion 19).
33. Given a rectangle, ellipse, polygon or star and a transform, then the rules of `0056` criteria 18 to 22 are applied with the matrix as the signed map: a rotation, a uniform scale, a mirror and a translation (any mix) keep the primitive and set its `rotation` and frame (a mirrored rectangle permutes its corner radii to the same physical corners); a transform that stretches (unequal magnitudes) keeps an unrotated rectangle or ellipse as such when the axes stay aligned (a rectangle with radii becomes a path if the radii would be elliptical, criterion 26), and converts a rotated or skewed primitive, and every polygon and star under a stretch, to a path exactly. No entry is made for a conversion. Examples: `<rect width="20" height="10" transform="rotate(30)"/>` is a rectangle of 20 × 10 mm with `rotation` 30° and centre (6.1603, 9.3301); `<rect width="20" height="10" transform="skewX(30)"/>` is a closed path with nodes (0, 0), (20, 0), (25.7735, 10), (5.7735, 10); `<rect width="20" height="10" transform="scale(2 1)"/>` is a rectangle of 40 × 10 mm.
34. Given a stroke and a transform, then the stroke width is multiplied by √|det| (the geometric mean of the two scale factors, the rule of `0005` criterion 8); the dash list does not change, because it is in multiples of the width. Under a stretch or skew the width is thus the average of both directions.
35. Given nested elements with different viewBox maps, transforms and a layer transform (Inkscape stores a layer's offset as `transform="translate(…)"` on the layer), then the result is the same as applying the nested matrices to each leaf in one step; the order of the leaves and their styles are unchanged by the baking. Test: the nested-transform fixture compared with an independent computation of five points per leaf, within 1e-6 mm.

### F. Style

36. Given the sources of a style, then they apply in this order, the later wins: the presentation attribute, the matching simple rule of a `<style>` element (specificity: `#id` over `.class` over element name over `*`; same specificity: later in the file wins), the `style` attribute (`prop: value;`, comments, `!important` read as plain, property names in any case). Inherited properties (fill, stroke and its parts, fill-opacity, stroke-opacity, fill-rule, display-independent `visibility`) are resolved down the tree to each leaf; `opacity` and `display` are not inherited. A leaf's resulting style is stored whole on the leaf (ADR 0002 §5). `<style>` is supported for these selectors: element name, `.class`, `#id`, `*`, and comma lists of them (this is what Illustrator and Figma write); `type="text/css"` or none. A rule with a combinator, attribute selector or pseudo-class, and every `@` rule (`@import` is never followed) is skipped; `var()` and `calc()` values are ignored (the default applies).
37. Given colours, then these forms are read: `#rgb`, `#rrggbb`, `#rgba`, `#rrggbbaa`, `rgb()` and `rgba()` with numbers or percentages, `hsl()` and `hsla()`, the 148 CSS colour names, `transparent` (alpha 0), and `currentColor` (the `color` property, default black). The colour's alpha multiplies the paint opacity (criterion 39). An unreadable colour is ignored; the property then takes the value it would have without it (inherited or default).
38. Given a fill or stroke, then: `none` switches it off; a colour switches it on; `url(#id)` to a gradient is replaced by the colour in the middle of the gradient (the stops interpolated in sRGB at offset 0.5, each channel rounded to the nearest whole value, halves up: black to white gives `#808080`); to a pattern by `#808080`; `url(#id) red` with a missing target uses the fallback colour; a missing target without fallback is `none`; `url(file.svg#x)` is `none`. The default fill is black and the default stroke is none, as in SVG; when a stroke is off, the file's width, colour and caps are still stored when present, otherwise the application defaults.
39. Given opacity, then `fill-opacity` times the fill colour's alpha is the fill opacity, `stroke-opacity` times the stroke colour's alpha is the stroke opacity, and `opacity` on an element is the node's opacity register (`0050`), also on groups and layers. Example: `fill="rgba(255,0,0,0.5)" fill-opacity="0.5" opacity="0.8"` gives a red fill with opacity 0.25 on a node with opacity 0.8. A group or layer with opacity below 1 fades each object separately here (`0050` Question 5, A), so overlaps inside it may look different from the file.
40. Given the stroke parts, then `stroke-width` (any length unit; a percentage is a percentage of the viewBox diagonal divided by √2, as SVG says) becomes millimetres (criterion 34 for transforms); `stroke-linecap`: butt, round, square; `stroke-linejoin`: miter, round, bevel (`miter-clip` and `arcs` are read as miter); the miter limit is always 4 (`stroke-miterlimit` is not kept); SVG `marker-start`, `marker-mid`, `marker-end` and `marker` are not read.
41. Given `stroke-dasharray`, then each length becomes millimetres and is divided by the stroke width in millimetres, so the list is stored in multiples of the width (`0007` criterion 8). An odd count is kept as written (the renderer repeats it, `0017` criterion 32); `none`, an empty list, a list with a negative number, or a list that sums to 0 is solid (the last two are read as solid). Example: `stroke-width="0.5" stroke-dasharray="2 1"` in a millimetre drawing is the list `4 2`; `stroke-width="2" stroke-dasharray="6 4"` in a pixel drawing is `3 2`. A `stroke-dashoffset` is not kept.
42. Given `display:none` on an element or an ancestor, or `visibility:hidden` on a leaf, then the element is imported as **hidden** (`visible` false, `0050`), not dropped, so the maker finds it in the Layers tab; a hidden layer is a hidden layer. `visibility` is read on leaves only (a group has no such state here).
43. Given `fill-rule` and `clip-rule`, then `clip-rule` is ignored and `fill-rule` is handled by Part H. `paint-order`, `mix-blend-mode`, `isolation` and `vector-effect` are ignored.

### G. Structure: groups, layers, clones

44. Given `<g>`, `<a>` and `<switch>`, then `<g>` and `<a>` are groups and `<switch>` is its first child that passes (no `requiredFeatures` or `systemLanguage` test is made: the first child element); an empty group is not imported (`0023` criterion 14). A group keeps its `inkscape:label` as name (cleaned by `clean_name`), its `opacity` and its hidden state. Its `id` is not kept as a name. Order is z-order: document order, last on top. Groups nested deeper than 32 levels are merged into their parent from level 33 on.
45. Given a `<g inkscape:groupmode="layer">` that is a child of the root `<svg>`, then it is a **layer** (`0050`): `inkscape:label` is the name (else the `id`, else "Layer N"), `display:none` makes it hidden, `sodipodi:insensitive="true"` makes it locked, `opacity` is its opacity, and its transform is applied to its children. An empty layer is kept. Layers are listed in file order, first at the bottom. A layer inside a group or a layer inside a layer is a group. Loose elements at the root stay loose at the top level (`0050` decision 2).
46. Given an element with `sodipodi:insensitive="true"`, then it is locked, whether a layer or an object.
47. Given `<use>` (customer decision of 2026-10-16, USE-CLONE B), then it becomes a **linked clone** (`0049`) where it can, and an ordinary copy where it cannot. The same test decides the export direction (Later: export, criterion 59).
    - **(a) Linked clone.** The `use` becomes a clone of the object that its target was imported as, with no override (neither own placement nor own style, `0057`), when all of these hold: (i) the target is a `<path>` that was imported as a path or compound path, or is itself a `use` that became a clone (a primitive is not converted to a path behind the maker's back, so a `use` of a `<rect>`, `<circle>`, `<ellipse>` or an Inkscape star is a copy); (ii) the target is drawn in the file, so an object of the document exists for it (not inside `defs`, `symbol`, `clipPath`, `mask`, `pattern` or `marker`); (iii) the clone matrix M below is a **move, rotation or flip only**; (iv) the copy would not look different from the target: the `use` and its ancestors set no style property that the target leaves unset, compared after the cascade of criterion 36, and the `use` has no `opacity` below 1 (a clone shows its original's style and opacity, `0049` criterion 8); (v) the chain stays at most 8 clones deep (`0049` criterion 52); deeper uses are copies.
    - **What M is.** M = C_use · translate(x, y) · A_target⁻¹. C_use is the composed matrix of the `use` itself (its ancestors' transforms, the viewBox map and the `use`'s own `transform`) in millimetres; A_target is the composed matrix of the target's **ancestors** only. The target's own `transform` is already baked into the target's imported geometry and cancels. M is stored in SVG order (a, b, c, d, e, f) in document millimetres, as `0049` defines it, and applied to the target's geometry it gives exactly the geometry the copy would have had. M is stored as computed and never snapped to the ideal rotation.
    - **Move, rotation, flip.** The linear part is orthogonal: a² + b² = 1, c² + d² = 1 and a·c + b·d = 0, each within 1e-6; the determinant is then +1 (rotation) or −1 (flip, valid for a clone, `0056` and `0049` criterion 25); the translation (e, f) may be any value within ±1e7. *Why only these:* SVG scales a `use`'s stroke with its matrix and a clone's stroke is not scaled by M (`0049` criterion 9), so a scale or skew would draw a different stroke. A rotation, a flip and a translation draw the same picture either way, and the clone keeps following its original.
    - **(b) Otherwise an ordinary copy.** The referenced element is copied to the place of the `use`: the target's own style, the `use`'s transform composed with `x`/`y` as a translation, and the style properties set on the `use` and its ancestors inherited by the copy where the target does not set them (SVG's rule). The copy is an ordinary leaf with no link. This covers: a target that is a primitive, a group or a nested `<svg>`; a `<symbol>` (read as a group, its viewBox and `preserveAspectRatio` applied when the `use` has a `width` and `height`); a target inside `defs`; an M with scale or skew; a differing style or opacity; a chain deeper than 8; and every case when `0049` is not yet built.
    - **(c) Rest.** A `use` with `display:none` gives a hidden clone (or a hidden copy); a clone has its own visible and locked flags (`0050`). A `use` to another file or address is ignored; a reference cycle or a target that does not exist is skipped. The original may stand before or after the `use` in the file. The clone is placed in the z-order of the `use`, in the layer or group of the `use`.
    - **(d) Limits.** The expansion is limited to depth 16 and 100,000 copies per file; copies count toward the 5,000,000 path commands of criterion 69, a clone counts as one element and no path command; past the limit the remaining `use` elements are skipped.
    - **Examples** (millimetre drawing, `path1` is the square (0, 0) to (10, 10)). `<use href="#path1" x="30"/>`: a clone with M = (1, 0, 0, 1, 30, 0); the square from (30, 0) to (40, 10). `<use href="#path1" transform="rotate(90)"/>`: M = (0, 1, −1, 0, 0, 0), a clone from (−10, 0) to (0, 10) (rotate maps (x, y) to (−y, x), criterion 31). `<use href="#path1" transform="scale(-1 1)"/>`: a clone with M = (−1, 0, 0, 1, 0, 0), determinant −1, from (−10, 0) to (0, 10). `<use href="#path1" transform="scale(2)"/>`: a **copy** of 20 × 20 mm with the stroke doubled (criterion 34). When `path1` sits in `<g transform="translate(5 5)">` (so it is stored at (5, 5) to (15, 15)) and the `use` is `x="30"` at the root: M = translate(30, 0) · translate(−5, −5) = (1, 0, 0, 1, 25, −5), and the clone covers (30, 0) to (40, 10).
    - **Test.** The fixture `clones.svg` (criterion 75): an Inkscape Alt+D clone moved and one rotated by 30° are clones with the expected M, moving a node of the original through the document API moves both; a mirrored clone has determinant −1; a scaled clone and a clone of a rectangle are copies; a clone of a clone is a chain of depth 2 whose resolved outline equals the copy's within 1e-6 mm; a `use` that sets `fill` where its target sets none is a copy with that fill; a `symbol` with a `use` is a group of copies.
48. Given `defs`, `symbol`, `clipPath`, `mask`, `pattern`, `marker`, gradients, `filter` and `style`, then they are never drawn on their own; they are read only as far as a rule above uses them (a gradient for its middle colour, a style for its rules, a symbol through `use`). Their other uses are ignored without a message: a clip path, mask or filter is not applied and the object comes in unclipped, unmasked and unfiltered (customer, 2026-10-16, CLIP A); a pattern paint becomes mid grey (criterion 38); SVG markers are not drawn.
49. Given `<text>`, `<tspan>`, `<textPath>`, `<flowRoot>` and `<image>`, then they are not imported and no placeholder object is made. `<foreignObject>`, `<script>`, `<animate*>`, `<set>`, `<audio>`, `<video>`, `<canvas>` and `<iframe>` are ignored and never run. Elements and attributes of other namespaces are ignored (criterion 13). Text converted to paths in Inkscape is ordinary paths and imports as such.

### H. The even-odd fill rule (EVENODD A, decided 2026-10-16)

50. Given a path (or an inherited style) with `fill-rule: evenodd`, **a fill that is on**, only closed outlines, and outlines that **do not touch (`touching_outlines`, 0.001 mm, ADR 0002 §3), cross each other or cross themselves**, then the outlines are wound so that the nonzero fill of the compound path looks exactly as the even-odd fill did: an outline's depth is the number of other closed outlines of the same path that contain it; an outline of even depth gets the direction of the outermost outline that contains it (an outline of depth 0 keeps its written direction) and an outline of odd depth the opposite direction, so the winding sum is 0 or 1 everywhere; a reversal is the one of Combine (`0054`). A path with the fill off is not re-wound (nothing is painted; the written direction is kept). Nothing is shown. Example: `<path fill-rule="evenodd" d="M0 0H40V40H0Z M10 10H30V30H10Z"/>` (both squares written clockwise): after import the point (20, 20) is not filled and (5, 5) is, with the nonzero rule; with `fill-rule="nonzero"` the same data stays as written and (20, 20) is filled. Three nested squares: (5,5) filled, (15,15) not, (25,25) filled.
51. Given `evenodd`, a fill that is on, and outlines that cross each other, touch (within 0.001 mm), or cross themselves (a pentagram, two overlapping circles in one path), or a path that has an open outline with an area next to at least one other outline (even-odd fills an open outline closed by its straight line and XORs it with the rest, which no choice of windings reproduces, and reversing an open outline would change its cutting direction), then the outlines stay as written and the object is drawn with the nonzero rule, so overlaps may be filled that the file left open (no message). A path with one outline that does not cross itself is unaffected either way.

### K. Safety (untrusted files)

67. Given any SVG, then the importer is a pure function from bytes to a result; it opens no file, makes no network request, runs no script and follows no reference outside the document, whatever the file asks for (`<image href>`, `<use href>` to another file, `@import`, `xml-stylesheet`, DTD, `file:` and `http:` addresses): such references are ignored. The SVG is never inserted into the page or the DOM of the application, and no name from a file is shown as markup (`clean_name`, text nodes only). The app sends nothing anywhere because of an import or export (R-SYS-007). Test: the hostile fixtures with a network-denying test harness and a check that no fixture string appears unescaped in the page's output.
68. Given a DOCTYPE, then the external part (`PUBLIC … "…svg11.dtd"`) is never fetched and the DOCTYPE is accepted. Internal `<!ENTITY name "text">` declarations are accepted only when every one is a plain literal (no `SYSTEM`/`PUBLIC`, no `%`, no `&` or `<` in the value), at most 64 declarations of at most 256 bytes each, and the file holds at most 100,000 references to them; this is what Adobe Illustrator's older SVG exports declare (`ns_ai`, `ns_extend`, `ns_graphs`, … used in `xmlns:x="&ns_extend;"`), and refusing it would refuse real Illustrator files and hide criterion 19(a). Anything else refuses the file by criterion 6(b), so a billion-laughs or external-entity file cannot expand or read anything (architect, 2026-10-14, `adrs.md`). The five predefined entities and numeric character references are read.
69. Given limits, then: a file above 50 MiB is refused (criterion 6); XML nested deeper than 256 elements is refused as "not an SVG drawing"; more than 500,000 elements or 5,000,000 path commands stop the import at that point and keep everything read so far (no message); a single attribute above 16 MiB is skipped; a `stroke-dasharray` longer than 1,000 numbers is read as its first 1,000; `use` limits as in criterion 47. No limit is reached by any fixture except the hostile ones.
70. Given arbitrary bytes, then the importer neither panics nor runs longer than 5 s on a file within the limits. Test: (a) every Inkscape fixture and every hostile fixture truncated at 200 evenly spaced lengths and with 200 single bytes changed, each yields a refusal or a result in under 2 s, no panic; (b) a fuzz target with the fixtures as seed corpus runs for 60 s in the nightly job without a crash or timeout.

53. Given the tree, then layers are written as `<g inkscape:groupmode="layer" inkscape:label="name">` at the top level in stacking order, hidden ones with `style="display:none"`, locked ones (layer or object) with `sodipodi:insensitive="true"`, opacity as `opacity`; groups as plain `<g>` with `inkscape:label` when named; loose top-level objects directly under the root; z-order is document order. Names are escaped as XML text (`&`, `<`, `>`, quotes) and written without control or bidirectional control characters. Ids are `layer1`, `g1`, `path1`, `rect1`, `ellipse1`, `circle1`, `polygon1`, `star1`, `compound1`, `use1` numbered per kind in document order; they are not the internal node ids and no identifier of the project leaks into the file.

54. Given a path, then it is written as `<path d="…">` in **absolute** coordinates in millimetres with `M`, `L`, `C` and `Z` only, one subpath per outline in outline order, nodes in stored order and direction (`0054` criterion 26: a compound path is one `<path>`, `Z` after closed outlines only). Numbers use a decimal point whatever the operating system's language, at most 6 decimals, no trailing zeros, no exponent, never `-0`, separated by one space (`M 10 20 C 11.5 20 13 21.2 14 22 Z` form; commands and their numbers are separated by spaces). `sodipodi:nodetypes` is written from the node kinds (Corner `c`, Symmetric `z`, Asymmetric `s`) so Inkscape keeps them. No transform is written on a path and no group has one.

55. Given a primitive, then a rectangle with one radius at all corners is `<rect x y width height rx ry>`, with `transform="rotate(deg cx cy)"` when it is rotated; an ellipse is `<ellipse>` (a circle `<circle>`), rotated the same way; a polygon or star is a `<path>` with `d` and the Inkscape star data (`sodipodi:type="star"`, `sodipodi:sides`, `sodipodi:r1`, `sodipodi:r2`, `sodipodi:arg1`, `sodipodi:arg2`, `sodipodi:cx`, `sodipodi:cy`, `inkscape:flatsided`, `inkscape:rounded="0"`, `inkscape:randomized="0"`) so it opens in Inkscape as an editable star; a rectangle with different radii at its corners is a `<path>` with `curvyo:kind="rectangle"` and the shadow data of criterion 57. Test: the exported star fixture is opened in Inkscape by hand (criterion 65) and edited with the star tool.

56. Given a style, then it is written as presentation attributes (not a `style` attribute, which several cutter programs read less reliably): `fill` (`none` or `#rrggbb`), `fill-opacity` when below 1, `stroke`, `stroke-width` (mm), `stroke-opacity`, `stroke-linecap`, `stroke-linejoin`, `stroke-dasharray` (the list times the width, in mm, `none` when solid; zero values written as `0`), `fill-rule="nonzero"` on every filled leaf, `opacity` on a node below 1. Attribute order is fixed. A stroke that is off is written as `stroke="none"` and no other stroke attribute. Hidden, locked and names as criterion 53.

57. Given values that the standard attributes say less exactly than the model stores, then **shadow data** is added in the `curvyo:` namespace and only there: `curvyo:dash` (the dash list in multiples of the width, exactly), `curvyo:stroke-width` (exact mm), `curvyo:radii` (the four corner radii), `curvyo:kind` (`rectangle`, `ellipse`, `polygon`, `star` when the standard element cannot say it), `curvyo:frame` (a primitive's centre, size, rotation, first-vertex angle, inner ratio), `curvyo:markers` (start, middle, end, place, count), `curvyo:outlines` (the open or closed state of each outline of a compound path, when it cannot be told from `Z`). Names use `inkscape:label` and need no shadow data. On import, shadow data is used **only if** the standard SVG next to it still agrees (lengths within 1e-6 mm, each dash length times the width within 1e-6 mm, geometry of a primitive within 1e-3 mm); otherwise the standard SVG wins and the shadow value is dropped. Attributes in `curvyo:` that are not in this list are ignored. **Number text:** lengths and coordinates in standard attributes have at most 6 decimals (criterion 54); every number in `curvyo:` data, and opacities, ratios and angles in any attribute, are written as the shortest decimal text that reads back to the same `f64` (Rust's `Display`, no exponent, never `-0`), so "exactly" in criterion 62 holds; angles in `curvyo:frame` are radians (architect, 2026-10-14).

58. Given a compound path, then the export meets `0054` criterion 26 and the import `0054` criterion 27 (as changed by Part H): same outlines, order, open or closed state, nodes and direction after a round trip, test with an open outline, a hole and a crossing pair.

59. Given a clone (`0049`), then it is written as a `<use>` (customer decision of 2026-10-16, USE-CLONE B): `<use id="use1" xlink:href="#path1" transform="matrix(a b c d e f)"/>` with `xmlns:xlink="http://www.w3.org/1999/xlink"` declared on the root (Inkscape 1.x writes the same; SVG 1.1 readers need `xlink:href`), when all of these hold: (i) the clone has **no override** (neither own placement nor own style, `0057`: its criterion 40 and `adrs.md` say a clone with any override is an ordinary path); (ii) its matrix M is a **move, rotation or flip only**, by the test of criterion 47 (orthogonal linear part within 1e-6, translation within ±1e7); (iii) its original is written in the file under an id (the original is a path or compound path written as `<path>`, or another clone written as `<use>` or as `<path>`) and is **not hidden** (a `display:none` target hides the `use` in SVG; a hidden master with visible clones is a normal state, `0049` decision 7, so it falls to the path rule); (iv) the clone is not an orphan (an orphan has no outline and is not written).
    - **What the matrix maps to.** The original is written in absolute millimetres and carries no transform (criterion 54), so the `use`'s `transform` is the clone's own matrix M in SVG order, with the six numbers in user units, which are millimetres (criterion 52). They are written as the shortest decimal text that reads back to the same `f64` (criterion 57), so the importer of criterion 47 gets M back exactly. For a chain, each clone's M is relative to **its own** original, as in the model: B → A → O is `<use id="use2" xlink:href="#use1" transform="M_B"/>` next to `<use id="use1" xlink:href="#path1" transform="M_A"/>`, and the composition is SVG's own.
    - **Style.** The `use` carries no style attribute (and no `opacity`): it shows its target, whose full style and opacity are written on the target (criterion 56), and a clone without override has exactly the root's style (`0049` criterion 8). Its name is `inkscape:label`, its hidden state `style="display:none"` and its lock `sodipodi:insensitive="true"` (criterion 53); the clone's own ancestors (layer, group) apply to it as to any object.
    - **Everything else is a path.** A clone that fails (i) to (iv) is written as an ordinary `<path>` with its resolved outline through the whole chain and its effective style, as `0049` criterion 41 and `0057` criterion 40 say. A clone that follows a clone written as a `<path>` still uses `<use>` when it passes the test, with its M relative to that path.
    - Markers (`0018`) are written only as `curvyo:markers`. Nothing is reported either way (customer, 2026-10-16: no report). What a hidden object means for a **machine** output is decided with the manufacturing view (R-MFG-005), not here.
    - *Test:* a document with a path P, a clone of P moved by (30, 0), a clone of P rotated 30° and flipped, a clone of that clone, a clone of P with a scale of 2, a clone with own style, a clone of a hidden path, and a clone with own placement: the first three are `<use>` with the expected matrices, the last four are `<path>`; the exported file imported by criterion 47 gives back clones with the same originals and matrices within 1e-9 for the first three.

60. Given the whole file, then it contains no absolute or relative file path of the maker, no user name, no time, no random number, no application version and no identifier of the project, only the drawing and the fixed text of this criterion's profile; two exports of the same document are byte-identical (criterion 72).

61. Given an export, then every `inkscape:`, `sodipodi:` and `curvyo:` attribute above is optional to other programs: removing them leaves a valid SVG 1.1 that any viewer draws as in Curvyo, apart from the notes of criterion 59. Test: strip the three namespaces from each exported fixture and compare the rendered outlines (an independent SVG path flattener in the test that expands `use`, tolerance 0.01 mm) with the document's outlines.

62. **Our own data.** Given a generated document that uses every kind and field of the model that this spec lists (path, compound path with open and closed outlines and holes, rectangle with four different radii and a rotation, ellipse, circle, polygon, star with the rotations 0°, 30° and −45°, groups nested three deep, layers hidden, locked and with opacity, names, dashes of odd length, caps, joins, all markers, stroke off, fill off, a background and a display unit), when it is exported and imported again, then the new document equals the old one: geometry within 1e-6 mm, **everything else exactly** (kinds, radii, counts, ratios, dash lists, flags, opacity, names, order, open or closed state, node kinds, direction), ids excepted. A clone written as a `<use>` comes back as a clone of the same original with the same matrix (within 1e-9); a clone written as a `<path>` comes back as a path with the same outline (criteria 47 and 59). A property test runs this over 500 random documents of those kinds.

63. **Export is stable.** Given any document `d`, then export(import(export(d))) is byte-identical to export(d). Given an Inkscape fixture `f`, then export(import(export(import(f)))) is byte-identical to export(import(f)). Test: every fixture and the 500 random documents.

64. **Inkscape-made files.** Given each Inkscape-made fixture, then (a) import gives the expected document (golden, criterion 74), (b) export(import(f)) equals the golden exported file, (c) import of that export has the same document as (a) within 1e-6 mm (nothing is lost by the second trip, whatever the first one dropped).

65. **Inkscape opens our export (hand list, release check, not a CI test).** Given the exported goldens opened in the current stable Inkscape, then: the page size and units are as in Curvyo; layers appear in the Layers dialog with their names, hidden and locked states, in the order of the Layers tab; rectangles, ellipses and stars are still rectangles, ellipses and stars (the star tool edits them); dashes, caps, joins and opacity look the same; no object has moved; Edit > Undo history is empty; saving in Inkscape and importing that file here gives the same document again. The tester lists the Inkscape version and the result in the PR; the customer is invited to repeat it with one of his own files.

66. **Edited in between.** Given an exported file in which a coordinate, a width, a colour, a dash list or a star's point count is changed by hand in a text editor (as Inkscape would change it, without touching our shadow data), then the import shows the edited value, never the old one (criterion 57). Test: five such edits, each a fixture pair.

71 (export part). Given the document of criterion 71, then exporting it takes under 1.5 s and writes under 25 MB (a native release build, `#[ignore]` benchmark).

72 (export part). Given the same document, then the exporter gives the same bytes on every run and every operating system of the same CPU family (criterion 60); no result depends on hash-map order, the clock, the locale, the file's path or the order of threads. Test: export twice, export with `LC_ALL=de_DE.UTF-8`, compare bytes; the ids written (criterion 53) are the same.

Golden file for the export: `name.exported.svg` beside each fixture, byte for byte on the Linux gate (criterion 63), plus the pinned `curvyo_all.svg` (criterion 75, item 12).

## Out of scope

- **A loss report.** No banner, no list of what was not imported, no "Last report…", no "Copy as text", no "Save report…", no examples with line numbers. Customer, 2026-10-16: "a report of what could not be imported has no added value; we will try to import as well as Inkscape over time and until then we simply try."
- **SVG export** in this slice (section "Later: export"), and with it a "Save as Inkscape SVG" that makes SVG the project format. The customer does not save natively in SVG.
- **A passthrough bag** that keeps what we do not model and writes it back (ADR 0002 §10), so `inkstitch:` data would survive a trip through Curvyo. It is built only if Curvyo later adopts SVG as a native file format (open, edit, save). Until then, importing an SVG as a composition drops the other information.
- **Text.** `<text>` is not imported; a text node needs a font model and is its own spec. Text converted to paths works.
- **Gradients, patterns, filters, masks, clip paths.** Gradients are not in the model (ADR 0002 §10, 2026-10-08); the substitutes of criterion 38 are the whole answer. A clip path is ignored (CLIP A); applying it as an intersection is a possible later command.
- **Images.** `<image>` is not imported; tracing a raster is `0025`.
- **Animation, scripts, interactivity, `foreignObject`.** Never run, never kept.
- **Full CSS.** Combinators, attribute selectors, pseudo-classes, `@media`, `@font-face`, `@import`, `var()`, `calc()`; only the simple selectors of criterion 36.
- **SVG markers**, `stroke-dashoffset` and a configurable miter limit: the model has none; they are ignored.
- **Compressed SVG (`.svgz`)**, other encodings than UTF-8, files above 50 MiB, entity declarations.
- **A pixel-resolution setting** (LightBurn's 72 or 96) or a dialog at open; criterion 19 detects the two known cases. A wrong guess is fixed with the existing resize with typed values (`0019`).
- **Clones of primitives, scaled or skewed clones.** A `use` of a primitive or with a scale is a copy (criterion 47).
- **A live link to a file** (reload when the SVG changes on disk), batch import, drag and drop of a file onto the canvas, paste of SVG text from the clipboard (all possible later, each its own entry).
- **Merging coincident end nodes**, closing gaps, removing duplicate nodes or tiny segments, simplifying paths: nothing is cleaned on import.
- **Multiple pages.** One page; the content of all pages lands on it.
- **Chords** for Import (R-SYS-009 review), a menu entry (there is no menu).
- **Mobile.**

## Decided by the product owner

Each is vetoable at the demo; none changes what the customer asked for.

- **D1. Open reads SVG too; Import SVG… adds to the project (Proposal).** The brief says "open"; the second route costs one dialog route and one history step. Import places the content on the centre of the view (criterion 3).
- **D3. Defined result over refusal.** Only five cases refuse (criterion 6), all of them files from which no drawing can be built or that endanger the machine; everything else imports, silently dropping what is not supported.
- **D4. Nothing is cleaned or guessed.** No node merged, no path turned into a circle, no coincident end closed. What is in the file is in the document. Primitives come only from primitive elements and from Inkscape's star data, and only when the drawn shape agrees.
- **D5. Transforms are applied to geometry.** The model has none and the groups carry none (`0023`); the one exception is a clone's matrix (criterion 47).
- **D8. Gradients become the middle colour, patterns mid grey, clips, masks and filters are ignored,** all without a message. The alternative (leave the object out) would make parts of a design vanish.
- **D9. Hidden objects are imported hidden.** SVG has a hidden state; the machine meaning is R-MFG-005's.
- **D10. Simple `<style>` rules are supported** (Illustrator and Figma write classes; without them their files import black).
- **D12. Unit conversions are exact:** 25.4/96, 25.4/72, 25.4/90; em as 16 px.
- **D13. File kind is decided by content, not extension.**
- **D14. No format change here;** the XML parser, the crate and the dependencies are the architect's and are decided in `adrs.md` (new crate `curvyo-svg-core`, ADR 0018 proposed; `roxmltree`, `svgtypes`, `simplecss`).
- (D2 and D11 of the earlier draft were about the report and are gone. D6 and D7, about our `curvyo:` data and the export format, apply to "Later: export": our data yields to the plain SVG whenever the two disagree; export writes millimetres, presentation attributes, absolute coordinates, `M L C Z` only.)

## Decided (customer, 2026-10-16)

No open questions remain. The customer answered the six questions of the earlier draft and a seventh that the PO put on 2026-10-16:

- **EVENODD (A).** An even-odd fill is re-wound by depth on import so the picture stays the same (criteria 50 and 51). Where outlines cross or touch, the object is drawn nonzero without a message.
- **USE-CLONE (B).** A `<use>` becomes a linked clone, and (in the later export) a linked clone is written as `<use>`, where its relation to the original is only a move, rotation or flip. The cases that fall back to a plain copy or path, and what the clone's matrix maps to, are in criterion 47 and, for the export, criterion 59. Checked against `0049` (a clone has a matrix of any affine kind, no own stroke scaling, ancestors resolve for visible, locked, opacity), ADR 0015/0016 and `0057` (own placement and own style are overrides: a clone with an override is a path on export; an imported clone has none), and `0056` (a flip is a valid negative determinant; the importer and exporter accept it).
- **REPORT-PLACE (no report).** There is no loss report at all: no catalogue, banner, list, "Last report…", "Copy as text", "Save report…" or Dismiss. What stays is the defined import result for what is supported, silent ignoring of the rest, one notice when an import produced nothing (criterion 8), and the five refusals where the file cannot be read, each ending "Nothing was changed.". Criteria 9 to 12 and 14 are removed.
- **BAG (A).** No passthrough bag in this slice. The bag is built only if Curvyo later adopts SVG as a native file format (open, edit, save). When an SVG is imported to be used as a composition, the other information (for example `inkstitch:` data) simply disappears. This amends the "kept per node" sentence of ADR 0002 §10 (`adrs.md`).
- **CLIP (A).** Clip paths are ignored.
- **PIXEL-SIZE (A).** 96 per inch, except Illustrator files (72) and Inkscape 0.91 or older without a viewBox (90), silently (criterion 19).
- **SVG-EXPORT-LATER (A).** The first slice is the import, placed on the centre of the view as a composition source, through the File tab "Import SVG…" and Open. SVG export moves to a later slice (section "Later: export"); R-SYS-006 is met in two steps. Open-edit-save of SVG is not the focus ("import and then place where we want is enough"). The placement on the centre of the view (not the file's origin) is the PO's reading and may be overridden by the customer at the demo.

### Busy state (criterion 7)

Parsing runs on the main thread, so nothing can animate while it runs (the rule of `0058`).

- Before the work starts the app sets the busy flag, the cursor `wait` on the whole window and paints one frame (two `requestAnimationFrame` turns). When the file is **1 MiB or more** (known before the parse; about 150 ms at the 2 s per 12 MB budget) the canvas notice slot first shows "Opening poster.svg..." / "Importing poster.svg..." (`role="status"`, no time limit, replaced by the result). Smaller files show nothing: a flash of text is noise.
- While busy, canvas input, the File buttons, Undo and the chords are ignored (`aria-busy` on the app root). No Escape and no progress bar.
- The result appears in the frame the work ends: the document and the selection together, and the notice of criterion 8 when it applies.

### The only notice (criterion 8)

"Nothing in poster.svg could be imported." in the canvas notice slot, `role="status"`, 3 s, no focus. There is no banner and no persistent line, so the Document preview banner (`0042`) is never in conflict. After a successful import there is no message; the selected objects in view are the confirmation.

### Refusal dialogs (criterion 6)

The existing error dialog pattern (modal, `role="alertdialog"`, focus on **OK**, Escape closes), one sentence per case, each ending "Nothing was changed.". The title is "Can't open file" for Open… (the file may be neither a project nor an SVG) and "Can't import SVG" for Import SVG…; the text for Open and Import:

| Case | Text |
|---|---|
| (a) Open, content is neither | "This file is not a Curvyo project or an SVG drawing. Nothing was changed." |
| (a) Import, or Open of a file that starts with `<` | "This file is not an SVG drawing (line 3, column 14). Nothing was changed." (position only when the parser gives one) |
| (b) entities | "This file defines XML entities, which Curvyo does not read because they can be used to exhaust memory. Nothing was changed." |
| (c) size | "This file is larger than 50 MiB. Nothing was changed." |
| (d) encoding | "Only UTF-8 SVG files can be opened. Save the file as plain SVG. Nothing was changed." |
| (e) compressed | "Compressed SVG (.svgz) is not supported. Save the file as plain SVG. Nothing was changed." |
