## User value

As a maker who draws in Inkscape, or who gets SVG files from elsewhere (a box generator, a stock site, a customer), I want to bring an SVG into my project as ordinary objects, in view and selected, so that I can place it where I want and work on it without redrawing or repairing a file by hand.

As a maker I want a file that holds things Curvyo does not draw (text, images, filters) to open anyway with everything it can use, and not to be refused or buried in warnings.

**What the reference tools do, and what we do differently** (from their documentation and behaviour as far as I know; check against the version the customer uses):

- *Inkscape.* SVG is its file format, so nothing is lost by construction. It keeps a path as written and records node types in `sodipodi:nodetypes`, keeps stars, arcs and spirals as `sodipodi:type` paths, marks layers with `inkscape:groupmode="layer"`, locks with `sodipodi:insensitive`, and writes `fill-rule:evenodd` on most paths it draws. Files from Inkscape 0.91 and earlier assume 90 pixels per inch; 0.92 and later use 96 (Inkscape wiki, "CSS96"). It asks the maker about legacy files in a dialog.
- *Ink/Stitch.* Its embroidery settings live in the SVG as `inkstitch:`-prefixed attributes. Curvyo does not keep them: an import uses the SVG as a composition source and the other information disappears (BAG, below).
- *LightBurn.* Imports SVG (and many other formats), with a setting in Edit > Settings that chooses 72 or 96 dpi for SVG pixels; the forum threads show that a wrong choice is the most common "my SVG came in 25 % too small" case, mostly with Illustrator files. It has no list of what it dropped.
- *What is better here.* (1) A defined result for every readable file, never a refusal for a feature we do not have: the file imports and what is not supported is left out silently. (2) Page size is decided by rules that a maker can read, and an Illustrator or old Inkscape file is recognised, so no setting and no dialog is needed. (3) Inkscape clones (`<use>`) stay linked clones where the picture allows. (4) The imported content lands in view, selected, ready to place. The goal over time is to read as much as Inkscape does; until then the importer simply tries.

## Words used below

- **Supported subset:** what this spec says is read. Everything else is **ignored** silently (criterion 13).
- **Page:** the document rectangle (`0015`). A document has one.
- **User unit:** the unit of the numbers inside the SVG, before the viewBox maps them to the page.
- **Leaf:** a path, compound path, rectangle, ellipse, polygon or star. **Clone:** `0049`; its **matrix** M maps the original's geometry to the clone's.
- Lengths are compared with the tolerances of the earlier specs: 1e-6 mm for drawn outlines, 1e-9 mm for stored values.

## What exists today

Facts from the code on `main` and from the accepted specs (2026-10-14).

- **No SVG code exists.** `Open` takes a `.curvyo` project only (`0001`, `0051`). ADR 0002 §10 fixes the strategy: a documented subset, golden files, a named and listed loss, gradients not in the subset (amended 2026-10-08). The customer's decisions of 2026-10-16 replace the "listed loss" (no report) and defer the passthrough bag (`adrs.md`).
- **The model has no per-node transform.** A group has none (`0023` criterion 25); a primitive stores a frame and a `rotation`; a path stores anchors; only a clone (`0049`) has a matrix. So every SVG transform is applied to the geometry on import.
- **A style is resolved per leaf** (ADR 0002 §5): fill none or one colour plus opacity, stroke on or off with width in mm, colour, opacity, dash (a list in multiples of the stroke width, no phase), join (miter limit fixed at 4), cap, and markers (`0017`, `0018`). Opacity of a node composes per paint, not as a group (`0050` Question 5, A). There is one fill rule, nonzero (`0054`).
- **Compound paths** hold open and closed outlines, touching or crossing (`0054`, built after `0050`). Holes are outlines of opposite direction (`0016`, `0035`).
- **Clones** (`0049`, `0057`): a clone stores its original and a matrix of any affine kind, draws the root original's style and opacity, does not scale its stroke by the matrix, may have its own placement and its own style (`0057`), and may have a negative determinant (`0056`).
- **Layers** are top-level groups with a `layer` marker, a name, `visible`, `locked` and `opacity` (`0050`). Groups nest to 32 levels (`0023`). Other nodes carry the same four registers.
- **Primitives:** rectangle (four corner radii, circular, `0013`), ellipse and circle, polygon and star (3 to 1024 points, inner ratio, first-vertex angle). Every primitive has a `rotation`. A stretch converts a rotated primitive to a path (`0047`, `0056`).
- **Page:** 1 to 100,000 mm per side (`0015`), a display unit mm, cm or in, a background colour with alpha or none (`0040`).
- **The File tab** holds New, Open…, Save, Save as…, Close, Quit and the version line; `0051` leaves "Export and Import of drawings" to this spec. There is no menu on Linux and Windows. Messages go to the canvas notice slot (transient notices of 3 s) or sit 4 px under the button that caused them (`docs/design-system.md`).
- **Crates:** pure logic lives in `*-core` crates that build for wasm, with no file access; a platform crate reads and writes files (`CLAUDE.md` §6, ADR 0011). Golden files live in the crate's `tests/fixtures/` (`CLAUDE.md` §5).

### C. The page, the units and the viewBox

15. Given the root `<svg>` with `width`, `height` and `viewBox`, then the page is width × height converted to millimetres (px 25.4/96, pt 25.4/72, pc 25.4/6, mm, cm, in, and em as 16 px, ex as 8 px; a number without a unit is px), and the viewBox maps to that rectangle by `preserveAspectRatio` (default `xMidYMid meet`). Examples: `width="210mm" height="297mm" viewBox="0 0 210 297"`: page 210 × 297 mm, one user unit is 1 mm, so `<rect x="10" y="20" width="30" height="40"/>` becomes a rectangle from (10, 20) to (40, 60). `width="2in" height="1in" viewBox="0 0 200 100"`: page 50.8 × 25.4 mm, one user unit is 0.254 mm, and `<rect x="100" width="100" height="100"/>` is from (25.4, 0) to (50.8, 25.4). For **Open** these rules give the page; for **Import SVG…** the project's page is not changed and they give only the scale from the file's units to millimetres. A viewBox that does not start at 0 (`viewBox="10 10 100 100"`) puts its top-left corner on the page's top-left corner.
16. Given a root with `width` and `height` but **no viewBox**, then one user unit is one CSS pixel (25.4/96 mm = 0.264583 mm; the SVG rule) (no message). Example: `width="210mm" height="297mm"` and `<rect width="100" height="50"/>`: page 210 × 297 mm, the rectangle is 26.4583 × 13.2292 mm. Nothing is guessed from the numbers' size.
17. Given a root with a viewBox but no usable `width` and `height` (missing, `auto`, or a percentage), then the page is the viewBox size read as pixels. Example: `viewBox="0 0 100 50"` only: page 26.4583 × 13.2292 mm, one user unit 0.264583 mm. Given a root with neither size nor viewBox, then the page is the drawing's bounding box from (0, 0) to its right and bottom edge (the stroke excluded), in millimetres, **rounded up to whole millimetres** (at least 1 mm), and nothing is moved: `<rect x="10" y="10" width="100" height="50"/>` gives a page of 30 × 16 mm with the rectangle at (2.6458, 2.6458), 26.4583 × 13.2292 mm. An empty drawing with no size gets the size of a new document (`0015`).
18. Given a viewBox whose aspect ratio differs from width : height, then the whole `preserveAspectRatio` is honoured (all nine alignments, `meet` and `slice`, and `none`) by applying the viewBox-to-viewport map to the geometry. Example: `width="100mm" height="100mm" viewBox="0 0 200 100"` (meet, centred): scale 0.5, and `<rect width="200" height="100"/>` is from (0, 25) to (100, 75); with `preserveAspectRatio="none"`: from (0, 0) to (100, 100). No clip is applied for `slice` (content outside the page is kept).
19. **Pixel size of known generators.** Given a file whose root has no viewBox or a viewBox together with pixel sizes, and which names its program, then: (a) a comment `Generator: Adobe Illustrator` or the namespace `http://ns.adobe.com/AdobeIllustrator/10.0/` makes px mean 1/72 inch, because Illustrator writes points as px; (b) `inkscape:version` below 0.92 on the root without a viewBox makes the user unit 1/90 inch, the legacy of Inkscape 0.91 and earlier. Both cases are silent: no message, no setting and no dialog (customer, 2026-10-16, PIXEL-SIZE A). All other files use 96 per inch. Test: an Illustrator-made fixture of 595.28 × 841.89 px gives 210 × 297 mm; the same numbers from another program give 157.50 × 222.75 mm.
20. Given the rest of the root: (a) a page side below 1 mm or above 100,000 mm is clamped to that range and the drawing is not scaled; (b) `sodipodi:namedview` with `inkscape:document-units` of `mm`, `cm` or `in` sets the display unit (`0015`), any other value leaves mm; (c) `pagecolor` with `inkscape:pageopacity` sets the document background (`0040`): the colour with that opacity, or none when the opacity is 0 or the attribute is missing; (d) several `inkscape:page` elements (Inkscape 1.2): the first sets the page size only when the root gives none, content of all pages is kept on the one page; (e) a nested `<svg>` element is a group with the viewBox map of criterion 18 applied and `x`, `y`, `width`, `height` honoured, its overflow clip ignored. Items (a) to (d) concern the page of **Open**; Import SVG… changes no page property.

### D. Shapes and paths

21. Given a `<path>`, then the whole path-data grammar of SVG 1.1 and 2 is read: M m L l H h V v C c S s Q q T t A a Z z, implicit repeats (extra coordinate pairs after M are lines, after C more curves), commas, spaces and none where unambiguous (`M10-5`, `1.5.5` is 1.5 and .5, `1e-3`, `.5`, `-.5`), exponents, and arc flags written without separators (`a1 1 0 00 5 5`). S and T use the reflected control point (or the start point after a different command). Q and T are raised to cubic Béziers exactly. A Z followed by a drawing command without M starts a new subpath at the start of the one just closed. The result for each command is a segment of the model (lines and cubic Béziers).
22. Given an arc `A`, then it is converted to cubic Béziers of at most 45° each, exactly as the SVG implementation notes (F.6) define the centre, with radii that are too small scaled up, a zero radius becoming a line, equal end points dropping the arc, and the four flag combinations choosing the four arcs. Every point of the result lies within 0.001 mm of the true arc for radii up to 100 mm. Example: `M 10 0 A 10 10 0 0 1 0 10` in a millimetre drawing is the quarter circle about (0, 0) from (10, 0) to (0, 10) (sweep 1 is clockwise on the screen); the points of the result are 10 ± 0.001 mm from (0, 0), and with the same flags `0 0` the arc bulges the other way. A rotated ellipse arc (`A 20 10 30 …`) is tested the same way against a computed ellipse.
23. Given path data with an error (a letter that is not a command, a number where a flag belongs, a missing coordinate), then the path is imported up to the last complete command before the error, as SVG says to render it. A path that is empty or has no complete command is skipped. Example: `M 10 10 L 20 20 L 30` gives an open path of two nodes.
24. Given a path with several subpaths, then they become **one compound path** (`0054` criterion 27): subpath order is outline order, a subpath with `Z` is closed and without it is open, touching and crossing subpaths are kept as written. A path with one subpath is an ordinary path. A subpath of one `M` and nothing else, or of `M` plus a zero-length `Z`, is skipped (`0054` criterion 27). Nodes are never merged, removed or re-ordered: a closed subpath whose last point equals its first and which has `Z` keeps both nodes as written (no clean-up is made on import; a "merge coincident end nodes" action is a later command).
25. Given the nodes of an imported path, then each gets a kind: with `sodipodi:nodetypes` on the element and the right number of letters, `c` is Corner, `z` Symmetric, `s` and `a` Asymmetric; without it (or with a wrong count), a node whose two handles are collinear and of equal length is Symmetric, collinear and unequal Asymmetric, everything else Corner (tolerance 1e-6 relative). The kind changes nothing about the drawn outline.
26. Given a `<rect>`, then it is a rectangle: `x`, `y`, `width`, `height`, and `rx`, `ry` (one missing takes the other's value; each clamped to half the side). `rx = ry` (within 1e-9 mm) becomes the same radius at all four corners; `rx ≠ ry` becomes a path with the elliptical corners as arcs (criterion 22), with no message. A `width` or `height` of 0 or below, or a missing one, skips the element. Percent and unit lengths follow criterion 15 (percent of the viewBox).
27. Given `<circle>` and `<ellipse>`, then they are an ellipse (a circle when rx = ry) with centre and radii; a radius of 0 or below skips the element. `<line>` is an open path of two nodes; `<polyline>` an open path; `<polygon>` a closed path (no polygon or star primitive is guessed from its points, criterion 29 and D4; the primitives come from our own data and Inkscape's star data only; architect, 2026-10-14: the guess contradicted criterion 29 and has no round trip, because the export never writes a `<polygon>`). A `points` list with an odd number of numbers drops the last number.
28. Given a `<path>` with `sodipodi:type="star"` (Inkscape's star and polygon tool) that carries `sodipodi:sides`, `sodipodi:r1`, `sodipodi:r2`, `sodipodi:arg1`, `sodipodi:cx`, `sodipodi:cy` and `inkscape:flatsided`, then it is a polygon (flat-sided) or star primitive with those numbers, **but only if** the drawn `d` equals the outline of that primitive within 1e-3 mm; if the maker edited the path since (the shape no longer matches), it is an ordinary path. `inkscape:rounded` or `inkscape:randomized` other than 0 make it an ordinary path. `sodipodi:type` `arc` and `spiral` are ordinary paths from `d` (*slice 1 and 2; slice 3 replaces this sentence by criteria 111 to 127: arcs become ellipse arcs, `0021` having been built (#153)*).
29. Given any other `<path>`, then no primitive is guessed from its geometry: a closed path that looks like a circle or a rectangle stays a path (the maker converts nothing, loses nothing, and the node data stays as drawn).
30. Given a coordinate, radius or length that is not a finite number or that lands beyond ±10,000,000 mm after all transforms, then the element is skipped. An element with a negative or zero `stroke-width` keeps its fill and has no stroke.

### E. Transforms

31. Given `transform` on any element, then every transform of the element and its ancestors, with the viewBox map, is composed in SVG order and **applied to the geometry** of each leaf; groups carry none (`0023`). The syntax of `matrix`, `translate`, `scale`, `rotate(a)` and `rotate(a cx cy)`, `skewX`, `skewY`, in any list with commas or spaces, is read. A transform that cannot be read is treated as the identity. A transform with determinant 0 (for example `scale(0)`) skips the element. Example (millimetre drawing): `<g transform="translate(100 50)"><path transform="rotate(90)" d="M10 0 L20 0"/></g>` is an open path whose nodes are (100, 60) and (100, 70) (rotate maps (x, y) to (−y, x) here).
32. Given a path, then anchors and handle vectors are transformed by the matrix (handles as vectors, anchors as points); the open or closed state, node order and node kinds stay; a mirror (negative determinant) keeps the order of the anchors (the direction on screen is mirrored; `0056` criterion 19).
33. Given a rectangle, ellipse, polygon or star and a transform, then the rules of `0056` criteria 18 to 22 are applied with the matrix as the signed map: a rotation, a uniform scale, a mirror and a translation (any mix) keep the primitive and set its `rotation` and frame (a mirrored rectangle permutes its corner radii to the same physical corners); a transform that stretches (unequal magnitudes) keeps an unrotated rectangle or ellipse as such when the axes stay aligned (a rectangle with radii becomes a path if the radii would be elliptical, criterion 26), and converts a rotated or skewed primitive, and every polygon and star under a stretch, to a path exactly. No entry is made for a conversion. Examples: `<rect width="20" height="10" transform="rotate(30)"/>` is a rectangle of 20 × 10 mm with `rotation` 30° and centre (6.1603, 9.3301); `<rect width="20" height="10" transform="skewX(30)"/>` is a closed path with nodes (0, 0), (20, 0), (25.7735, 10), (5.7735, 10); `<rect width="20" height="10" transform="scale(2 1)"/>` is a rectangle of 40 × 10 mm.
34. Given a stroke and a transform, then the stroke width is multiplied by √|det| (the geometric mean of the two scale factors, the rule of `0005` criterion 8); the dash list does not change, because it is in multiples of the width. Under a stretch or skew the width is thus the average of both directions.
35. Given nested elements with different viewBox maps, transforms and a layer transform (Inkscape stores a layer's offset as `transform="translate(…)"` on the layer), then the result is the same as applying the nested matrices to each leaf in one step; the order of the leaves and their styles are unchanged by the baking. Test: the nested-transform fixture compared with an independent computation of five points per leaf, within 1e-6 mm.

### F. Style

36. Given the sources of a style, then they apply in this order, the later wins: the presentation attribute, the matching simple rule of a `<style>` element (specificity: `#id` over `.class` over element name over `*`; same specificity: later in the file wins), the `style` attribute (`prop: value;`, comments, `!important` read as plain, property names in any case). Inherited properties (fill, stroke and its parts, fill-opacity, stroke-opacity, fill-rule, display-independent `visibility`) are resolved down the tree to each leaf; `opacity` and `display` are not inherited. A leaf's resulting style is stored whole on the leaf (ADR 0002 §5). `<style>` is supported for these selectors: element name, `.class`, `#id`, `*`, and comma lists of them (this is what Illustrator and Figma write); `type="text/css"` or none. A rule with a combinator, attribute selector or pseudo-class, and every `@` rule (`@import` is never followed) is skipped; `var()` and `calc()` values are ignored (the default applies).
37. Given colours, then these forms are read: `#rgb`, `#rrggbb`, `#rgba`, `#rrggbbaa`, `rgb()` and `rgba()` with numbers or percentages, `hsl()` and `hsla()`, the 148 CSS colour names, `transparent` (alpha 0), and `currentColor` (the `color` property, default black). The colour's alpha multiplies the paint opacity (criterion 39). An unreadable colour is ignored; the property then takes the value it would have without it (inherited or default).
38. Given a fill or stroke, then: `none` switches it off; a colour switches it on; `url(#id)` to a gradient is replaced by the colour in the middle of the gradient (the stops interpolated in sRGB at offset 0.5, each channel rounded to the nearest whole value, halves up: black to white gives `#808080`); to a pattern by `#808080`; `url(#id) red` with a missing target uses the fallback colour; a missing target without fallback is `none`; `url(file.svg#x)` is `none`. The default fill is black and the default stroke is none, as in SVG; when a stroke is off, the file's width, colour and caps are still stored when present, otherwise the application defaults.
39. Given opacity, then `fill-opacity` times the fill colour's alpha is the fill opacity, `stroke-opacity` times the stroke colour's alpha is the stroke opacity, and `opacity` on an element is the node's opacity register (`0050`), also on groups and layers. Example: `fill="rgba(255,0,0,0.5)" fill-opacity="0.5" opacity="0.8"` gives a red fill with opacity 0.25 on a node with opacity 0.8. A group or layer with opacity below 1 fades each object separately here (`0050` Question 5, A), so overlaps inside it may look different from the file.
40. Given the stroke parts, then `stroke-width` (any length unit; a percentage is a percentage of the viewBox diagonal divided by √2, as SVG says) becomes millimetres (criterion 34 for transforms); `stroke-linecap`: butt, round, square; `stroke-linejoin`: miter, round, bevel (`miter-clip` and `arcs` are read as miter); the miter limit is always 4 (`stroke-miterlimit` is not kept); SVG `marker-start`, `marker-mid`, `marker-end` and `marker` are not read.
41. Given `stroke-dasharray`, then each length becomes millimetres and is divided by the stroke width in millimetres, so the list is stored in multiples of the width (`0007` criterion 8). An odd count is kept as written (the renderer repeats it, `0017` criterion 32); `none`, an empty list, a list with a negative number, or a list that sums to 0 is solid (the last two are read as solid). Example: `stroke-width="0.5" stroke-dasharray="2 1"` in a millimetre drawing is the list `4 2`; `stroke-width="2" stroke-dasharray="6 4"` in a pixel drawing is `3 2`. A `stroke-dashoffset` is not kept.
42. Given `display:none` on an element or an ancestor, or `visibility:hidden` on a leaf, then the element is imported as **hidden** (`visible` false, `0050`), not dropped, so the maker finds it in the Layers tab; a hidden layer is a hidden layer. `visibility` is read on leaves only (a group has no such state here).
43. Given `fill-rule` and `clip-rule`, then `clip-rule` is ignored and `fill-rule` is handled by Part H. `paint-order`, `mix-blend-mode`, `isolation` and `vector-effect` are ignored.

### G. Structure: groups, layers, clones

44. Given `<g>`, `<a>` and `<switch>`, then `<g>` and `<a>` are groups and `<switch>` is its first child that passes (no `requiredFeatures` or `systemLanguage` test is made: the first child element); an empty group is not imported (`0023` criterion 14). A group keeps its `inkscape:label` as name (cleaned by `clean_name`), its `opacity` and its hidden state. Its `id` is not kept as a name. Order is z-order: document order, last on top. Groups nested deeper than 32 levels are merged into their parent from level 33 on.
45. Given a `<g inkscape:groupmode="layer">` that is a child of the root `<svg>`, then it is a **layer** (`0050`): `inkscape:label` is the name (else the `id`, else "Layer N"), `display:none` makes it hidden, `sodipodi:insensitive="true"` makes it locked, `opacity` is its opacity, and its transform is applied to its children. An empty layer is kept (it wins over criterion 44; lead, 2026-10-26); on Import SVG… the file's layers are groups (criterion 3), so an empty one is dropped like any empty group. Layers are listed in file order, first at the bottom. A layer inside a group or a layer inside a layer is a group. Loose elements at the root stay loose at the top level (`0050` decision 2).
46. Given an element with `sodipodi:insensitive="true"`, then it is locked, whether a layer or an object.
47. Given `<use>` (customer decision of 2026-10-16, USE-CLONE B), then it becomes a **linked clone** (`0049`) where it can, and an ordinary copy where it cannot. The same test decides the export direction (Later: export, criterion 59).
    - **(a) Linked clone.** The `use` becomes a clone of the object that its target was imported as, with no override (neither own placement nor own style, `0057`), when all of these hold: (i) the target is a `<path>` that was imported as a path or compound path, or is itself a `use` that became a clone (a primitive is not converted to a path behind the maker's back, so a `use` of a `<rect>`, `<circle>`, `<ellipse>` or an Inkscape star is a copy); (ii) the target is drawn in the file, so an object of the document exists for it (not inside `defs`, `symbol`, `clipPath`, `mask`, `pattern` or `marker`); (iii) the clone matrix M below is a **move, rotation or flip only**; (iv) the copy would not look different from the target: the `use` and its ancestors set no style property that the target leaves unset, compared after the cascade of criterion 36, and the `use` has no `opacity` below 1 (a clone shows its original's style and opacity, `0049` criterion 8); (v) the chain stays at most 8 clones deep (`0049` criterion 52); deeper uses are copies.
    - **What M is.** M = C_use · translate(x, y) · A_target⁻¹. C_use is the composed matrix of the `use` itself (its ancestors' transforms, the viewBox map and the `use`'s own `transform`) in millimetres; A_target is the composed matrix of the target's **ancestors** only. The target's own `transform` is already baked into the target's imported geometry and cancels. M is stored in SVG order (a, b, c, d, e, f) in document millimetres, as `0049` defines it, and applied to the target's geometry it gives exactly the geometry the copy would have had. M is stored as computed and never snapped to the ideal rotation.
    - **Move, rotation, flip.** The linear part is orthogonal: a² + b² = 1, c² + d² = 1 and a·c + b·d = 0, each within 1e-6; the determinant is then +1 (rotation) or −1 (flip, valid for a clone, `0056` and `0049` criterion 25); the translation (e, f) may be any value within ±1e7. *Why only these:* SVG scales a `use`'s stroke with its matrix and a clone's stroke is not scaled by M (`0049` criterion 9), so a scale or skew would draw a different stroke. A rotation, a flip and a translation draw the same picture either way, and the clone keeps following its original.
    - **(b) Otherwise an ordinary copy.** The referenced element is copied to the place of the `use`: the target's own style, the `use`'s transform composed with `x`/`y` as a translation, and the style properties set on the `use` and its ancestors inherited by the copy where the target does not set them (SVG's rule). The copy is an ordinary leaf with no link. This covers: a target that is a primitive, a group or a nested `<svg>`; a `<symbol>` (read as a group, its viewBox and `preserveAspectRatio` applied when the `use` has a `width` and `height`); a target inside `defs`; an M with scale or skew; a differing style or opacity; a chain deeper than 8; and every case when `0049` is not yet built.
    - **(c) Rest.** A `use` with `display:none` gives a hidden clone (or a hidden copy); a clone has its own visible and locked flags (`0050`). A `use` to another file or address is ignored; a reference cycle or a target that does not exist is skipped. The original may stand before or after the `use` in the file. The clone is placed in the z-order of the `use`, in the layer or group of the `use`.
    - **(d) Limits.** The expansion is limited to depth 16 and 100,000 copies per file; copies count toward the 5,000,000 path commands of criterion 69, a clone counts as one element and no path command; past the limit the remaining `use` elements are skipped.
    - **Examples** (millimetre drawing, `path1` is the square (0, 0) to (10, 10)). `<use href="#path1" x="30"/>`: a clone with M = (1, 0, 0, 1, 30, 0); the square from (30, 0) to (40, 10). `<use href="#path1" transform="rotate(90)"/>`: M = (0, 1, −1, 0, 0, 0), a clone from (−10, 0) to (0, 10) (rotate maps (x, y) to (−y, x), criterion 31). `<use href="#path1" transform="scale(-1 1)"/>`: a clone with M = (−1, 0, 0, 1, 0, 0), determinant −1, from (−10, 0) to (0, 10). `<use href="#path1" transform="scale(2)"/>`: a **copy** of 20 × 20 mm with the stroke doubled (criterion 34). When `path1` sits in `<g transform="translate(5 5)">` (so it is stored at (5, 5) to (15, 15)) and the `use` is `x="30"` at the root: M = translate(30, 0) · translate(−5, −5) = (1, 0, 0, 1, 25, −5), and the clone covers (30, 0) to (40, 10).
    - **Test.** The fixture `clones.svg` (criterion 75): an Inkscape Alt+D clone moved and one rotated by 30° are clones with the expected M, moving a node of the original through the document API moves both; a mirrored clone has determinant −1; a scaled clone and a clone of a rectangle are copies; a clone of a clone is a chain of depth 2 whose resolved outline equals the copy's within 1e-6 mm; a `use` that sets `fill` where its target sets none is a copy with that fill; a `symbol` with a `use` is a group of copies.
48. Given `defs`, `symbol`, `clipPath`, `mask`, `pattern`, `marker`, gradients, `filter` and `style`, then they are never drawn on their own; they are read only as far as a rule above uses them (a gradient for its middle colour, a style for its rules, a symbol through `use`). Their other uses are ignored without a message: a clip path, mask or filter is not applied and the object comes in unclipped, unmasked and unfiltered (customer, 2026-10-16, CLIP A); a pattern paint becomes mid grey (criterion 38); SVG markers are not drawn.
49. Given `<text>`, `<tspan>`, `<textPath>`, `<flowRoot>` and `<image>`, then they are not imported and no placeholder object is made (*slice 1; slice 2 replaces this sentence by criteria 78 to 105*). `<foreignObject>`, `<script>`, `<animate*>`, `<set>`, `<audio>`, `<video>`, `<canvas>` and `<iframe>` are ignored and never run. Elements and attributes of other namespaces are ignored (criterion 13). Text converted to paths in Inkscape is ordinary paths and imports as such.

### H. The even-odd fill rule (EVENODD A, decided 2026-10-16)

50. Given a path (or an inherited style) with `fill-rule: evenodd`, **a fill that is on**, only closed outlines, and outlines that **do not touch (`touching_outlines`, 0.001 mm, ADR 0002 §3), cross each other or cross themselves**, then the outlines are wound so that the nonzero fill of the compound path looks exactly as the even-odd fill did: an outline's depth is the number of other closed outlines of the same path that contain it; an outline of even depth gets the direction of the outermost outline that contains it (an outline of depth 0 keeps its written direction) and an outline of odd depth the opposite direction, so the winding sum is 0 or 1 everywhere; a reversal is the one of Combine (`0054`). A path with the fill off is not re-wound (nothing is painted; the written direction is kept). Nothing is shown. Example: `<path fill-rule="evenodd" d="M0 0H40V40H0Z M10 10H30V30H10Z"/>` (both squares written clockwise): after import the point (20, 20) is not filled and (5, 5) is, with the nonzero rule; with `fill-rule="nonzero"` the same data stays as written and (20, 20) is filled. Three nested squares: (5,5) filled, (15,15) not, (25,25) filled.
51. Given `evenodd`, a fill that is on, and outlines that cross each other, touch (within 0.001 mm), or cross themselves (a pentagram, two overlapping circles in one path), or a path that has an open outline with an area next to at least one other outline (even-odd fills an open outline closed by its straight line and XORs it with the rest, which no choice of windings reproduces, and reversing an open outline would change its cutting direction), then the outlines stay as written and the object is drawn with the nonzero rule, so overlaps may be filled that the file left open (no message). A path with one outline that does not cross itself is unaffected either way.

### K. Safety (untrusted files)

67. Given any SVG, then the importer is a pure function from bytes to a result; it opens no file, makes no network request, runs no script and follows no reference outside the document, whatever the file asks for (`<image href>`, `<use href>` to another file, `@import`, `xml-stylesheet`, DTD, `file:` and `http:` addresses): such references are ignored. The SVG is never inserted into the page or the DOM of the application, and no name from a file is shown as markup (`clean_name`, text nodes only). The app sends nothing anywhere because of an import or export (R-SYS-007). Test: the hostile fixtures with a network-denying test harness and a check that no fixture string appears unescaped in the page's output.
68. Given a DOCTYPE, then the external part (`PUBLIC … "…svg11.dtd"`) is never fetched and the DOCTYPE is accepted. Internal `<!ENTITY name "text">` declarations are accepted only when every one is a plain literal (no `SYSTEM`/`PUBLIC`, no `%`, no `&` or `<` in the value), at most 64 declarations of at most 256 bytes each, and the file holds at most 100,000 references to them; this is what Adobe Illustrator's older SVG exports declare (`ns_ai`, `ns_extend`, `ns_graphs`, … used in `xmlns:x="&ns_extend;"`), and refusing it would refuse real Illustrator files and hide criterion 19(a). Anything else refuses the file by criterion 6(b), so a billion-laughs or external-entity file cannot expand or read anything (architect, 2026-10-14, `adrs.md`). The five predefined entities and numeric character references are read.
69. Given limits, then: a file above 50 MiB is refused (criterion 6); XML nested deeper than 256 elements is refused as "not an SVG drawing"; more than 500,000 elements or 5,000,000 path commands stop the import at that point and keep everything read so far (no message); a single attribute above 16 MiB is skipped; a `stroke-dasharray` longer than 1,000 numbers is read as its first 1,000; `use` limits as in criterion 47. No limit is reached by any fixture except the hostile ones.
70. Given arbitrary bytes, then the importer neither panics nor runs longer than 5 s on a file within the limits. Test: (a) every Inkscape fixture and every hostile fixture truncated at 200 evenly spaced lengths and with 200 single bytes changed, each yields a refusal or a result in under 2 s, no panic; (b) a fuzz target with the fixtures as seed corpus runs for 60 s in the nightly job without a crash or timeout.

## Slice 2: text and images (customer request 2026-10-27)

**Goal.** An SVG with live text and embedded bitmaps opens or imports with the text as **editable Curvyo text objects** (`0074`, `0078`, `0079`, `0080`) and the bitmaps as **image objects** (`0058`), so the import topic is closed. Everything in slice 1 holds; criteria 13 and 49 give way to the criteria below for text and images. One branch, one PR (`story/svg-text-images`, stacked on `0058`'s branch). No new UI: the Import button, Ctrl+I, drop, Open… and the notices are those of slice 1 and `0058`.

**Principle (permit over refuse).** A text stays a text wherever the model can say what the file draws. What the model cannot say in one text object is split into several text objects that together look like the file (criterion 92); what has no counterpart at all (underline, small caps, …) is left out silently (criterion 97). Text is never converted to paths on import: the maker can always do that afterwards with Object to path, and it needs the font, which is the one thing the import cannot promise.

### Field reference: how other programs write and read SVG text

- **Inkscape 1.x writes** one `<text xml:space="preserve">` per text with `x`, `y` and a `style` holding `font-size` in user units (written `px`, so in a millimetre document `font-size:10.5833px` is 10.58 mm, 30 pt), `line-height:1.25`, `font-family`, `font-weight`, `font-style`, `font-stretch` and `-inkscape-font-specification` ("Source Sans 3 Bold"). Each line is a `<tspan sodipodi:role="line" x y>`; manual kerns (Alt+arrows) are `dx`/`dy` lists on a `tspan`, turned characters (Ctrl+[ and ]) a `rotate` list; a bold word is a `tspan` with its own style. Letter and word spacing are CSS `letter-spacing`/`word-spacing`; vertical text is `writing-mode:vertical-rl` (older: `tb-rl`) with `text-orientation`. Text on path is `<textPath xlink:href="#path1" startOffset="50%">`, usually with `text-anchor:middle`. Frame text is SVG 2 `shape-inside:url(#rect1)` (the rectangle in `defs`) or `inline-size` for a wrap width; Inkscape 0.48 to 0.92 wrote `<flowRoot>`/`<flowRegion>`/`<flowPara>`, which browsers do not draw at all.
- **Illustrator writes** `<text transform="matrix(1 0 0 1 72.5 100.2)" class="st1 st2">` with the font in a `<style>` class, often by its **PostScript name** (`font-family:'MyriadPro-Regular'`), lines as `<tspan x="0" y="14.4">`, tracking as `letter-spacing`, and kerned pairs as extra `tspan`s with their own `x`. Older exports wrap the drawing in `<switch>` behind a `<foreignObject requiredExtensions="&ns_ai;">`.
- **Inkscape reads** all of this back as editable text (flowed text as frame text) and substitutes a missing font silently. **LightBurn** asks makers to convert text to paths before export and does not import embedded fonts ([forum](https://forum.lightburnsoftware.com/t/importing-svg-text-objects/1621), [docs](https://docs.lightburnsoftware.com/2.1/GetStarted/CreatingAndImportingArtwork/)). **Embedded bitmaps** are `<image xlink:href="data:image/png;base64,…">` (Inkscape's default "embed"); "link" writes a file path.
- **What is better here.** (1) Live text from Inkscape and Illustrator comes in editable, with the face, weight, size, kerns, spacing, alignment, vertical mode and text on path it had; a cutter program makes the maker outline it first. (2) A missing font is visible: the text keeps the file's font name and shows the "Font missing" tag of `0074` instead of being silently swapped, so the maker installs the font or picks another before cutting. (3) Every letter lands where the file draws it (within 0.05 mm of Inkscape's own Object to Path), including Illustrator's per-tspan positions. (4) Embedded bitmaps come in as image objects ready for tracing (`0025`).

### N. Text: the object, the font and the size

78. Given a `<text>` element that holds at least one character after criterion 79, then it becomes **one text object** (`0074`; exceptions in criterion 92) at the z-order place of the element, in its layer or group (criteria 44, 45). The name is `inkscape:label` (cleaned by `clean_name`), else the default name of `0074` criterion 27; hidden, locked and opacity follow criteria 42, 46 and 39; fill and stroke (colour, opacity, width, dash, join, cap) are resolved by criteria 36 to 41 as for a path and stored as the text's style. A `<text>` with no character, a `font-size` of 0 or below, or one inside `defs`, `symbol` (except through `use`), `clipPath`, `mask`, `pattern` or `marker` gives nothing. A `<use>` of a text gives an ordinary copy (criterion 47 (b); a straight text has no linked clone, `0080` out of scope). An `<a>` inside a text is read as a `tspan`.
79. Given the characters of a text, then whitespace follows SVG: without `xml:space="preserve"` and without `white-space: pre`, `pre-wrap` or `break-spaces`, newlines are removed, tabs become spaces, runs of spaces become one, and leading and trailing spaces of the text are removed; with `xml:space="preserve"` every newline and tab becomes a space and all spaces are kept; with `white-space: pre` (Inkscape 1.x) a newline starts a new line (criterion 85) and spaces are kept. Control characters other than these are removed. Character references (`&#x2014;`) are read (criterion 68). `<tref>`, `<title>` and `<desc>` inside a text add nothing.
80. Given `font-family` (a comma list; quotes optional; the cascade of criterion 36, so a `<style>` class works), then the face is looked up in the font sources of `0074` in their order (Curvyo fonts, Included, This computer on the desktop): for each entry of the list in order, an entry matches a family whose family name (typographic family, else family) equals it ignoring case, or a single face whose **full name** or **PostScript name** equals it (Illustrator's `MyriadPro-Regular`); the first entry that matches wins. A full-name or PostScript-name match picks that face directly; a family match picks the face by criterion 81. The generic names map to the included families: `sans-serif`, `system-ui`, `monospace` and `fantasy` to Source Sans 3, `serif` to Source Serif 4, `cursive` to Great Vibes. No `font-family` at all means `sans-serif`. `-inkscape-font-specification` is not read (Inkscape also writes the CSS properties it stands for).
81. Given a matched family, then the face is chosen from its faces in the same block by the rules of `0078` (Terms): the requested **italic state** (`font-style: italic` or `oblique`; otherwise upright), then the requested **width** (`font-stretch`, the OS/2 width class; the nearest class, narrower first when the request is narrower than normal), then the **weight class** nearest to the requested `font-weight` (`normal` 400, `bold` 700, numbers 1 to 1000; `bolder` and `lighter` relative to the parent by the CSS table: bolder gives 400 below 350, 700 from 350 to 549, 900 from 550; lighter gives 100 below 550, 400 from 550 to 749, 700 from 750); on a tie the lighter face for a request of 500 or less, the heavier above (CSS Fonts 4). When the family has no face of the requested italic state, the closest face of the other state is used; **no bold or slant is synthesised** (`0078`). A family that exists but lacks the requested weight is **not** missing: the closest face is used silently. Test: `font-family:'Source Sans 3';font-weight:600` picks the Bold face (Semibold is not in the included set, 700 is nearer than 400); `font-weight:300;font-style:italic` picks Light Italic.
82. Given a `font-family` list whose named entries (not generic) all fail to match, then the text is a **missing-font text** (`0074` criterion 29): the reference keeps the first named entry as the family and the style name made from the requested weight and italic state ("Bold Italic", "Regular"), with no content hash (the reserved sentinel `MISSING_FACE_HASH`, 64 zeros, `adrs.md` note 2; accepted by the customer 2026-10-27); it is drawn in the substitute face with the tag "Font missing", and the Font button and the Missing block name it. A list with a named entry that is missing and a generic entry after it (`'Lobster', cursive`) is a missing-font text too: the maker should see that the file asked for Lobster. Installing the font (or adding it to the Curvyo folder) and reopening the project makes the text use it, as for any missing font (`0074` criterion 30). In the browser build (no system fonts) a file that names system fonts therefore comes in with "Font missing" tags; nothing is refused.
83. Given `font-size`, then **Size** (the height of the capital H, `0074` criterion 12) is the font size in millimetres times the H ratio of the chosen face (the measured H height of `0074` Terms divided by the units per em; for a missing font, of the substitute face). The font size in millimetres is the CSS value in user units (`px` and a bare number are one user unit; `pt` 4/3, `pc` 16, `in` 96, `cm` 96/2.54, `mm` 96/25.4 user units; `em` and `%` of the parent's font size, `ex` half of it; the keywords `xx-small` to `xx-large` 9, 10, 13, 16, 18, 24, 32 px, `larger` and `smaller` ×1.2 and ÷1.2; no value 16 px), times √|det| of the text's composed matrix (criterion 84), times the user unit's size in millimetres (criteria 15 to 19). Size is then clamped silently to 0.1 to 2,000 mm (`0074` criterion 12). Example (millimetre document, Inkscape's 30 pt text): `font-size:10.5833px` in Source Sans 3, whose measured H is 656 of 1,000 units (OS/2 states 660), gives Size 6.943 mm within 0.001 mm (corrected 2026-10-27, Proposal). Every other length of the text (spacing, kerns, line height, Distance) is converted the same way.
84. Given the composed matrix M of a text (its ancestors, the viewBox map and its own `transform`, criterion 31), then the uniform part s = √|det M| goes into the lengths (criterion 83) and the text's **own transform** (`0074` criterion 26) is M with its linear part divided by s, so a move or rotation gives a plain rotated text, a mirror a flipped text, and a skew or unequal scale a text with that transform kept and its Size as computed; the anchor is mapped by M. A determinant of 0 skips the text (criterion 31). Test: `<text transform="rotate(30)" …>` comes in with the rotation 30° and the Size of the same text without the transform; `transform="scale(2 1)"` gives a text whose Size is that of `scale(1.4142)` and whose transform stretches by √2 horizontally and 1/√2 vertically.

### O. Text: lines, positions, spacing, alignment

85. Given the lines of a text, then a new line starts at each `tspan` with `sodipodi:role="line"` (Inkscape), at each newline under `white-space: pre` (criterion 79), and at each character with an absolute `y` (horizontal text) or `x` (vertical text) that puts it on a different baseline from the line before it (Illustrator and most generators). **Line spacing** (`0079` criterion 10) is `line-height` times the font size (`line-height` as a number, a length or a percentage; `normal` or none: Auto); when the file gives `line-height` only on an ancestor, it is inherited as CSS says. A line whose baseline in the file is not where Line spacing puts it is moved there by a vertical kern on its first character (`0079` criterion 27: the line moves, the next line stays), so uneven gaps keep their look. A text of one line keeps the Line spacing the file gives, for when the maker adds lines. An empty line (`tspan sodipodi:role="line"` with no characters) is kept as an empty line.
86. Given `x`, `y`, `dx` and `dy` (single values or lists, one value per character in code points, on the `text` or any `tspan`; a nested element's values win for its characters; a shorter list leaves the rest to flow), then the **anchor** is the position of the first character of the first line, and every later absolute position or relative shift is expressed by **per-character kerns** (`0079` criteria 26 to 31, stored by ADR 0021): a horizontal kern equal to the distance between where the character would land after the text's shaping and spacing and where the file puts it, and a vertical kern likewise (`dy` down in the file is a negative vertical kern; both kerns are cumulative, as `dx` and `dy` are). The comparison uses the face the text is drawn with at import (for a missing font the substitute, so positions computed for a font the computer does not have may shift once it is installed). Result: **every character lands where SVG 1.1 places it**, within 0.01 mm of the computed position. Test: for each Inkscape fixture of criterion 107 (fonts from the Included block), Object to path of the imported text (`0074` criterion 22) matches the same text converted by Inkscape (Path > Object to Path) within 0.05 mm per node (the two shapers may round advances differently); for the hand-written fixtures, the glyph origins match the positions computed by hand from the font's advances within 0.01 mm.
87. Given `rotate` (a list of angles, one per character; the last value holds for the rest of the element's characters; absolute, not cumulative), then each angle becomes that character's **per-character rotation** (`0079` criterion 27b), turned the way the file draws it (SVG's positive angle is clockwise on screen) and normalised to −180° to 180°. SVG turns a glyph about its origin on the baseline and Curvyo about its cluster's centre (`0079` criterion 11), so the difference is corrected with a horizontal and vertical kern on that character and the opposite kerns on the next character of the line: the glyph lands where the file draws it within 0.01 mm. Test: "ABC" with `rotate="0 90 0"`: B is turned a quarter clockwise and its outline matches Inkscape's conversion within 0.05 mm; A and C are unchanged.
88. Given `letter-spacing` and `word-spacing` (a length, `em`, or `normal` = 0, on the text or inherited), then they become the text's **Letter spacing** and **Word spacing** (`0079` criteria 8 and 9) in millimetres by criterion 83. A value outside `0079`'s typed range is not clamped: the range's limit is the text's value and the rest is added as horizontal kerns on the characters, so the look is kept. Spacing set on a `tspan` only (not the whole text) is expressed as kerns on that tspan's characters (Illustrator's tracking of a word). `textLength` with `lengthAdjust="spacing"` (the default) adds the extra letter spacing that makes the line extent equal to `textLength`; with `spacingAndGlyphs` it does the same (the glyphs are not stretched; criterion 97).
89. Given `text-anchor` (`start`, `middle`, `end`; inherited), then it becomes the **alignment** (`0079` criterion 1): Left, Centre, Right, and the anchor's x is the anchor point of the first line, so every line of an Inkscape multi-line text with `text-anchor:middle` is centred on the same x as in the file. In a vertical text the same values mean top, middle and bottom (`0079` criterion 22). `text-align` is read only for flowed text (criterion 96), where `justify` gives Justify. `direction: rtl` and `unicode-bidi` are not read: the characters are shaped in the order they are written (bidi is out of scope in `0074`).
90. Given `dominant-baseline` or `alignment-baseline` (generators use them to centre labels) and `baseline-shift`, then the baseline is moved by a vertical kern on the first character of each affected line or run (and back after a run): `middle` moves the text down by half the face's x-height (OS/2 `sxHeight`, else 0.5 em), `central` down by half of ascender plus descender (descender negative), `hanging` down by 0.8 of the ascender, `text-top`/`text-before-edge` down by the ascender, `text-bottom`/`text-after-edge`/`ideographic` up by the descender's depth, `mathematical` down by half the ascender; `auto`, `alphabetic` and the rest none (ascender and descender from `hhea`, or OS/2 typo with USE_TYPO_METRICS, as `0074` criterion 4). `baseline-shift` as a length or percentage of the font size moves up by that amount; `super` and `sub` use the face's OS/2 superscript and subscript y offsets, else ⅓ of the font size up and ⅕ down. Test: `<text y="50" dominant-baseline="middle">x</text>` in Source Sans 3 has its x centred on y = 50 within 0.05 mm.
91. Given `writing-mode`, then `horizontal-tb`, `lr`, `lr-tb`, `rl` and `rl-tb` are Horizontal; `vertical-rl`, `tb-rl` and `tb` are **Vertical, right to left**; `vertical-lr` is **Vertical, left to right** (`0079` criterion 20). `text-orientation: mixed` is Auto, `upright` Upright, `sideways` and `sideways-right` Sideways; SVG 1.1 `glyph-orientation-vertical` `0` is Upright, `90` Sideways, `auto` Auto (`0079` criteria 22, 23). In a vertical text, `x` and `y` change roles for lines (criterion 85) and kerns (`0079` criterion 27).
92. Given a text that **one** text object cannot hold, then it becomes **several text objects in one group** named by the text's `inkscape:label` when it has one (cleaned as in criterion 78), else by the first 24 characters of the whole text (`0074` criterion 27) (Proposal, 2026-10-27: criterion 78's name rule holds for the group), together looking as the file draws it (criterion 86), each editable. A new text object starts (Frage 48, default A): (a) where a character's face, Size, fill, stroke, opacity, writing mode or glyph orientation differs from the one before it (a bold word, a coloured letter, a smaller date line); (b) where a kern of criteria 86 to 90 would fall outside `0079`'s kerning range (an Illustrator `tspan` placed far away, a word set in another column); (c) after 10,000 characters (`0074` criterion 31). Each new text object takes the alignment, Line spacing and the other text values of its first character and has its anchor where its first character lands; within a line the pieces follow each other as the file has them. A text that needs one object is never grouped. Test: "Hello **world**" (the second word a `tspan` with `font-weight:bold`) gives a group of two texts, "Hello " in Regular and "world" in Bold, whose outlines together match Inkscape's conversion within 0.05 mm.

### P. Text on path and flowed text

93. Given a `<textPath>` whose `href` (or `xlink:href`) points to a `<path>`, `<rect>`, `<circle>`, `<ellipse>`, `<line>`, `<polyline>` or `<polygon>` of the file, then its characters become a **text on path** (`0080`) on the object that element was imported as (the **carrier**). Its **Position** (the arc length of the text's middle, `0080` Terms) is `startOffset` (a length, or a percentage of the carrier's length; `pathLength` on the carrier scales a length) plus half the text's width for `text-anchor:start`, plus 0 for `middle`, minus half the width for `end`, so the letters lie where the file draws them; `side="right"` (SVG 2) is Side Below with Line Baseline and its Position is counted back from the carrier's end (SVG 2 runs such a text along the reversed carrier, so `startOffset` and the anchor are measured from the end: Position is the carrier's length minus the value above; lead decision 2026-10-27: the rule is that the letters lie where the file draws them), otherwise Side Above with Line Baseline; Distance is 0, and a `dy` or `baseline-shift` on the characters becomes vertical kerns along the carrier's normal (`0080` criterion 47). Carrier direction and start agree with SVG for every kind (a path from its first node, an ellipse from its rightmost point clockwise, a rectangle from the top edge after its corner, clockwise; `0080` Terms). Letters past the carrier's end, which SVG hides, are drawn on the extension (`0080` criterion 26). Test: "CURVYO" on a circle of radius 40 mm with `startOffset="75%"` and `text-anchor:middle` matches Inkscape's conversion within 0.05 mm.
94. **(Proposal) The carrier's role.** Given a carrier imported from a drawn element, then it **keeps the role the file gives it**: a carrier with a visible paint in the file (fill or stroke on, opacity above 0) stays a drawn object with its style, because the maker drew it to be seen or cut (a ring around a badge); a carrier with neither fill nor stroke becomes a **guide** (`0046`), drawn green and dashed and not output, because SVG drew nothing there; a hidden carrier becomes a guide and stays hidden. A carrier referenced from `defs`, or whose user space differs from the text's (SVG lays the text along the path in the text's coordinate system, so a text with its own `transform` follows a moved copy of the path), is made as a **new guide path** just below the text in z-order, in the text's group or layer, with the outline SVG uses; the drawn path, if any, stays as it is. Either way the text follows edits of its carrier (`0080` criterion 24) and Guide on or off is one press. *Why not always a guide (`0080` TOP-CARRIER-OUTPUT B):* that rule is right when the maker puts a text on a path in Curvyo; for an imported file it would silently take a drawn and cut ring out of the output.
95. Given the other cases of text on path, then: a `<text>` whose content mixes characters outside and inside a `textPath` gives a straight text for the outside characters and a text on path for the inside ones (criterion 92); several `textPath`s in one text give one text on path each; a `textPath` whose target is missing, is another file, is a `use`, a group or a text, gives a straight text at the text's `x`, `y` (`0080` criterion 35); a carrier that is a compound path uses its first outline (the rest of SVG's run across later subpaths continues on the extension, criterion 93); `method="stretch"` and `spacing="exact"` are read as their defaults (criterion 97); a vertical text on a path is laid out horizontally (`0080` criterion 48). A text on path with mixed styles gives several texts on the same carrier, each with its own Position (`0080` criterion 32).
96. **(Proposal) Flowed text becomes plain lines.** Given frame text, then it is imported as a straight text whose lines are broken as the file shows them, and the frame is not kept (Curvyo has no frame text; `0074` out of scope): (a) **Inkscape 1.x `shape-inside` or `inline-size`**: when the text holds positioned lines (`tspan`s with `x` and `y`, which Inkscape writes for SVG 1.1 readers), those are the lines by criterion 85; otherwise the content is broken as in (b) with the width of the `inline-size` or of the shape's box; the shape referenced by `shape-inside` is not drawn (it sits in `defs`) and `shape-padding` is subtracted from the width. (b) **`<flowRoot>`** (Inkscape 0.48 to 0.92): the first shape of its `flowRegion` gives a box; each `flowPara` or `flowDiv` starts a line (a `flowSpan` is a run, `flowBreak` is ignored); a paragraph wider than the box is broken at spaces greedily, by the shaped widths in the chosen face and size, a word wider than the box on a line of its own; the first baseline is the box's top plus the face's ascender at that size, and the next lines follow Line spacing; `text-align` start, center, end and justify give Left (anchor at the box's left), Centre (box middle), Right (box right) and Justify. Text that does not fit the box below is kept (nothing is cut). A `flowRoot` with no region or a region of zero width gives one line per paragraph at the region's top-left (or 0, 0). Test: a `flowRoot` of 60 mm width in Inkscape 0.92 (or hand-written to that layout) gives the same line breaks as Inkscape 1.x shows for that file.
97. Given text features with no counterpart in the model, then they are **left out silently** (criterion 13) and the rest of the text imports: `text-decoration` (underline, overline, line-through), `font-variant` (small caps and the rest), `font-feature-settings`, `font-variation-settings` (a variable font is used at its default instance, `0074` criterion 21), `font-kerning: none` and `kerning` (the font's kerning always applies), `lengthAdjust="spacingAndGlyphs"` beyond its spacing (criterion 88), `textPath` `method` and `spacing`, `direction` and `unicode-bidi`, `white-space` values that wrap without a frame, `paint-order` on text, SVG fonts (`<font>`, `<font-face>`, `@font-face`; nothing is fetched, criterion 67) and an embedded font in a data URI. `text-transform: uppercase`, `lowercase` and `capitalize` are **applied to the stored string** (the text reads as in the file and stays editable).
98. Given limits and safety, then: every string from the file (text content, font names) is stored and shown as plain text, never as markup (criterion 67); a font name longer than 128 characters is cut there; a file holds at most 1,000,000 text characters (the rest of the texts is skipped, no message), and each `<text>` counts as one element and each character as one path command toward criterion 69; per-character values (`x`, `y`, `dx`, `dy`, `rotate` lists) are read up to 10,000 numbers per attribute. Test: hostile fixtures with a 2,000,000-character text, 100,000 one-character texts, and 10,000 different font names import within criterion 70's bounds without a panic.
99. Given a `<switch>`, then its first child that SVG would draw is taken (criterion 44 already passes over a child with a non-empty `requiredExtensions`, so Illustrator's `<foreignObject requiredExtensions="&ns_ai;">` is skipped today). Slice 2 adds the missing tests: a child with `requiredFeatures` naming anything other than an SVG 1.1 feature string, or with a `systemLanguage` that names no English language tag (`en`, `en-…`), is passed over, and a bare `<foreignObject>` child (no `requiredExtensions`) is passed over too instead of being taken and yielding nothing. Test: the `switch` of `text_generators.svg` (criterion 107) pins both layouts: Illustrator's (`foreignObject` with `requiredExtensions` first) and a bare `foreignObject` first; each imports the group behind it with its shapes and its text.

### Q. Images

100. Given an `<image>` whose `href` (or `xlink:href`; SVG 2 `href` wins when both are present) is a **`data:` URI** (RFC 2397; base64 or percent-encoded; spaces and line breaks inside base64 are skipped), then the decoded bytes are identified **by their content**, as `0058` criterion 2 does (the MIME type in the URI is not trusted): PNG, JPEG and WebP become an **image object** (`0058`) by the rules of `0058` for colour, orientation, alpha and the working image (criteria 6 to 8, 18, 19). Any other content (GIF, BMP, SVG, TIFF, …) is ignored (criterion 103).
101. Given the frame of an image, then `x`, `y`, `width` and `height` (lengths by criterion 83's units; `auto` or missing `width`/`height` take the image's pixel size as user units, SVG 2; 0 or below skips it) give the **viewport**, and `preserveAspectRatio` places the picture in it: `none` fills it (the picture is stretched); the default `xMidYMid meet` and the other `meet` alignments give the largest frame of the picture's aspect inside the viewport, at the alignment; `slice` (Proposal) gives the smallest frame of the picture's aspect that covers the viewport, at the alignment, and **the whole picture shows**, also outside the viewport (an image has no crop, `0058` out of scope; `0067` clipping is later). The frame is then mapped by the composed matrix (criterion 31), so a rotated, skewed or mirrored image keeps exactly that map (`0058` criterion 32). The physical size comes from the file only: `0058`'s DPI rule (criterion 9), the fit to the document (criterion 10) and the clamp (criterion 12) do not apply. Test: a 200 × 100 px PNG in `<image width="50" height="50">` in a millimetre document: with the default it is 50 × 25 mm at y 12.5 to 37.5; with `none` 50 × 50 mm; with `xMinYMin slice` 100 × 50 mm from (0, 0).
102. Given the registers of an image, then `opacity`, hidden, locked and the name follow criteria 39, 42, 46 and 44 (`inkscape:label`, else the name "Image"); `image-rendering` is not read (the zoom quality of `0058` criterion 28 applies); `clip-path`, `mask` and `filter` on it are ignored (CLIP A, criterion 48); a `<use>` of an image gives an ordinary copy that shares the asset (an image has no linked clone, `0058` criterion 38); an image inside `defs`, `pattern`, `mask`, `clipPath` or `marker` is not drawn.
103. Given an `<image>` that cannot be brought in, then it is **ignored silently** (criterion 13) and nothing else changes: an `href` that is a file path or an address (Inkscape's "link" mode; nothing is ever read or fetched, criterion 67), a data URI of another type, a damaged or truncated picture (`0058` criteria 20 and 21: also a truncated JPEG is skipped here, since there is no notice to say it is incomplete), a picture over `0058`'s file or pixel ceiling (criterion 16), or one that would take the project over 512 MiB of assets (images are taken in document order until the limit). The notices of `0058` (reduced resolution, size, ceilings) are not shown for an SVG import (customer, 2026-10-16: no report); the reduction of the working image happens all the same.
104. Given the images of an import, then their bytes are stored as **assets** by `0058` criterion 23 (verbatim, content-addressed, stored once): the same bytes in several `<image>` elements, or bytes the project already holds, are one asset. The images and their assets are part of the **one** history step "Import SVG" (Undo removes them; the assets stay while the history holds them, `0058` criterion 25), or of the new project for Open. Redo does not decode the SVG again.
105. Given the 16 MiB limit for one attribute (criterion 69), then (product owner, 2026-10-27, Proposal) it **does not apply** to the `href`/`xlink:href` of an `<image>` whose value starts with `data:`: such a value is bounded only by the 50 MiB file limit (criterion 6), so a 30 MB scan embedded by Inkscape (40 MB as base64) still comes in. Its decoded bytes are then subject to `0058`'s ceilings (criterion 103). Every other attribute keeps the 16 MiB limit. The decoding is done without a second full copy of the base64 text where the parser allows it (peak memory for one image: at most the base64 text plus the decoded bytes plus `0058` criterion 19's decoder cap).

**Goal.** A maker moves a project to Inkscape, Ink/Stitch, LightBurn or a plain viewer without hand-fixing geometry (R-SYS-006): one **Export SVG…** button, four switches, no dialog of ours. One branch, one PR (`story/0024-svg-export`), built from the accepted plan `export-plan.md` (what existed, the gaps, the architecture). The numbers 4, 52 to 66, 71 and 72 are those of the original specification of 2026-10-14 to 2026-10-16, amended below where the customer's decisions of 2026-11-01 or the model since then change them; new criteria start at 128. There is no export report (customer, 2026-10-16): no catalogue of what was left out. The only counted notice is the one of criterion 148 for texts kept as text.

**Decided by the customer (2026-11-01).** SVG-PAGES A: one SVG with all pages as Inkscape pages, plus an **Active page only** option. SVG-TEXT A: live `<text>`, with a **Text as paths** option. SVG-MARKERS A: real SVG `<marker>` definitions plus `curvyo:markers` for the round trip. SVG-GUIDES B: guides in a hidden, locked layer "Guides" that comes back as guides. SVG-OPTIONS A: an inline row of switches under Export SVG… in the File tab, remembered per user, no dialog. One PR for everything (the plan's 4a/4b split is dropped).

**Field reference.** Inkscape 1.2+ writes pages as `<inkscape:page id x y width height inkscape:label>` children of `sodipodi:namedview` and keeps the first page as the root `viewBox`; Inkscape writes live text as `<text xml:space="preserve">` with `<tspan sodipodi:role="line">` per line (slice 2, field reference); LightBurn reads paths, shapes, strokes and images but not live text from a file, and asks makers to convert text to paths; Ink/Stitch reads stroke and fill attributes and needs closed or open paths, not live text. What we do better: pages, text, images, arcs, markers and guides arrive in Inkscape as the objects they are in Curvyo, and every option that a cutter program needs (Text as paths, Strokes as paths) is one switch away instead of a menu hunt in the receiving program.

4. Given the File tab, when the maker chooses **Export SVG…** (its own row below the button block, tooltip "Export SVG"; `ux-notes.md`, "SVG export"), then the OS save dialog opens (a download in the browser build) with the default name (the source's name if the project was opened from an SVG, else "<project file name without extension>.svg", else "Untitled.svg"). On success everything in scope (criteria 130 and 131) is written as criteria 52 to 61 and 128 to 157 say, the canvas notice slot says "Exported <file name>." (3 s; "Downloaded <file name>." in the browser build), and the project is unchanged: not dirty, same path and title, no history step. A cancelled dialog changes nothing. A failed write shows the existing error dialog pattern with the title "Can't export drawing" and the system's reason, and writes no partial file (the file is written whole or not at all). Exporting an empty document, or one with nothing in scope, writes a valid SVG with no drawing elements. The Import SVG… button is not in the File tab any more (the tool rail has Import); the export does not depend on it.

52. Given an export, then the file is UTF-8 XML, a single `<svg>` with `xmlns`, `xmlns:inkscape`, `xmlns:sodipodi` and `xmlns:curvyo="urn:curvyo:svg:1"`, `width` and `height` in millimetres ("210mm"), `viewBox="0 0 <w> <h>"` so one user unit is one millimetre, and `curvyo:format="1"` (the version of this SVG profile, independent of the application version). A `sodipodi:namedview` with `inkscape:document-units` of the display unit, `pagecolor` and `inkscape:pageopacity` of the background (opacity 0 when none) follows. The background is **not** written as a rectangle (it would become a cuttable object). Skeleton for an A4 document with one layer "Cut" holding a rectangle:

    ```xml
    <?xml version="1.0" encoding="UTF-8"?>
    <svg xmlns="http://www.w3.org/2000/svg" xmlns:inkscape="http://www.inkscape.org/namespaces/inkscape"
         xmlns:sodipodi="http://sodipodi.sourceforge.net/DTD/sodipodi-0.dtd" xmlns:curvyo="urn:curvyo:svg:1"
         width="210mm" height="297mm" viewBox="0 0 210 297" curvyo:format="1">
      <sodipodi:namedview id="namedview1" inkscape:document-units="mm" pagecolor="#ffffff" inkscape:pageopacity="0"/>
      <g id="layer1" inkscape:groupmode="layer" inkscape:label="Cut">
        <rect id="rect1" x="10" y="20" width="30" height="40" fill="none" stroke="#000000" stroke-width="0.25"/>
      </g>
    </svg>
    ```

    **Amended 2026-11-01 (SVG-PAGES A).** The skeleton is the file of a document with **one page**. The page is the document's first page, wherever it lies; the **export origin** is its top-left corner, so every coordinate in the file is the model coordinate minus the origin (a page moved to (200, 0) gives the same file as one at (0, 0)). Objects off the page (on the pasteboard) are written with their coordinates, negative or beyond `width`/`height`; nothing is clipped. A document with **several pages** is criterion 128, and the Active page only option is criterion 130. `xmlns:xlink="http://www.w3.org/1999/xlink"` is declared when the file has a `<use>`, an `<image>` or a `<textPath>` (criteria 59, 137, 134). The ids of `<marker>`, `<inkscape:page>` and `<text>` are numbered like the others of criterion 53. The background is written as `pagecolor` for every page alike.

53. Given the tree, then layers are written as `<g inkscape:groupmode="layer" inkscape:label="name">` at the top level in stacking order, hidden ones with `style="display:none"`, locked ones (layer or object) with `sodipodi:insensitive="true"`, opacity as `opacity`; groups as plain `<g>` with `inkscape:label` when named; loose top-level objects directly under the root; z-order is document order. Names are escaped as XML text (`&`, `<`, `>`, quotes) and written without control or bidirectional control characters. Ids are `layer1`, `g1`, `path1`, `rect1`, `ellipse1`, `circle1`, `polygon1`, `star1`, `compound1`, `use1` numbered per kind in document order; they are not the internal node ids and no identifier of the project leaks into the file. **Amended 2026-11-01:** kinds added are `text1`, `image1`, `marker1`, `page1`; an arc is `path1`; a sketch is `g1` (criterion 138). **Guides (SVG-GUIDES B)** are not written in their own layers or groups but in one hidden, locked layer "Guides" after all other layers (criterion 143); a layer or group that held only guides is not written (criterion 143). Layers are shared by all pages (`0059` criterion 11) and are written once. A layer that is empty in the model is written empty, as before, unless an option left everything of it out (criteria 130, 131).

54. Given a path, then it is written as `<path d="…">` in **absolute** coordinates in millimetres with `M`, `L`, `C` and `Z` only, one subpath per outline in outline order, nodes in stored order and direction (`0054` criterion 26: a compound path is one `<path>`, `Z` after closed outlines only). Numbers use a decimal point whatever the operating system's language, at most 6 decimals, no trailing zeros, no exponent, never `-0`, separated by one space (`M 10 20 C 11.5 20 13 21.2 14 22 Z` form; commands and their numbers are separated by spaces). `sodipodi:nodetypes` is written from the node kinds (Corner `c`, Symmetric `z`, Asymmetric `s`) so Inkscape keeps them. No transform is written on a path and no group has one.

55. Given a primitive, then a rectangle with one radius at all corners is `<rect x y width height rx ry>`, with `transform="rotate(deg cx cy)"` when it is rotated; an ellipse is `<ellipse>` (a circle `<circle>`), rotated the same way; a polygon or star is a `<path>` with `d` and the Inkscape star data (`sodipodi:type="star"`, `sodipodi:sides`, `sodipodi:r1`, `sodipodi:r2`, `sodipodi:arg1`, `sodipodi:arg2`, `sodipodi:cx`, `sodipodi:cy`, `inkscape:flatsided`, `inkscape:rounded="0"`, `inkscape:randomized="0"`) so it opens in Inkscape as an editable star; a rectangle with different radii at its corners is a `<path>` with `curvyo:kind="rectangle"` and the shadow data of criterion 57. Test: the exported star fixture is opened in Inkscape by hand (criterion 65) and edited with the star tool. **Amended 2026-11-01:** this holds for polygons and stars with Curve 0 % only; with a Curve above 0 % they are criterion 140; ellipse arcs (`0021`) are criterion 139. An ellipse with a rotation writes the `<ellipse>` with `transform="rotate(deg cx cy)"` and its `cx`, `cy`, `rx`, `ry` in the unrotated frame, as the rectangle.

56. Given a style, then it is written as presentation attributes (not a `style` attribute, which several cutter programs read less reliably): `fill` (`none` or `#rrggbb`), `fill-opacity` when below 1, `stroke`, `stroke-width` (mm), `stroke-opacity`, `stroke-linecap`, `stroke-linejoin`, `stroke-dasharray` (the list times the width, in mm, omitted when solid as in criterion 52's skeleton, lead 2026-11-01; zero values written as `0`), `fill-rule="nonzero"` on every filled leaf, `opacity` on a node below 1. Attribute order is fixed. A stroke that is off is written as `stroke="none"` and no other stroke attribute. Hidden, locked and names as criterion 53.

57. Given values that the standard attributes say less exactly than the model stores, then **shadow data** is added in the `curvyo:` namespace and only there: `curvyo:dash` (the dash list in multiples of the width, exactly), `curvyo:stroke-width` (exact mm), `curvyo:radii` (the four corner radii), `curvyo:kind` (`rectangle`, `ellipse`, `polygon`, `star` when the standard element cannot say it), `curvyo:frame` (a primitive's centre, size, rotation, first-vertex angle, inner ratio), `curvyo:markers` (start, middle, end, place, count), `curvyo:outlines` (the open or closed state of each outline of a compound path, when it cannot be told from `Z`). Names use `inkscape:label` and need no shadow data. On import, shadow data is used **only if** the standard SVG next to it still agrees (lengths within 1e-6 mm, each dash length times the width within 1e-6 mm, geometry of a primitive within 1e-3 mm); otherwise the standard SVG wins and the shadow value is dropped. **Amended 2026-11-01:** the list also holds `curvyo:size` and `curvyo:face` (a text's exact Size and face reference, criterion 132), `curvyo:guides` (the Guides layer, criterion 143), and the exact forms of `curvyo:markers` (criterion 141) and of `curvyo:frame` for a polygon or star with Curve (criterion 140). Attributes in `curvyo:` that are not in this list are ignored. **Number text:** lengths and coordinates in standard attributes have at most 6 decimals (criterion 54); every number in `curvyo:` data, and opacities, ratios and angles in any attribute, are written as the shortest decimal text that reads back to the same `f64` (Rust's `Display`, no exponent, never `-0`), so "exactly" in criterion 62 holds; angles in `curvyo:frame` are radians (architect, 2026-10-14).

58. Given a compound path, then the export meets `0054` criterion 26 and the import `0054` criterion 27 (as changed by Part H): same outlines, order, open or closed state, nodes and direction after a round trip, test with an open outline, a hole and a crossing pair.

59. Given a clone (`0049`), then it is written as a `<use>` (customer decision of 2026-10-16, USE-CLONE B): `<use id="use1" xlink:href="#path1" transform="matrix(a b c d e f)"/>` with `xmlns:xlink="http://www.w3.org/1999/xlink"` declared on the root (Inkscape 1.x writes the same; SVG 1.1 readers need `xlink:href`), when all of these hold: (i) the clone has **no override** (neither own placement nor own style, `0057`: its criterion 40 and `adrs.md` say a clone with any override is an ordinary path); (ii) its matrix M is a **move, rotation or flip only**, by the test of criterion 47 (orthogonal linear part within 1e-6, translation within ±1e7); (iii) its original is written in the file under an id (the original is a path or compound path written as `<path>`, or another clone written as `<use>` or as `<path>`) and is **not hidden** (a `display:none` target hides the `use` in SVG; a hidden master with visible clones is a normal state, `0049` decision 7, so it falls to the path rule); (iv) the clone is not an orphan (an orphan has no outline and is not written).
    - **What the matrix maps to.** The original is written in absolute millimetres and carries no transform (criterion 54), so the `use`'s `transform` is the clone's own matrix M in SVG order, with the six numbers in user units, which are millimetres (criterion 52). They are written as the shortest decimal text that reads back to the same `f64` (criterion 57), so the importer of criterion 47 gets M back exactly. For a chain, each clone's M is relative to **its own** original, as in the model: B → A → O is `<use id="use2" xlink:href="#use1" transform="M_B"/>` next to `<use id="use1" xlink:href="#path1" transform="M_A"/>`, and the composition is SVG's own.
    - **Style.** The `use` carries no style attribute (and no `opacity`): it shows its target, whose full style and opacity are written on the target (criterion 56), and a clone without override has exactly the root's style (`0049` criterion 8). Its name is `inkscape:label`, its hidden state `style="display:none"` and its lock `sodipodi:insensitive="true"` (criterion 53); the clone's own ancestors (layer, group) apply to it as to any object.
    - **Everything else is a path.** A clone that fails (i) to (iv) is written as an ordinary `<path>` with its resolved outline through the whole chain and its effective style, as `0049` criterion 41 and `0057` criterion 40 say. A clone that follows a clone written as a `<path>` still uses `<use>` when it passes the test, with its M relative to that path.
    - **Amended 2026-11-01 (SVG-MARKERS A, SVG-GUIDES B).** Markers (`0018`) are written as real `<marker>` definitions plus `curvyo:markers` (criterion 141), no longer only as `curvyo:markers`; the old note "other programs draw no arrows" is void. "Not hidden" in (iii) includes the ancestors: an original in the hidden Guides layer (criterion 143), or in a hidden layer or group, makes its clones paths. A clone whose original is left out by an option (criteria 130, 131) is a path. A linked text clone (`0080`) is never a `<use>` (criterion 134). Nothing is reported either way (customer, 2026-10-16: no report). What a hidden object means for a **machine** output is decided with the manufacturing view (R-MFG-005), not here.
    - *Test:* a document with a path P, a clone of P moved by (30, 0), a clone of P rotated 30° and flipped, a clone of that clone, a clone of P with a scale of 2, a clone with own style, a clone of a hidden path, and a clone with own placement: the first three are `<use>` with the expected matrices, the last four are `<path>`; the exported file imported by criterion 47 gives back clones with the same originals and matrices within 1e-9 for the first three.

60. Given the whole file, then it contains no absolute or relative file path of the maker, no user name, no time, no random number, no application version and no identifier of the project, only the drawing and the fixed text of this criterion's profile (**amended 2026-11-01** (Proposal): text content, font names, face hashes (content hashes of font files) and the bytes of embedded pictures are drawing content; a picture is written exactly as the project stores it, including whatever metadata that file holds, because re-encoding would change the maker's picture; an image's file name is not written, only the object's name); two exports of the same document are byte-identical (criterion 72).

### S. Pages and scope (SVG-PAGES A)

128. **Several pages are Inkscape pages.** Given a document with two or more pages (`0059`), when it is exported without options, then the root `width`, `height` and `viewBox` are the **first page** in list order (Inkscape reads the root as its first page; customer feedback on PR #242, 2026-11-01, replacing the earlier union of all pages), the **export origin** (criterion 52) is the top-left corner of that page, and `sodipodi:namedview` holds one `<inkscape:page id="page1" x y width height inkscape:label="<page name>"/>` per page in list order, with `x`, `y` relative to the origin (user units, millimetres; a page left of or above the first has negative values). A single page writes no `inkscape:page`. Example: page "Front" at (-50, 20) of 100 x 100 mm and page "Coaster" at (70, 20) of 100 x 50 mm give `width="100mm" height="100mm" viewBox="0 0 100 100"`, `<inkscape:page id="page1" x="0" y="0" width="100" height="100" inkscape:label="Front"/>`, `<inkscape:page id="page2" x="120" y="0" width="100" height="50" inkscape:label="Coaster"/>`, and a rectangle at model (-40, 30) of 10 x 10 mm is written `x="10" y="10"`. Objects lying on no page are written with their coordinates, unclipped. Page names are escaped like other names (criterion 53). The page grid and the rulers' origin are not written (criterion 145). A plain viewer sees one canvas (criterion 61).
129. **Open reads the pages back (Proposal).** Given an SVG with one or more `inkscape:page` elements, when it is opened (Open…, not the import that adds to a project), then the project has those pages in file order with their names (`inkscape:label`, else "Page N"), sizes and positions (relative positions kept, the first page at the origin of the file's coordinates) and the first page is active; the root size is then not used for the page size. An Import that adds to a project still puts all content on the one page as criterion 3 says and ignores `inkscape:page`. A file without `inkscape:page` behaves as before (criteria 14 to 19). This is the one change to the import in this slice; it is needed for criterion 150 and amends the "Multiple pages" line of the import's Out of scope. ### T. Text (SVG-TEXT A)

132. **Live text.** Given a text object (`0074`) and Text as paths off, when exporting, then it is one `<text id="text1" xml:space="preserve" inkscape:label="<name>">` at its place in the tree, with: `font-family` the face's family name (quoted `'…'` when it holds a space or a character that is not a letter, digit or hyphen; no generic fallback), `font-weight` the face's weight class as a number, `font-style` `italic` or `normal`, `font-stretch` as the CSS keyword of the width class (omitted for normal), `font-size` = Size divided by the face's H ratio (criterion 83 inverted) in millimetres with at most 6 decimals, `fill`, `fill-opacity`, `stroke` and the other stroke attributes by criterion 56, `opacity`, hidden and locked by criterion 53; the text's own transform (`0074` criterion 26) as `transform="matrix(a b c d e f)"` when it is not the identity, with all positions below in the text's own frame. 133. **Lines, alignment, spacing, kerns.** Given a text, then: (a) each line is one `<tspan sodipodi:role="line" x y>` whose `x`, `y` are the anchor of that line (the alignment anchor, criterion 89's inverse) and the baseline of the line as the canvas draws it, vertical kerns of its first character included (criterion 85's inverse); an empty line is an empty `tspan`; (b) `text-anchor` is `start`, `middle` or `end` for Left, Centre and Right, and for a vertical text top, middle, bottom (criterion 89); **Justify** is written as `start` with the justified spacing of each line as `dx` values on its spaces, so the look is kept and the text comes back as Left (**Proposal**); (c) Letter spacing and Word spacing are `letter-spacing` and `word-spacing` in millimetres, and Line spacing is `line-height` as a number (Line spacing divided by the font size; `normal` for Auto); (d) the writing mode is `writing-mode` (`horizontal-tb`, `vertical-rl`, `vertical-lr`) and `text-orientation` (`mixed`, `upright`, `sideways`) as criterion 91 inverted; (e) per-character horizontal and vertical kerns (`0079` criterion 26 to 31) are `dx` and `dy` lists on the line's `tspan` with one value per character (omitted when all are 0), and per-character rotations are a `rotate` list (SVG's clockwise positive), the pivot difference of criterion 87 corrected so each glyph lands where the canvas draws it within 0.01 mm; (f) every length in these attributes has at most 6 decimals (criterion 54). A **linked text clone** (`0080` criteria 37 to 42: several carriers, one source text) is written as an independent `<text>` with its own `textPath` and its own carrier, with the source's string and the style that `0057` resolves for it; it is never a `<use>`, and the link to the source is not kept (on import it is an ordinary text on path; **Proposal**). ## Slice 3: Inkscape shapes as primitives (customer request 2026-10-27)

Customer, 2026-10-27: import Inkscape's own objects as Curvyo primitives wherever we have the primitive; for spirals and 3D boxes "a group of paths is already great". Today (criteria 26 to 28) these shapes come in as ordinary paths that draw exactly right but lose their handles. Items marked **Proposal** are the product owner's and vetoable at the demo. Customer default rules apply: exact geometry first, keep primitives.

### Field reference (slice 3)

- **Inkscape** writes every shape tool object as a `<path>` with the true outline in `d` and the tool's numbers in `sodipodi:` / `inkscape:` attributes. Arc: `sodipodi:type="arc"`, `cx`, `cy`, `rx`, `ry`, `start`, `end` (radians, parametric angle, clockwise on screen from 3 o'clock, the same as `0021`), `open="true"` (0.92 and older: an open arc) and, since 1.0, `arc-type` = `slice`, `arc` or `chord`. A whole circle or ellipse is written as `<circle>` / `<ellipse>` (criterion 27) unless it came from the arc tool without angles. Star/polygon: `sodipodi:type="star"` (criterion 28) with `flatsided`, `sides`, `r1`, `r2`, `arg1`, `arg2`, `rounded` (a fraction of the side, can be negative), `randomized`. Spiral: `sodipodi:type="spiral"`, `cx`, `cy`, `expansion`, `revolution`, `radius`, `argument`, `t0`; `d` is a Bézier approximation. 3D box: `<g sodipodi:type="inkscape:box3d" inkscape:perspectiveID="#perspNNN">` with six `<path sodipodi:type="inkscape:box3dside" inkscape:box3dsidetype="…">` and a `inkscape:persp3d` in `defs`; Inkscape 1.x still draws it but marks the tool as legacy.
- **Ink/Stitch and LightBurn** read the `d`, not the tool numbers; LightBurn has no arc or star objects on import at all. Inkscape itself keeps the numbers only until the maker edits the nodes. We keep the primitive when `d` still matches and say nothing otherwise, which is what the maker expects from the picture.

### Acceptance criteria (slice 3)

111. Given any shape of this section, then the **drawn `d` wins**: the primitive is made from the `sodipodi:` numbers only if its outline (after the transform of criterion 114, as the document would draw it) and the outline of `d` lie within 0.001 mm of each other (every point of one within 0.001 mm of the other, checked on at least 16 points per segment, for coordinates up to 1,000 mm); otherwise the element is an ordinary path from `d` with no message. Attributes that are missing, unreadable, non-finite, out of the primitive's range (`0021`, polygon and star tools: sides, ratio) or contradict each other give the path, never a refusal. This replaces the "equals its outline" wording of criterion 28 for all shapes and keeps it as the rule.
112. Given `<path sodipodi:type="arc">` with `cx`, `cy`, `rx`, `ry` (greater than 0) and optional `start` (default 0) and `end` (default 2π) in radians, then it is an ellipse with the arc of `0021`: start and end converted to degrees, `end` increased by 2π while it is not greater than `start`; kind from `arc-type` (`slice` is pie, `arc` is arc, `chord` is chord); without `arc-type`, `open="true"` is arc and anything else pie. The ellipse has centre (`cx`, `cy`) and radii `rx`, `ry` (a circle when equal within 1e-9 mm). Example (millimetre drawing): `cx=50 cy=50 rx=20 ry=20 start=0 end=1.5708` with `arc-type="slice"` is a pie of 90° from (70, 50) clockwise on screen to (50, 70), and `arc-type="chord"` the same arc closed by a straight chord. Fill and stroke of an open arc follow `0021` criterion 4 (the fill is closed by a straight line, only the arc is stroked), which is also Inkscape's drawing.
113. Given `sodipodi:type="arc"` with no `start` and `end`, or a sweep equal to 2π within 0.1° (`0021`), then it is a whole ellipse (a circle when `rx = ry`), whatever `open` and `arc-type` say. Example: `cx=30 cy=20 rx=10 ry=5` and no angles is an ellipse of 20 × 10 mm centred at (30, 20).
114. Given a `transform` (own or inherited) on a shape of this section, then criterion 33 applies with the matrix as the signed map: a rotation, a uniform scale, a mirror and a translation keep the primitive (an arc keeps its kind; a mirror runs the arc the other way round and the angles are set so that the drawn outline is the same), a stretch keeps an aligned ellipse arc as such and converts a rotated or skewed one to a path exactly, and every polygon and star under a stretch is a path (criterion 33). Example: the quarter pie of criterion 112 with `transform="rotate(30)"` is an ellipse arc with `rotation` 30° and the same start and end angles.
115. Given a `<rect>` with `rx ≠ ry`, then it stays **a path with elliptical corners** exactly as criterion 26 says: `0013` has one circular radius per corner and no elliptical corner, so no rectangle primitive can hold it exactly, and the closest primitive (a rectangle with the mean radius) would change the cut line, which exact-geometry-first forbids. A rectangle with `rx = ry` (one missing takes the other's value) stays a rectangle. No elliptical corners are added to `0013` for this slice. Revisit if the customer asks for elliptical corners as a feature.
116. Given `sodipodi:type="star"` with `inkscape:flatsided="true"`, `sodipodi:sides` N (3 or more, within the polygon tool's range), `r1`, `arg1`, `cx`, `cy`, `rounded` 0 (or absent) and `randomized` 0 (or absent), then it is a **polygon** primitive with N sides, outer radius `r1`, centre (`cx`, `cy`) and the first vertex at angle `arg1` from the centre (radians, clockwise on screen from 3 o'clock; `r2` and `arg2` are ignored), Curve 0%. Example: `sides=6 r1=10 arg1=0 cx=0 cy=0` is a hexagon with vertices at (10, 0), (5, 8.6603), (−5, 8.6603), …. This is criterion 28 made explicit for polygons; criterion 28's check is criterion 111's.
117. Given `sodipodi:type="star"` with `flatsided` false or absent, `sides` N, `r1`, `r2`, `arg1`, `arg2`, `rounded` 0 and `randomized` 0, then it is a **star** primitive with N points, outer radius `r1`, ratio `r2 / r1` and the first outer vertex at `arg1`; a star whose `arg2` is not `arg1 + π/N` within 1e-6 rad (a twisted star, which the star primitive cannot hold) is a path. Example: `sides=5 r1=10 r2=4 arg1=−1.5708` is a five-pointed star with a point straight up on the screen.
118. Given `inkscape:rounded` other than 0 (a polygon or star) or `inkscape:randomized` other than 0, then the element is **an ordinary path from `d`**. Inkscape rounds a corner with a Bézier whose handle length is a fraction of the side; the Curve of `0021` (criterion 36) is a circular arc through the two vertices of a side, and the two outlines differ by more than 0.001 mm for any visible rounding, so the primitive cannot be exact (a randomized shape has no regular primitive at all). No Curve value is guessed from the path (criterion 29). Test: a star with `rounded=0.3` and one with `randomized=0.2` import as paths whose points equal the points of `d`.
119. Given `sodipodi:type="spiral"`, then it is **one ordinary path** from `d` (open, nodes and handles as drawn; node kinds by criterion 25), named by criterion 121. **Proposal:** no group is made, because an Inkscape spiral is one path, so a group of one path would be a layer of structure with nothing in it; the customer's "group of paths" is met by the box in criterion 120. `cx`, `cy`, `expansion`, `revolution`, `radius`, `argument` and `t0` are not kept: there is no spiral primitive and no Spiral tool.
120. Given `<g sodipodi:type="inkscape:box3d">`, then it is a **group of paths** (`0023`): one path per `box3dside` child (normally six), in the file's order, each with its own style (Inkscape styles the faces separately), each an ordinary path from its `d`; the group is named by criterion 121. The `inkscape:persp3d` in `defs`, `inkscape:perspectiveID`, `inkscape:corner0`, `inkscape:corner7` and `inkscape:box3dsidetype` are not kept, so the box is not a box any more when ungrouped or edited: no perspective, no box primitive (a box primitive with perspective handles is not worth building for a tool Inkscape itself calls legacy). Children that are not `box3dside` paths import like any group child (Part G).
121. Given the names of these objects (criterion 44's rule: `inkscape:label` first), then an object without a label is named after the Inkscape object: **"Arc"** for a path made into an ellipse arc, **"Spiral"** and **"3D box"** for the spiral and the box group; polygon, star and whole ellipse take the default names of the Curvyo primitive. A box face without a label is named "Face 1" to "Face 6" in file order. A label always wins.
122. Given a `transform` on a spiral, a box group or on a face, then it is applied to the geometry of each path (criteria 31 to 35); the group carries none (`0023`); stroke widths follow criterion 34.
123. Given the maker has edited the object in Inkscape (a node moved by node editing or an XML edit of `d`), then the `sodipodi:` numbers no longer match and criterion 111 gives the path. Inkscape itself drops `sodipodi:type` when nodes are edited, so this is mostly the case of a file edited by hand or by another program (a path effect on a star is an ordinary path from `d`, the effect result). Test: an arc whose `d` has one node moved by 0.002 mm is a path; moved by 0.0005 mm it is the arc.

Given hostile numbers (criterion 30): `sides` of 0, 1, 2, a fraction, or above the polygon tool's maximum, `r1` ≤ 0, `rx` ≤ 0 or `ry` ≤ 0, NaN or infinite values, a `start` or `end` beyond ±1e6, then the element is a path from `d` (criterion 111), or skipped if `d` itself is unusable (criterion 23, 30); nothing hangs or panics. ### Decided by the lead for slice 3 (2026-10-27, Proposal, vetoable at the demo)

- **S3-6 Ellipses and arcs are compared with the true curve** (criterion 111): the 0.001 mm rule measures an ellipse or arc primitive against the true ellipse, not against the four-cubic (or 22.5° piece) drawing the canvas uses. The primitive is exact; its drawing in cubics is a rendering detail.
- **S3-7 A pie whose `d` retraces an edge matches** (criterion 111): when `d` draws the same line as the pie but runs along one of its radii twice, it is the pie: the geometry is the same and the primitive is the cleaner object.
- **S3-8 What "within 0.001 mm" checks** (criterion 111, after the tester's finding that 16 samples per segment let gaps through): both outlines have the same number of subpaths, each open or closed alike (a subpath whose ends are within 0.002 mm counts as closed, because its missing closing line is then within 0.001 mm of its ends), and every point of each lies within 0.001 mm of the other. The distance is bounded exactly rather than sampled: both outlines are flattened within 1e-5 mm and the remaining margin is applied to the polylines, so a gap anywhere is found.
- **S3-9 Polygons and stars allow for the rounding of the written numbers** (criteria 111 and 117, 2026-10-27, after the customer's star from the star tool came in as a path): Inkscape writes every number with `numericprecision` significant digits (8 by default, as low as 6 when set so). At 6 digits `arg1` and `arg2` are each off by up to 5e-6 rad, so a plain star failed the 1e-6 rad twist test, and at coordinates of 100 mm and more `d` and the `sodipodi:` numbers are each off by up to 0.0005 mm, so it failed the 0.001 mm test. For a polygon or star the precision is read from its numbers (the most significant digits any of `cx`, `cy`, `r1`, `r2`, `arg1`, `arg2` shows, at least 6); the twist tolerance is 1e-6 rad or the rounding of `arg1` and `arg2`, whichever is larger, and the distance allowed is 0.001 mm plus how far that rounding can move the outline (a point of `d`, the centre, and an outer vertex by `r1` and `arg1`). At the default 8 digits this adds less than 0.0001 mm on an A4 page; a node moved by 0.01 mm or a twist of 0.001 rad still gives a path.
- **S3-10 A star whose `r2` is the larger radius** (criterion 117, 2026-10-27, after the customer's real Inkscape 1.4.4 file brought a 12-point star with `r1=14.290906 < r2=27.971268` in as a path): Inkscape lets `r2` exceed `r1`, and then the vertices at `r2`/`arg2` are the tips and those at `r1`/`arg1` the valleys. Such a star is the star primitive with outer radius `r2`, ratio `r1 / r2` and the first tip at `arg2`. A star is untwisted when `arg2` is `arg1 + π/N` modulo `2π/N` (the same vertices; `arg1 − π/N` is the usual case when `r2 > r1`). `r2 = r1` (within the rounding of the written numbers) draws a regular polygon of 2N corners and comes in as that **polygon** (2N up to 1024, else a path). The 0.001 mm check of `d` is unchanged.

Criteria 9 to 12 and 14 are removed.
- **BAG (A).** No passthrough bag in this slice. The bag is built only if Curvyo later adopts SVG as a native file format (open, edit, save). When an SVG is imported to be used as a composition, the other information (for example `inkstitch:` data) simply disappears. This amends the "kept per node" sentence of ADR 0002 §10 (`adrs.md`).
- **CLIP (A).** Clip paths are ignored.
- **PIXEL-SIZE (A).** 96 per inch, except Illustrator files (72) and Inkscape 0.91 or older without a viewBox (90), silently (criterion 19).
- **SVG-EXPORT-LATER (A).** The first slice is the import, placed on the centre of the view as a composition source, through the File tab "Import SVG…" and Open. SVG export moves to a later slice (section "Slice 4: export"); R-SYS-006 is met in two steps. Open-edit-save of SVG is not the focus ("import and then place where we want is enough"). The placement on the centre of the view (not the file's origin) is the PO's reading and may be overridden by the customer at the demo.

## Decided by the customer (2026-10-27)

- **Budget of criterion 71 (confirmed).** 3.0 s of thread CPU time for 20,000 paths with 400,000 nodes and 3.5 s for 5,000 groups of 4 (restated from the earlier 2.0 s and 2.5 s after measurement); 100 KB Inkscape file under 100 ms unchanged.
- **MISSING_FACE_HASH (accepted).** A text whose font is not found keeps the file's font name and style name and carries the reserved sentinel `MISSING_FACE_HASH` (64 zeros) instead of a content hash (criterion 82; `adrs.md` note 2; `plan.md`). The customer likes how missing fonts look (the substitute face and the "Font missing" tag of `0074`), so the sentinel stays.

## Decided by the lead (2026-10-26, Proposal)

Found by the tester; the customer may overrule them at the demo.

- **Empty layer (criteria 44 and 45).** An empty layer of the file is kept on Open; criterion 45 wins over criterion 44's "an empty group is not imported", which still holds for an empty `<g>`. On Import SVG… the file's layers become groups, so an empty one is dropped.
- **Selection after Import (criterion 3).** Hidden or locked top-level children of the new layer are not selected, as everywhere else (`0050`).
- **Undo of an Import (criterion 3).** Ctrl+Z restores the selection from before the import.

### Busy state (criterion 7)

Parsing runs on the main thread, so nothing can animate while it runs (the rule of `0058`).

- Before the work starts the app sets the busy flag, the cursor `wait` on the whole window and paints one frame (two `requestAnimationFrame` turns). When the file is **1 MiB or more** (known before the parse; about 150 ms at the 2 s per 12 MB budget) the canvas notice slot first shows "Opening poster.svg..." / "Importing poster.svg..." (`role="status"`, no time limit, replaced by the result). Smaller files show nothing: a flash of text is noise.
- While busy, canvas input, the File buttons, Undo and the chords are ignored (`aria-busy` on the app root). No Escape and no progress bar.
- The result appears in the frame the work ends: the document and the selection together, and the notice of criterion 8 when it applies.

### The only notice (criterion 8)

"Nothing in poster.svg could be imported." in the canvas notice slot, `role="status"`, 3 s, no focus. There is no banner and no persistent line, so the Document preview banner (`0042`) is never in conflict. After a successful import there is no message; the selected objects in view are the confirmation.

### Refusal dialogs (criterion 6)

The existing error dialog pattern (modal, `role="alertdialog"`, focus on **OK**, Escape closes), one sentence per case, each ending "Nothing was changed.". The title is "Can't open file" for Open… (the file may be neither a project nor an SVG) and "Can't import SVG" for Import SVG…; the text for Open and Import:

| Case | Text |
|---|---|
| (a) Open, content is neither | "This file is not a Curvyo project or an SVG drawing. Nothing was changed." |
| (a) Import, or Open of a file that starts with `<` | "This file is not an SVG drawing (line 3, column 14). Nothing was changed." (position only when the parser gives one) |
| (b) entities | "This file defines XML entities, which Curvyo does not read because they can be used to exhaust memory. Nothing was changed." |
| (c) size | "This file is larger than 50 MiB. Nothing was changed." |
| (d) encoding | "Only UTF-8 SVG files can be opened. Save the file as plain SVG. Nothing was changed." |
| (e) compressed | "Compressed SVG (.svgz) is not supported. Save the file as plain SVG. Nothing was changed." |

### Layers tab and the imported tree (criteria 44 to 46, 3)

- Names come through `clean_name` (128 characters); the Layers tab renders them as text with the usual ellipsis and a tooltip. Layers keep file order (first at the bottom, so the list shows the file's last layer on top); hidden layers show `EyeOff`, locked ones `Lock` with the dimmed name, as for layers made here. A layer without a label takes the `id`, else "Layer N"; an object without a label takes the default "Path 3f9a1c" (a file `id` is not a name, criterion 44). A clone shows as a clone (`0049`).
- **Import SVG…** makes one layer named after the file (cut at 128), the file's layers as groups inside it with `Group` glyphs; it is the active layer afterwards and its top-level children are selected. The History tab shows one step "Import SVG". A file with 10,000 objects is covered by `0050` criteria 48 to 52.
- **Open** leaves the active tab as `0051` criterion 14 says (Document or Style) and the Layers tab with the first layer active.
