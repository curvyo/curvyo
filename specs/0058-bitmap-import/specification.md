# Bitmap import: a PNG, JPEG or WebP as an object in the drawing

Status: Done (#207; UX notes 2026-10-15, Import trigger revised 2026-10-27; customer decisions of 2026-10-16 and 2026-10-27 applied; ADR 0017 accepted, spike done 2026-10-26). Leftovers: the "Original size" button (34) and the Image block in the Style tab (35) are Proposals and not built yet; they stay in the backlog.
Priority: Must (it is the prerequisite of the Must slice `0025-raster-trace`, R-VEC-001; on its own it is the reference image under a drawing)
Origin: Customer (request of 2026-10-14, translated: "For 0025 (tracing) bitmaps (bmp, jpeg, png, ...) must be importable first; we can't do that yet. I'd do it upstream."). The customer decided on 2026-10-16 (see "Decided by the customer"): formats PNG, JPEG, WebP (BMP and GIF dropped, TIFF only if easy), the image goes on top of the active layer, DPI rule, storage in the container, 512 MiB per project. Everything still marked **(Proposal)** is the product owner's and not accepted until the customer says so: several files at once (5), the "Original size" button (34), the Image block in the Style tab (35). The import of a truncated JPEG (21, JPEG-TRUNC) was confirmed by the customer on 2026-10-27.
Depends on: `0001` (project file, `assets/` in the container, ADR 0004 §1), `0050-layers-and-objects-panel` (images are nodes in layers; lock, eye, opacity, active layer), `0051-sidebar-and-no-menu` (the File tab), `0020-undo-redo` (one import = one step), `0019` and `0047` (group box and transforms), `0056` (flip). ## User value

As a maker I want to bring a PNG, JPEG or WebP into my drawing as an object, at a sensible size and in a place I can see, so that I can draw over it by hand, trace it with the Trace tool of `0025`, or use it as a faint reference under my cut lines.

As a maker I want a photo that is too big for my machine, or a file that is broken, to give me a clear result and a clear sentence and not a crash, a freeze or a silent nothing.

**Field reference (what the other tools do).**

- *Inkscape.* File > Import (Ctrl+I) and drag-and-drop; a dialog asks "embed or link", "image rendering mode" (smooth or blocky) and "DPI: from file or default"; the image is a `<image>` element with `x`, `y`, `width`, `height` and a `transform`. Size comes from the file's DPI, else a preference (96 dpi). Embedded images are base64 in the SVG, which makes large SVGs slow and big. A linked image breaks when the file moves. Its Trace Bitmap works on the selected image.
- *Illustrator.* File > Place with a Link or Embed check box; a placed image is a "linked file" with a Links panel; template layers are dimmed and locked images for tracing. Image Trace works on a selected placed image.
- *LightBurn.* File > Import (Ctrl+I) puts a bitmap in at the size of its DPI; an image has Image Settings (dither mode, passes) because the laser engraves it; Trace Image is on the selected bitmap. A bitmap is always embedded in the `.lbrn2` file.
- *Where we do better.* No dialog before the import: the image appears at a size computed from its own DPI, fitted to the document when it would be larger, with one sentence saying what was done and a button that undoes it. It is always embedded (one file, works on another computer and in the browser), and the same picture imported twice costs the file size once. A damaged or oversized file ends in a notice and an unchanged document, never in a half-made object. The pixels are never touched: the original bytes are kept in the project, so a later trace or engrave works from the full-resolution file.

## What exists today

Facts from the specs and ADRs (the code is not read for this draft; the architect confirms in `adrs.md`).

- **No image object.** The document model has paths, compound paths, rectangles, ellipses, polygons, stars, groups (`0023`), layers (`0050`) and clones (`0049`). ADR 0002 §10 lists "images" in the SVG subset it owns, but nothing models them. Adding the image node kind is a document-model change and takes the next `format_version` at merge (see the plan in `specs/README.md`); it needs a new ADR: [0017](../../docs/adr/0017-image-nodes-and-embedded-assets.md).
- **The container has a place for assets, not the code.** ADR 0004 §1 names `assets/` "for embedded bitmaps and fonts" in the zip. The code writes only `manifest.json`, `document.loro` and `document.json`, and `pack(&Document)` has no input for bytes; `unpack` ignores other members. This slice extends both (ADR 0017 §2). The workspace already depends on `zip` (deflate). No image decoder is a dependency yet (`png` and `sha2` are in the lock file only as transitive dependencies).
- **The File tab** (`0051`) holds New, Open…, Save, Save as…, Close, Quit; its criterion about future rows says each import and export "adds its rows to the File tab when it is specified". There is no menu bar.
- **Layers** (`0050`): new objects go to the active layer; the first object drawn into a document without a layer makes "Initial Layer" in the same step (criterion 35 there). Hidden and locked objects cannot be selected; opacity is a per-node register.
- **Customer rule (2026-10-14):** the right panel never grows sections for an operation; operations are tools or actions with a visible trigger; nothing appears out of nowhere. This is why the import is a File tab button and a key, not a panel, and why there is no import dialog.
- **`0024` svg-import-export is not written.** ADR 0002 §10 says images are part of the owned subset; the draft list in `specs/README.md` says an SVG `<image>` is a listed loss until someone models it. This spec models it; the requirements it places on `0024` are in "Coordination with `0024`".

## Terms

- **Image object:** a node of the document tree that shows one bitmap in a frame. It has a name, a position, a size, a rotation, may be flipped, scaled and skewed like any object, and is a leaf (not a container).
- **Asset:** the original bytes of the imported file, stored once in the project container under `assets/`. Content-addressed: the name is the hash of the bytes, so the same file imported twice is one asset.
- **Working image:** the decoded pixels the app draws and the Trace tool reads: 8 bits per channel, RGBA, sRGB assumed, orientation applied, at most the working limits of criterion 23. Derived from the asset; never stored in the document.
- **Natural size:** pixel width / DPI x 25.4 mm by pixel height / DPI x 25.4 mm, with the DPI of criterion 9.
- **Pixels per millimetre ("effective resolution")** of an object: pixel width divided by its current drawn width, shown as dpi (x 25.4).
- **View centre:** the centre of the visible canvas rectangle in document millimetres.
- Lengths in millimetres, tolerance 1e-6 mm for computed frames (earlier specs). Notice texts are at most 70 characters, `role="status"`, 3 s, in the canvas notice slot (as in `0056`), except where a criterion says otherwise.

## Acceptance criteria

### Part A: how an image is brought in

1. Given the tool rail (customer change of 2026-10-27; `docs/design-system.md`, row "Tool rail architecture"), then column A has a card of its own named "Import", 8 px under the Path tools card, with one 40 x 40 px button: Lucide `Import` at 20 px, accessible name **"Import"**, tooltip "Import (Ctrl+I)" ("Cmd+I" on macOS). It is an **action, not a tool**: a press opens the OS file picker (desktop) or the browser's file picker (browser build) at once, the active tool does not change, it has no `aria-pressed` and is never dimmed or hidden. The picker is filtered to "Drawings and images (*.svg, *.png, *.jpg, *.jpeg, *.webp)" with "All files" so a renamed file can still be tried. The File tab has **no** import button ("Import SVG…" of `0024` leaves it too); **Open…** still opens `.svg` as a project. A cancelled picker changes nothing, shows nothing and returns focus to the button.
2. Given a chosen file, when the picker returns, then the file is identified **by its content** (the first bytes), never by its extension or MIME type: a PNG named `photo.jpg` imports as a PNG; a text file named `x.png` is not an image (criterion 26). The import is **one commit** with the History name "Import image" (`0020`), it needs no further click, shows no dialog and no panel, and after it the new image object is **the selection** and the Select tool is active (the tool switches if another was active, as the SVG import of `0024` does; the Import button itself never becomes the active tool) and focus goes to the canvas. An SVG picked in the same picker is routed by its content to the SVG import of `0024` (its own commit "Import SVG"); a project file or anything else gets the notice of criterion 26. The canvas shows the object in the same frame as the commit.
3. Given the keyboard concept of `0010` (customer change of 2026-10-27), then **Ctrl+I** (Cmd+I on macOS) does what the Import button does, **only outside text edit mode**: with a text field, a chip or the on-canvas text editor open it stays italic (or whatever that field does), and during a drag it is ignored, like every chord. The key is listed in the shortcut table of `docs/design-system.md` in the PR. (Inkscape and LightBurn both use Ctrl+I.)
4. Given one or more files dragged from the file manager onto the canvas (customer change of 2026-10-27), when they are dropped, then each is routed by its content as the picker's files are: an image is imported by criterion 2 with its **centre at the drop point** (document millimetres under the pointer), an SVG by `0024` with its content centred on the drop point; the clamp of criterion 12 does not apply to a drop. While files hover over the canvas a plain 2 px dashed outline of the canvas shows (no text); over the panel, rail and rulers the drop effect is `none`. A drop of a `.curvyo` file or any other type shows the notice of criterion 26 and opens nothing.
5. (Proposal) Given a picker selection of several files (at most 20), then they are imported in the order the picker returns them as **one commit** named "Import images" (a single file: "Import image"; a batch that mixes SVG and images: "Import"), each placed by criteria 9 to 15 with the centre of the second and each further image moved 10 mm right and 10 mm down from the one before; all new objects are selected afterwards. More than 20 files import the first 20 and the notice reads "Imported 20 of 31 images. The rest were skipped." (46 characters with those numbers). A file in the list that fails does not stop the others; one notice per failed file is merged into "2 files could not be imported." with the first reason after it, and the successful ones are one commit.

### Part B: formats, colour and what is ignored

6. Given the formats (customer decision IMG-FORMATS, 2026-10-16), then the import accepts, by content: **PNG, JPEG (baseline and progressive) and WebP** (Must; WebP lossy, lossless and with alpha). An animated WebP imports its first frame and the notice reads "Animated image: only the first frame was used." (50). **TIFF is not supported**: it was Could, only if the pinned decoder supported it without an extra dependency or extra wasm size, and the spike of ADR 0017 (2026-10-26) found five more crates and +406 KB of wasm. **BMP and GIF are not supported** (dropped by the customer): like TIFF, AVIF, HEIC/HEIF, JPEG XL, ICO, PDF, SVG (`0024` imports SVG as vector, not as a bitmap), camera RAW and any other content, they import nothing and show the "unsupported format" notice of criterion 26. Test: the fixtures of the "Fixtures" list import or fail exactly as the list says; a BMP and a GIF are refused by their signature bytes, built in the test (no BMP or GIF fixture file exists).
7. Given the colour handling, then these rules are fixed and written in the user documentation:
   - **Colour space:** every pixel is taken as **sRGB**. Embedded ICC profiles (PNG `iCCP`, JPEG `APP2`, WebP `ICCP`), PNG `gAMA` and `cHRM`, and any other colour-management data are **read past and ignored**; nothing is converted. (Colour management is `0022`.) A photo in Adobe RGB or Display P3 therefore looks slightly flat, as in Inkscape without colour management; this is not announced.
   - **Bit depth:** 16-bit channels are reduced to 8 bits by taking the high byte after rounding (`(v + 128) / 257`); 1, 2, 4-bit and indexed images are expanded through their palette; grey and grey+alpha are expanded to RGB.
   - **Alpha:** an alpha channel (PNG RGBA, grey+alpha, `tRNS`, WebP alpha) is kept as **straight (non-premultiplied)** alpha 0 to 255 and drawn so that transparent areas show what is behind.
   - **JPEG CMYK/YCCK** (Adobe, inverted) is converted to RGB by the plain formula (R = 255 - min(255, C + K) without any profile); a decoder that cannot do it makes the file fail by criterion 26. Decided by the architect (ADR 0017 §4): no own conversion in this slice; the spike showed that the pinned decoder converts it, so the fixture is valid and expects RGB.
   - **Metadata is never interpreted** beyond what criteria 8 and 9 name: no text chunks, XMP, thumbnails, GPS, colour names, layers or paths of the file are shown or used.
8. Given a file with an orientation tag (EXIF `Orientation` 2 to 8 in a JPEG, a WebP `EXIF` chunk or a PNG `eXIf` chunk), then the working image is **rotated or mirrored upright** before anything else (size, trace and display all see the upright picture); value 1 or none: unchanged. The orientation is the one the pinned `image` decoder reports (`ImageDecoder::orientation`, applied with `DynamicImage::apply_orientation`); no own EXIF parser exists (ADR 0017 §4). Test: the fixture `jpeg_exif_orientation_6.jpg` (stored sideways, 40 x 20 px, a red marker in the stored top-left corner) shows as 20 x 40 px with the marker in the top-right corner; a table test covers 2 to 8 for JPEG and one case each for WebP and PNG.

### Part C: size, place and stacking

9. Given the physical size, then the **natural size** uses, in this order: a PNG `pHYs` chunk in pixels per metre (unit "metre"; unit "unknown" gives only an aspect ratio and is ignored for size); a JPEG JFIF density (units dpi or dots per cm); WebP has none. An EXIF `XResolution` is not read (the `image` crate hands out the EXIF block raw and a reader of our own is not worth it: camera EXIF usually says 72 dpi, which is not a print size); a JPEG with only EXIF density comes in at 96 dpi. The horizontal and vertical values are used separately, so a file with non-square pixels (150 x 300 dpi) comes in with the right aspect. A value below 10 or above 2,400 dpi, 0, or no value uses **96 dpi** on both axes (the SVG/CSS pixel; decision D2). Examples: a 3000 x 2000 px PNG with `pHYs` 11811 px/m (300.0 dpi) has the natural size 254.0 x 169.33 mm; an 800 x 600 px WebP with no density is 211.67 x 158.75 mm; a JPEG with JFIF 600 x 600 dpi of 6000 x 4000 px is 254.0 x 169.33 mm.
10. Given the natural size larger than the document in width or height, then the image is **uniformly scaled down so that it fits the document** (the largest scale at which both width and height are within the document, never above 1.0) and the notice reads "Scaled to 20 % to fit the document." (the percent is the factor rounded to a whole number, "Scaled to <10>% ..." for 10 %; 35 characters with two digits; the sentence "Original size restores it." joins it when criterion 34 is built, amended 2026-10-27). A smaller image is never enlarged. A document larger than the image and a picture that fits show no notice. Example: a 4000 x 3000 px JPEG with no density (natural 1058.33 x 793.75 mm) imported into an A4 portrait document (210 x 297 mm): factor min(210 / 1058.33, 297 / 793.75) = 0.19843, the object is 210.0 x 157.5 mm, the notice says 20 %.
11. Given a document of any size and an image, then the document size is **never changed** by an import (the customer's drawing area is theirs, `0015`); an image may lie partly or wholly outside the document edge after a drop or later moves (`0015` criterion on drawing outside).
12. Given the centre rule (non-drop), then the new image's centre is placed at the **view centre**, then moved by the smallest amount that puts the whole image inside the document rectangle if it fits there (after criterion 10 it always does when a fit was needed; an image that was not larger than the document fits by definition). If the view centre is outside the document, the clamp pulls the image back in. Example: an A4 landscape document (297 x 210 mm), view centre at (500, 100) mm, image 100 x 50 mm: the centre is clamped from x = 500 to x = 247 (297 - 100/2), y = 100 stays; the image covers x 197 to 297, y 75 to 125. Example 2: view centre at (150, 105) (inside), the image is placed with its centre there.
13. Given the layer rules of `0050`, then the new object is added to the **active layer** (if there is no layer yet, "Initial Layer" is made in the same step as `0050` criterion 35 says) and not to an entered group's parent unless a group is entered (`0023`: then to that group, as every new object).
14. Given the stacking (customer decision IMG-STACK, option B, 2026-10-16), then the image is inserted **on top of the active layer's children** (in front of everything already in that layer, as every new object is), is **not locked**, and is selected after the import. Several files of one import (criterion 5) stack in picker order, the last on top. The image object's name register is the file name without its folder (see criterion 22), and the Layers tab shows it with the kind glyph `Image`. An opaque photo therefore covers the drawing below it until the maker lowers its opacity, hides, locks or reorders it in the Layers tab (`0050`); no extra control is added for that.
15. Given an import into an empty document with no layer, then the result is one layer "Initial Layer" holding the image, the image selected, and one history step. Undo (`0020`) removes the object and the layer in that one step.

### Part D: limits and safety

16. Given the limits, then these constants are fixed (decision D5): **file size ceiling 100 MiB** (104,857,600 bytes); **header pixel ceiling 50,000,000 px** (width x height as the file header declares); **working limit 16,000,000 px with at most 8192 px on the long side**; (Proposal, architect, customer question 5) **assets of one project 512 MiB in total**. A constant is one named value in the code with a test, not scattered numbers.
17. Given a file over a ceiling, when it is picked, then **nothing is decoded** (the header is read first, the file's declared dimensions are checked before any pixel buffer is allocated) and nothing is imported; the notice reads "Image too large: 12,000 x 9,000 px. The limit is 50 megapixels." resp. "File too large: 140 MB. The limit is 100 MB." (both under 70 characters). A third refusal, with the total of a project: "Project too large: this image adds 140 MB. The limit is 512 MB." (63). These are the only cases where a valid image is not imported; it exists because a larger buffer can crash the browser tab, and the notice gives the number.
18. Given an image over the working limit but within the ceilings (for example a 5000 x 4000 px JPEG, 20,000,000 px), then it **is imported**, and the **working image** is scaled down by the factor `f = min(1, 8192 / max(w, h), sqrt(16,000,000 / (w * h)))` with the new size `floor(w * f) x floor(h * f)` (5000 x 4000 gives f = 0.894427, 4472 x 3577 px), using an **area-averaging (box) filter in integer arithmetic**, so equal input pixels give byte-identical output on every platform and in the browser (the input of a JPEG or lossy WebP may differ by 1 per channel between decoder code paths; PNG does not). The object's **physical size is unchanged** (the natural size comes from the original pixel size and DPI); its effective resolution shown is the working one. The asset still holds the **original bytes**. The notice reads "Shown and traced at reduced resolution (16 MP). Original is kept." (66).
19. Given the decoding, then the decoded size is checked **before any pixel buffer exists**: after the header ceiling of criterion 17, the decoder's own buffer size (`total_bytes()` in its own pixel layout, at most 8 bytes per pixel) plus the working image (4 bytes per working pixel) must not exceed a **decoder memory cap of decoder buffer + working image + 64 MiB** (spike correction 1 of ADR 0017: the pinned decoder does not enforce its own allocation limit on the path that reads the orientation). The full-size picture is never converted to RGBA8: the downscale of criterion 18 reads the decoder's own layout (grey, grey+alpha, RGB, RGBA, 8 or 16 bit) and writes the RGBA8 working image (spike correction 2), so a 50 Mpx JPEG peaks at about 150 MB + 64 MiB. Our own buffers are allocated fallibly; a failure to allocate, or a decoder error, ends the import as a failure by criterion 26 with the document unchanged. A panic cannot be caught on `wasm32-unknown-unknown` (it aborts the module), so the defences are the header checks of criterion 17, these limits and a time-boxed fuzz run (10 minutes per format, result in the PR description); a core crate has no clock, so "over **10 s** of CPU on the build host for any fixture of the budget (criterion 46)" is a test bound and not a runtime timeout. No import ever leaves a half-made object, an orphan asset or a changed History.
20. Given a file whose header declares dimensions that do not match its data (a PNG claiming 60,000 x 60,000 px with a 1 KB data stream, a "decompression bomb"), a truncated PNG or WebP (a truncated JPEG: criterion 21), a bad checksum, a zero width or height, an invalid palette index, or a nested or recursive structure (a JPEG with an endless marker chain, a WebP with an overflowing chunk size), then the import fails by criterion 26, **within 2 s and with at most 300 MiB of memory** on the build host (measured by the fixture test), without panic and without a hang. Amended 2026-10-27 (customer default): an invalid palette index may import, the index reading black as browsers show it; a chunk whose length claims more than the file holds is always refused. Test: each fixture of the "Damaged and hostile files" list.
21. (Decided by the customer, JPEG-TRUNC, 2026-10-27) Given a **truncated JPEG** (the file ends before its end-of-image marker, as after a broken transfer), then the part that decodes **is imported** (the pinned decoder fills the rest grey, as browsers show it) and the notice reads "photo.jpg is incomplete; the part that could be read was imported." (the name cut to 24 characters as in criterion 26; 66 characters with a 9-character name). A JPEG counts as truncated when no end-of-image marker (`FF D9`) follows its first start-of-scan marker. Every other damaged file is not imported (the whole file or nothing); partial recovery of PNG and WebP is in "Out of scope".
22. Given the file name, then it is shown and stored only as a display name: the folder part is cut off (both `/` and `\`), control characters and the characters `<` `>` `"` are removed, it is cut to 128 characters at a character boundary, and an empty result becomes "Image". The name is never opened, run or used as a path later.
23. Given the project file, then **the asset is stored once, verbatim**: the bytes of the imported file go into `assets/<hash>.<ext>` of the container (extension from the detected type: `png`, `jpg`, `webp`; the hash is the lowercase hex of a cryptographic hash named by the architect, 64 hex characters for SHA-256), not decoded and not re-encoded; the zip entry for an already-compressed type (PNG, JPEG, WebP) is **stored** (not deflated again). Importing the same bytes a second time, or duplicating the image object (Ctrl+D) or copy-paste inside the project, adds **no second asset**: the container grows by at most 1 KiB (the new object). Test: import a 2,000,000-byte PNG twice: the saved container is at most 2,000,000 + 64 KiB larger than one without the images, not 4 MB.
24. Given an import of an image of 10 MB or more (10,485,760 bytes), then the notice adds a second line "This image adds 24.0 MB to the project file." (the size is the file's size with one decimal, "MB" = 1,048,576 bytes). Below 10 MB there is no size notice. (Embedding is not optional, decision D3.)
25. Given a project with an image object whose last reference is deleted, when the maker wipes the document history (`0020`, `R-HIST-004`) and saves, then the container **no longer holds that asset**; with the history kept the asset stays because an undo or a history preview can bring the object back. Test: import, delete, save: the asset is in the file; wipe history, save: it is gone. Only the document wipe removes assets (ADR 0017 §2): an object wipe keeps the data (ADR 0014 Q4), and a save never scans the history, so a file may hold bytes that only history refers to until the next wipe.

### Part E: the failure notices

26. Given a file that cannot be imported, then the document is **exactly as before** (same snapshot, no history step, selection unchanged, no asset) and one notice shows in the canvas notice slot for 5 s (a failure is read, not glanced at). Texts: "This file type isn't supported. Use PNG, JPEG or WebP." (54); TIFF, BMP, GIF and every other unrecognised content get this text; "The image is damaged and could not be read." (43); "Image too large ..." (criterion 17); "Not enough memory to open this image." (37). The notice names the file when one file was chosen: the name (criterion 22) cut to 24 characters with an ellipsis is the first line, "photo-of-the-long-name…", and the reason the second. It never contains a path, a stack trace or the decoder's error text. The decoder's error is written to the log (`tracing`, debug) with the file name and size but not the bytes.

### Part F: how an image looks on the canvas

27. Given an image object, then it is drawn by `render-core` as a **textured quad** (the frame, rotated and skewed by the object's map) in its stacking position among the other objects, with **its effective opacity** (`0050` criteria 27 and 28: the object's own times its ancestors'), alpha-blended over what is behind, and **not drawn while hidden** (`0050`). The exported or drawn colour of a fully opaque pixel is exactly its stored sRGB value (no tone change; test: a 4 x 4 fixture at 1 : 1 gives back the pixel values within 1 per channel after the blend).
28. Given the zoom quality, then the texture is sampled **bilinear with mipmaps (trilinear)** when it is shrunk and **bilinear** when it is enlarged up to 8 screen pixels per image pixel, and **nearest** from 8 screen pixels per image pixel upward, so pixel art and a 1-bit scan show their grid when zoomed far in and nothing shimmers when zoomed out. Test (pixel readback of the canvas, as the renderer tests do): a 64 x 64 px fixture of a 1-pixel black and white checkerboard drawn at 8 screen pixels in total width has a centre pixel within 24 of mid-grey (128) and no pixel exactly 0 or 255 inside the image; the same fixture at 16 screen pixels per image pixel has each image pixel centre exactly black or white, with a hard edge (no blend at the pixel boundary).
29. Given an image rotated or skewed, then its edge is anti-aliased like the edge of a filled shape and its pixels are resampled as above (no nearest-neighbour stair-stepping at zoom 100 % for a rotation of 30°: the test compares against a reference rendering within a mean difference of 4 per channel).
30. Given the maker is zoomed so that the image is off the screen, then it is not drawn and costs no draw time; given a project just opened, then the **frame outline** of each image shows at once (the frame is in the document) and the pixels fill in as soon as the image is decoded (criterion 46); an image that is still decoding is drawn as its frame with a neutral hatch at 20 % opacity; a decode that fails on open (file damaged by hand after the save) draws the frame with a diagonal cross and the object stays selectable, movable and deletable, and the notice of the bad-asset case reads "An image in this project could not be read." once per open.

### Part G: select, move, scale, rotate, flip

31. Given an image object, then it is **hit** by a click anywhere inside its frame (its quad after rotation, skew and flip), **transparent pixels included**, so the hit area is predictable; it is one candidate in the click, marquee, lasso and Alt-click cycle of `0014` like every object; the topmost object under the pointer wins, so a shape drawn above the image is hit first; a locked or hidden image is never selected (`0050` criterion 14), and the cursor shows the lock over a locked image as for every locked object. The marquee selects the image if its true bounding box is selected by the rule `0014` states for objects.
32. Given a selected image, then the Select tool shows the same box and handles as for a rectangle, and **move, resize (corner, edge, Ctrl for proportions, Shift from the centre), rotate, skew, the typed move and size chips, the arrow-key nudge and Flip horizontally/vertically** all work as `0005`, `0008`, `0010`, `0019`, `0044`, `0047` and `0056` say for a rectangle, also in a selection with other objects. An image is **never converted to a path** by a stretch or skew; instead the frame is mapped (stretch and skew distort the picture, as in Inkscape). A flip mirrors the picture (the pixels are mirrored, `0056` criterion 23: "mirror the drawn result"). Scale stroke width and Scale corner radius do not apply to an image. After the gesture the drawn quad equals the original quad mapped by the gesture's map within 1e-6 mm at the corners. Test: a 100 x 50 mm image with its top-left pixel red, rotated by 90° clockwise about its centre (typed in the angle chip), has the red pixel at the top-right corner of the box.
33. Given the maker dragging a corner handle without Ctrl, then the image is **stretched freely**, as every object is; Ctrl keeps the proportions. This is deliberate consistency (decision D6); the Style tab block (criterion 34) shows the effective resolution so that a stretched photo is visible as 300 x 150 dpi, and "Original size" gives the picture its shape back.
34. (Proposal) Given a selection that holds at least one image, then the **Select bar** shows a kind group "Image" (the kind groups of the design system show only when the selection holds that kind) with one text button **"Original size"**. ### Part I: the hand-off to raster trace (`0025`, R-VEC-001)

42. Given a selected single image object, then the document read model exposes it for other slices as: the **working image** (width, height, RGBA8 pixels, row-major, top row first, premultiplication none), the **map from pixel coordinates to document millimetres** (the pixel (0, 0) top-left corner at the frame's top-left, pixel (w, h) at the bottom-right, including rotation, skew and flip), and the **asset hash**. A core function returns the working image given the asset bytes and nothing else (no file system, no clock; callers pass the bytes in), and builds for `wasm32-unknown-unknown`. Test: a 4 x 2 px fixture imported into a 40 x 20 mm frame, rotated 90° and flipped horizontally, gives for pixel (3, 1) the map position that the hand-computed affine gives within 1e-6 mm; two reads give identical pixels (determinism).
43. Given `0025`, then its Trace tool takes the **selected image** as its input (the maker selects the image, then starts the Trace tool, which is `0025`'s trigger and not part of this spec), and a traced path lands exactly over the pixels it came from by the map of criterion 42. The image is on top and selected right after the import (criteria 2 and 14), so the maker can start the Trace tool at once; nothing here depends on the image being the bottom object. This slice builds the data and the guarantee; it does not build the tool, the trace, or any button called Trace.

### Part J: file, history, budget

44. Given a project with images (a mix: a PNG with alpha, a JPEG, a WebP, one image rotated 30°, flipped and 50 % opaque, one in a group, one hidden, one locked, one duplicate sharing an asset), when the maker saves, closes and reopens it, then every object is as before: the same frame (to 1e-9 mm), name, opacity, visibility, lock, layer and stacking position, the working image is **pixel-identical** to the one before closing, and the container holds exactly one asset per distinct file (verbatim bytes, hash names). Given `0020`, then the import is one step ("Import image" / "Import images"), a move, resize, rotate, flip, "Original size" and delete of an image are one step each with their usual names, and Ctrl+Z brings back the exact previous state; undoing the import removes the object (the asset stays in the container as long as the history holds it, criterion 25); redo of the import brings the object back **without a second decode of the file from disk** (the asset is in the container). 46. ## Coordination with `0024` (svg-import-export, not written yet)

Requirements this spec places on `0024`, for the product owner of that spec to take over without a second round of questions:

- **SVG export:** an image object is written as `<image x y width height transform="matrix(...)" opacity="..." xlink:href="data:<mime>;base64,<asset bytes>"/>`: the asset's original bytes as a data URI (no re-encoding, no downscale), the frame and the map as the `transform`, the object's effective opacity as `opacity`, hidden objects as `display:none`, the name as `inkscape:label`. Round-trip through Inkscape keeps the picture and its place.
- **SVG import:** an `<image>` with a `data:` URI of a supported format and a plain `preserveAspectRatio` ("none" or the default) becomes an image object by this spec's rules, but with its size taken from `width`, `height` and `transform` of the SVG, not from the file's DPI. An `<image>` whose `href` is a file path or a URL is a **listed loss** (core crates do not read files or the network; the report names it) and the frame is not drawn. An unsupported data type is a listed loss too. A `preserveAspectRatio` with `slice` or `meet` is honoured by cropping or letterboxing the frame (the crop is not modelled: it is a listed loss, "image cropped by preserveAspectRatio", and the whole image shows).
- This slice does not write or read SVG. Until `0024` exists an image in a `.curvyo` project is saved and opened normally and appears in no other format.

## Out of scope

- **Trace itself**, its settings, preview and result paths (`0025`; R-VEC-002 to R-VEC-004), and any button called Trace.
- **Linking an image to a file on disk** ("link, don't embed"): see decision D3. A "Replace image" or "Edit in external editor" action, a "Links" panel and "Embed all" are part of it.
- **Clones of images** (`0049`): Linked clone is not offered (criterion 38). Duplicates share the asset.
- **Clipping and masks**, cropping an image to a rectangle or a shape (the frame is the whole image), a non-destructive crop, rounded corners.
- **Image editing:** brightness, contrast, gamma, threshold, dither, invert, grayscale, levels, blur, sharpen, "Image settings" for the laser. Dither and halftone belong to the engrave-as-raster slice.
- **Raster engrave output**, pass count, line interval, DPI of a job (a later slice of the laser line). This slice only keeps the data (criterion 41).
- **Colour management** (`0022`): ICC conversion, wide-gamut, CMYK profiles, 16-bit and HDR output.
- **BMP, GIF, AVIF, HEIC, JPEG XL, ICO, camera RAW, PDF, SVG-as-bitmap**: not imported (criterion 6; BMP and GIF dropped by the customer 2026-10-16). TIFF is out (criterion 6; ADR 0017 spike).
- **Animated images:** only the first frame of an animated WebP (criterion 6).
- **Clipboard paste of a bitmap** (Ctrl+V of a screenshot) and **screen capture / scanner / camera import**; both are plausible later requests, neither is asked for.
- **Partial recovery of a damaged PNG or WebP** (criterion 21; a truncated JPEG imports its readable part); **stripping metadata** from the asset (see the risk below).
- **Setting the DPI by hand at import**, a size dialog or an import options dialog (customer rule of 2026-10-14: nothing pops up; the typed size chip and "Original size" cover the cases).
- **Opening an image as a new document** ("File > Open" with a PNG): Open stays `.curvyo` only (`0051`).
- Text in images (OCR), vectorising at import, image-to-grid, a library of reference images, template/guide layers with their own look (the Layers tab's lock and opacity do this job).
- Collaboration and sync of assets (ADR 0004/0008/0009: a blob travelling to a peer, quota, sealing); this slice is local.
- The undo of a decoder **version change**: a later decoder upgrade may change a lossy JPEG decode by a few values per channel; the asset is the truth, the working image is derived (criterion 44 compares within the version).

**Risk to tell the customer (not a question):** the asset is stored **byte for byte**, so a photo's EXIF block, including GPS position and camera serial number, goes into the `.curvyo` file and into any copy of the project that is shared. The app never shows or uses it. A "Remove metadata" action or a strip at import would need a lossless JPEG/PNG rewriter; it is not in this slice and can be asked for.

## Decided by the product owner

Each is vetoable at the demo; none changes what the customer asked for (bitmaps importable as the base of `0025`; the formats were then fixed by the customer on 2026-10-16).

- **D1. Formats.** PNG, JPEG, WebP Must (customer, 2026-10-16: BMP and GIF dropped); TIFF Could, only if the pinned decoder supported it without extra dependency or size (it does not: out after the spike of 2026-10-26); everything else not supported with a notice. By content, never by extension.
- **D2. Default 96 dpi, DPI from the file, fit to the document, never enlarge.** 96 dpi is the SVG/CSS pixel, so an image and its later SVG round trip (`0024`) agree and a pasted web graphic has its familiar size. A photo is typically 72 to 300 dpi or none; the fit rule keeps a 4000 px photo from coming in 1 m wide, and "Original size" gives the other result in one click, so neither case needs a dialog (customer rule of 2026-10-14). Not a size dialog, not a preference (confirmed by the customer, IMG-DPI = A).
- **D3. Always embedded, never linked.** ADR 0004 §1 already decides the container holds `assets/` for embedded bitmaps; one file that opens on any computer and in the browser (no file system in core crates, the browser has no path) is the whole point of a `.curvyo` project. The price is file size, paid once per distinct file (content-addressed, criterion 23) and announced above 10 MB (criterion 24). Linking would break on a move, cannot work in the browser, and cannot be synchronised or encrypted (ADR 0008) without embedding anyway.
- **D4. Verbatim original plus a derived working image.** The bytes are never re-encoded (no generation loss, no encoder, a later trace or engrave can use the full file); the working image is rebuilt from them, deterministically. The alternative (store a downscaled PNG when over the limit) would make files larger than the JPEG they came from and lose the original.
- **D5. Limits 100 MiB, 50 Mpx ceiling, 16 Mpx / 8192 px working.** 16 Mpx RGBA is 64 MB (85 MB with mipmaps): five such images fit in a browser tab; 8192 is the limit of the working image, not of the texture: WebGL2 guarantees only 2048 and the renderer takes the adapter's limits, so on a smaller device the host skips the top mip levels (ADR 0017 §5); 50 Mpx RGBA (200 MB) is about the largest decoder buffer a wasm32 heap holds with room for the document (the browser's own limit is below 4 GiB). Above the working limit the maker gets a smaller working copy and a notice, not a refusal (the customer's principle); above the ceiling a refusal is unavoidable and the notice gives the numbers.
- **D6. An image behaves like every object in the transform bar.** Free stretch, Ctrl keeps proportions, skew and flip work. A different default (proportional for images only) would be the one place the handles behave differently. "Original size" is the safety net.
- **D7. Hit area is the whole frame, transparent pixels included.** Predictable, and fast (no pixel lookup). The image is on top (criterion 14), so objects below it are reached through the Alt-click cycle (`0014`) and the Layers tab; hiding, locking or sending the image to the back (`0050`) frees the clicks.
- **D8. No size dialog, no import options, no panel.** Per the customer rule of 2026-10-14. All adjustments after the fact: the size chip, the Select bar button, the Opacity field.
- **D9. Placed at the view centre, pulled into the document.** An import never leaves the maker looking for the image, and never enlarges the document.
- **D10. Colour: sRGB assumed, ICC ignored, 8 bit.** It is what the browser canvas does without colour management, what the first renderer needs, and `0022` can add profiles. Said in the user documentation, not in a notice.
- **D11. Candidate decoder crates, for the architect to evaluate (the product owner does not choose; licences from memory, to be confirmed by `cargo deny` and the crates' manifests):**

  | Crate | Formats | Licence | Note |
  |---|---|---|---|
  | `image` (umbrella, `default-features = false` and per-format features) | PNG, JPEG, WebP, TIFF and more | MIT OR Apache-2.0 | one API and limits (`Limits`); pulls the format crates below; most used; check the WASM build size |
  | `png` | PNG | MIT OR Apache-2.0 | decode and, if criterion 18 stays as designed, no encode is needed |
  | `zune-jpeg`, `zune-image` family | JPEG (baseline, progressive, CMYK in part), more | MIT OR Apache-2.0 OR Zlib | fast, pure Rust, `no_std` friendly; the `image` crate's JPEG decoder since 0.25 |
  | `jpeg-decoder` | JPEG | MIT OR Apache-2.0 | the older decoder; maintenance status to check |
  | `image-webp` | WebP (lossy, lossless, alpha, animation) | MIT OR Apache-2.0 | pure Rust |
      | `kamadak-exif` (`exif`) or the EXIF reader in `image` | EXIF orientation | BSD-2-Clause | not needed: `image` 0.25 reports the orientation itself (criterion 8; ADR 0017 §4) |
  | `fast_image_resize` | scaling | MIT OR Apache-2.0 | criterion 18 needs an integer, deterministic box filter; a 40-line own function may be simpler (KISS) |
  | `sha2` or `blake3` | asset hash | MIT OR Apache-2.0 (`sha2`); CC0-1.0 OR Apache-2.0 (`blake3`) | criterion 23 |

  **Architect's choice (ADR 0017 §4):** `image` 0.25.x pinned with `=`, features exactly `png`, `jpeg`, `webp` (+ `tiff` only if the spike shows it is free), plus `sha2` (SHA-256); no `kamadak-exif`, in a new crate `curvyo-image-core`; our own 40-line box filter instead of `fast_image_resize`. The project licence is AGPL-3.0-or-later (ADR 0006); all of the above are compatible. **Requirements on the choice:** pure Rust (no C library, no `unsafe` outside the crate), builds for `wasm32-unknown-unknown` without threads, supports a memory/dimension limit set before allocation, and has a fuzzing history. Whether the decoding lives in a new `-core` crate or in `document-core`, whether the asset bytes live in Loro or only in the container, and whether a new ADR is needed: architect.
- **D12. A failed file is a notice and a clean document**, not a partial object (criterion 21).

## Decided by the customer (2026-10-16 and 2026-10-27)

- **IMG-FORMATS:** PNG, JPEG and WebP are Must. TIFF only if easy (Could; criterion 6). BMP and GIF are dropped everywhere: criteria, fixtures, the hostile-file list and the decoder feature set.
- **IMG-STACK = B:** the imported image goes on top of the active layer, not locked, and is selected after the import (criterion 14).

### Busy state (criteria 2, 46)

Decoding runs on the main thread, so nothing can animate while it runs. What the maker sees:

- **Before the decode starts**, the app sets a busy flag, the cursor `wait` on the whole window, and paints one frame (two `requestAnimationFrame` turns) before it decodes. For a file of 5 MB or more, or a header of 8 megapixels or more (both known before any decode), the canvas notice slot first shows "Importing photo.jpg..." (name cut at 24 characters, `role="status"`, no time limit; the result notice replaces it). Smaller files show nothing: they finish in well under 150 ms and a flash of text would be noise.
- **While busy**, canvas input, the rail button, Ctrl+I, drop and Undo are ignored (Undo already is "during a long operation"). No Escape: the thread is blocked, so the notice does not promise a cancel. A batch yields one frame between files and shows "Importing 3 of 12 images..." (the count updates), still gated.
- **Worst case** is the 8 s budget of the 50 Mpx ceiling with a frozen window. This is acceptable only because it is rare and stated in the user documentation. If the architect moves the decode to a worker, the busy notice stays and Escape cancels the import (no change to the document); that is not specified here.

Subject line "Image", "3 images", or "N objects" (mixed). Then a 16 px muted line "Opacity is in the Layers tab." (the one pointer to where a reference image is faded). About 140 px with the subject line.
- **Values.** Name: the object's name ("3 images" for several). Pixels: "4000 x 3000 px", with a second muted line "Original 5000 x 4000" only when criterion 18 reduced it (the row is 24 px, 40 px with the second line; this is the only height change and happens only for a reduced image). Resolution: "254 dpi", "300 x 150 dpi" when the axes differ by more than 1 %. File: "2.4 MB, PNG, embedded". Several images: Pixels, Resolution and File show "Mixed" unless equal; File for several different files shows the total, "7.2 MB, 3 files". "Greyed when not applicable": a row whose value does not exist (an unreadable asset, criterion 30; a frame of zero width) shows "Unknown" in `--panel-muted-fg`, never an empty row.
- **Keyboard.** The block holds no control. Shift+Ctrl+F with only images selected focuses the block itself (`tabindex="-1"`, the panel's focus ring), so the shortcut does not fail for lack of a first control, and a screen reader reads its rows. Rows are a description list.

### Notices

All import notices go to the **canvas notice slot** (where the picture lands, and Ctrl+I and drop have no button to hang a notice under); this is the one exception to "a notice caused by a panel button stays under the button" and it is the spec's own choice (criterion 10). "Original size" and the refusal of a command keep their Action-notice place. Success `role="status"`, 3 s, or 5 s above 70 characters in total. Several notices of one import (criteria 10, 18, 24) are **one notice with up to three lines** in that order, each line at most 70 characters, so the slot never stacks. A success import with no notice announces "Imported photo.jpg." in the hidden polite region.

### On the canvas and in the Layers tab (criteria 14, 27 to 32, 36, 41)

- **Selection and handles.** The dashed `--accent` box with its casing and the rectangle's handles; the hover box `--hover-box` follows the quad, so the hit area (the whole frame, transparent pixels included) is visible before the press. The casing keeps the dashed line readable over a blue photo; the UX review checks it on a saturated image. Locked image: the padlock cursor as for any locked object. Nothing is drawn around an unselected image.
- **Pending and failed (criterion 30).** Frame outline 1 px `--toolbar-icon` at 60 % with the casing; pending adds the 45-degree hatch of `--mixed-hatch` at 20 %; failed adds a 1 px diagonal cross in the outline colour. Shape, not colour, tells them apart. Transparent pixels show what is behind (no checkerboard: a checkerboard means a transparent colour in a swatch).
- **Zoom.** The switch to hard pixels at 8 screen pixels per image pixel is instant and has no control; no readout.
- **Layers row.** Lucide `Image` 16 px as kind glyph; name = file name. No thumbnail in this slice: a 28 px row cannot show one legibly, shapes tell kinds apart, and a thumbnail needs a second texture readback; revisit after use. Tooltip: whole name, then the muted line "Image, 4000 x 3000 px. Not sent to the machine." (criterion 41; the line is rewritten when raster engrave ships, and says nothing about hidden or locked nodes). Accessible name "photo.jpg, image, 4000 by 3000 pixels, opacity 50 percent". The image has no alt-text field: the canvas is not an accessibility tree, the name and these rows are what a reader gets.
- **Node tool.** With an image selected, the Node bar slot shows the text-only pill "Images have no nodes." (the pattern for clones and compounds); a click on an image selects nothing and posts nothing.

### Differences from the criteria (for the PO and the customer)

1. Criterion 1: "directly under Open..." becomes "a row under Close" (no cell under Open...).
2. Criterion 36: "nothing shows" gets the Node-bar pill above, so the bar is not blank.
3. Criterion 37: the refusal text gets " Nothing was changed." (the convention of every refusal), 60 characters; criterion 47's string test uses the longer text.
4. Select bar: the two stroke and corner switches are hidden for an image-only selection (criterion 32 says they do not apply; this is the `0049` precedent).
5. Criterion 14 (customer decision of 2026-10-16): the image is on top, not at the bottom. An opaque photo covers the drawing, so the pointer line "Opacity is in the Layers tab." of the Style tab block matters more; no new control is added (the Layers tab has eye, lock, opacity and the order commands).
6. New small texts not in the criteria: "Importing photo.jpg...", "Importing 3 of 12 images...", "Opacity is in the Layers tab.", "Images have no nodes.", and the Layers tooltip line "Not sent to the machine." All vetoable.
