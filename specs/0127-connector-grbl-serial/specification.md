# Connector speaks GRBL over USB serial: the first real laser

Status: Done (PR #386)
Priority: Should
Origin: Customer (the machine connector, request of 2026-10-17; CONN-FIRST A: the first connector speaks GRBL over serial; Frage 222 CONN-ORDER answered A on 2026-11-18: after Send to machine comes the real laser). This is slice 4 of `0064` (order in `specs/0064-machine-connector/adrs.md`, "slice order for the rest of 0064"). Everything marked **(Proposal)** is the product owner's and vetoable at the demo.

## User value

As a maker with a GRBL laser on a USB cable I want to start `curvyo-connector-server` on the computer next to it, press Send to machine on my laser page, press Start in the Connector row and watch my own design run on the real laser, with Pause, Resume and Stop that really stop the beam, so that a Curvyo job cuts on my machine without a second program (`R-MFG-LASER-002`, `R-MFG-LASER-003`, `R-MFG-011`).

**What other tools do.** LightBurn, LaserGRBL and Universal G-code Sender stream G-code to GRBL over serial with the character-counting protocol, poll `?`, and show state and position. LaserGRBL and UGS show GRBL's own error and alarm numbers. Pain points we answer: a name with `!` in a comment header pauses the machine (GRBL reads `!`, `~`, `?` anywhere in the byte stream, comments included; G5), a cable pulled mid-job leaves the program guessing (G15), Stop that only stops sending and leaves the laser lit (G12). **We do better:** the connector checks the job before the first byte reaches the controller, never lets the stream overflow GRBL's buffer, and treats "laser off" as part of every stop, alarm and loss.

**One-line meaning (Proposal; builds on `0125`):** *Start* now means the connector streams the held job's lines to a real controller over the serial port; nothing else about Send, Ready, Start, Pause, Resume and Stop changes for the maker. The Connector row and the Output group look as before and gain a Controller line (G2, G19).

## What changes in the demo

- `curvyo-connector-server --serial /dev/ttyUSB0 --baud 115200` (instead of `--fake-controller`) opens the laser's port, identifies GRBL and says so on its terminal and in the app: the Connector row's Controller line reads for example "GRBL 1.1h on /dev/ttyUSB0, 115200 baud, laser mode on, S max 1000" (G2, G19). `--fake-controller` still works and still moves nothing.
- **Send to machine** (`0125`) on a laser page, then **Start** in the Connector row: the laser runs the page's own job. Progress, position, **Pause**, **Resume** and **Stop** follow the real machine (G4, G8, G10 to G12); an alarm or a failed line shows in words (G7, G13).
- A cable pulled mid-job shows "Lost the controller at line 120" and never "Running" (G15); after plugging in again the connector finds the machine, and the job is not resumed on its own.
- Without a laser at hand: `cargo run -p curvyo-connector-io --example grbl_pty` starts a GRBL simulator on a pseudo-terminal and prints its path; `curvyo-connector-server --serial <that path>` runs against it exactly as against a laser (G22).
- Try it on the real laser (customer check, G24): start with an empty bed or paper, low power and the lid shut.
- **Alarm at power-up** (GRBL locked, homing on): the Connector row shows "Alarm: Locked, not homed" and an **Unlock** symbol button next to it; pressing it sends `$X` through the connector, the alarm clears when GRBL reports Idle, from any paired app, with nobody at the connector's computer (G14, G33).
- **Laser mode off** (`$32=0`): Send to machine is refused with "Laser mode is off ($32=0)"; no job is held and nothing reaches the laser (G19, G34).
- The project file does not change. Frame, Home, jog and focus are not here (`0118`).

## Design principle (customer, 2026-11-18)

The connector is usually a systemd service and should not have to be operated: **no new behaviour may need a person at the connector's terminal.** Everything a maker does on the machine is done from the app. Existing exceptions, unchanged in this slice: `--require-local-start` (Enter on the terminal, `0064`) and the pairing code printed at start (read from the journal when it runs as a service). Frage 242 (CONN-LOCALSTART-SERVICE) asks how the first one gets a service-friendly way; the systemd unit file is a follow-up (own slice with Frage 242 A).

## Boundary (Proposal)

- **In:** the connector's serial transport and GRBL streaming (flags, identify, status polling, flow control, pause, resume, stop, alarm, loss handling, read-only settings), the `Controller` trait with its second implementation (see below), the Controller line and the failure and alarm words in the existing Connector row and state line, a GRBL simulator for tests, golden transcripts.
- **The `Controller` trait.** Slice 2 left the fake controller a plain struct "until the second controller" (`0064` Q20, `CLAUDE.md` §5). This slice adds the second implementation, so the trait arrives here with exactly two implementations: `FakeController` and `GrblController`. The architect (ADR 0035 (Consequences) left "the GRBL streaming state machine and where its pure part lives" to this story) decides the trait's shape and the module split in the addendum to `specs/0064-machine-connector/adrs.md`; the seam already exists as core's `ControllerCommand` and `Event`.
- **Reuses, does not change:** the protocol messages and states (protocol stays 0; additive fields only, G19 and G7, each with a golden file), pairing, TLS, the job assembly and its checks, local start, `jobs.log`, `Send to machine`, `0118` stays out.
- **Serial crate and operating-system support are the architect's decision** (permissive licence, `cargo deny` green, listed in the PR). Linux is the platform of this slice (`0064` criterion 1); Windows and macOS are not tested here and are said so in the PR.
- **No new crate** (`-io` and `-server` of slice 2 grow), no `format_version` change.

## Acceptance criteria

Prefix `G`, so that the criteria of `0064` (`P`, `Q`), `0125` (`S`) and `0029` keep their numbers. "Simulator" is the GRBL simulator of G22; "line" means a line of the job text as in `0064` (a final line without a newline counts).

*Start, identify, reconnect*

- G1. Given `curvyo-connector-server --serial <port> [--baud <n>]`, then the connector uses that port; `--baud` defaults to 115200 and accepts 1 to 4,000,000 (the range of the profile field, `0026`); `--serial` with `--fake-controller`, or `--baud` without `--serial`, or a baud outside the range is a usage error (exit code 2, message names the flags); without either flag the state is `NoController` as in slice 2; `--help` lists both; every other flag (`--listen`, `--state-dir`, `--require-local-start`, `--pair`, `--list-clients`, `--revoke`) behaves as before (`0064` A11).
- G2. Given the port opens, then the connector sends a soft reset (`0x18`) so that GRBL prints its banner whatever state it was in, reads the banner, then `$I` and `$$`, and reports `Welcome.controller` with name "GRBL" and the firmware version (for example "1.1h") from the banner or `$I`, and the state `Idle` (or `Alarm` with GRBL's own state, G14). Given no GRBL banner within 5 s, or bytes that are not a GRBL banner, then the state is `NoController` and the app reads "No GRBL answer on <port>"; the connector retries (G3). The connector prints on its terminal what it did and, when it could not open the port, why (not found, permission denied, in use). Tested with the simulator, a silent port and a port that prints other text.
- G3. Given the port is absent at start, closes later, or GRBL does not answer, then the state is `NoController` and the connector retries to open and identify every 2 s (period injected in tests) until it works; it never exits for a missing port. Every successful open is a fresh identify (G2). Given a job was held, Ready or running when the controller was lost, then it is gone after the reconnect: it is never started or resumed by the reconnect (G15).
- G17. Given any open of the port, then the soft reset of G2 is the first thing sent, so the machine is in a known state and the laser is off whatever an earlier connector process left behind; a reset that GRBL answers with an alarm is shown as the alarm (G14), not hidden.

*Status and position*

- G4. Given an identified controller, then the connector polls GRBL with `?` (a real-time byte, not counted against the buffer, G6): 5 times a second while `Running`, `Paused` or `Alarm`, once a second otherwise; the answers feed `Status` through the existing limiter (at most 5 pushes a second, `0064` P20). GRBL's `Idle`, `Run`, `Hold`, `Alarm` map to the states of `0064`; any other GRBL state (`Door`, `Check`, `Home`, `Sleep`, `Jog`) is shown as the word GRBL gave ("Controller state: Door") and never as `Running` for a job the connector is not streaming. In `Door`, `Check` or `Sleep` a `SubmitJob` is refused as `Busy`, and a `Start` ends the job `Done { Failed }` with the state's words before any byte is sent (architect review, Proposal). `Status.position` carries the **work position** in millimetres (the coordinates the job uses; machine position minus GRBL's work coordinate offset), also when GRBL reports machine coordinates; `null` until the first answer. Tested with simulator reports in both coordinate modes.

*Streaming*

- G5. Given `Start`, then before the first byte of the job is written, the connector prepares every line and checks all of them: it removes comments (`( ... )` and from `;` to the end), spaces and the carriage return, sends only lines that are not empty after that (an empty or comment-only line counts as a line, is acknowledged at once and never sent), and **never writes a line that contains `?`, `!` or `~` after the comment removal** (GRBL acts on them anywhere in the byte stream). The exact rule (Proposal): `?`, `!` and `~` inside a comment are harmless because the comment is removed first (a page named `Hello!` is fine); one that is left in a prepared line, outside any comment, fails the **whole job** before the first byte, like every other check here, with "Failed at line <n>: Contains !, ~ or ?" (no attempt to strip or escape it). A prepared line longer than 79 characters, a line that would write a machine setting (`$<n>=<value>`, `$RST`, `$N`), or one that unlocks (`$X`) ends the job as `Done { Failed }` at that line with nothing sent and a text that names the line and the cause in the form of the UX notes section 5 ("Failed at line 12: Longer than 79 characters", "Failed at line 4: Changes a machine setting", "Failed at line 4: Unlocks the machine"); `$H` is allowed (the job of `0029` can start with it, G9). Tested: a page named `Hello! ~?` (its header comment holds all three) runs to the end with no pause (the `0125` S7 job).
- G6. Given streaming, then the connector counts characters: it sends the next prepared line, with its newline, only while the bytes written and not yet acknowledged (`ok` or `error`) stay within GRBL's receive buffer less a safety margin (Proposal: 120 of 128; one named constant), and each `ok` or `error:<n>` frees the oldest line's bytes. Test: a simulator with a 128-byte receive buffer that answers any overflow with a visible failure and acknowledges after a varying, line-count-driven delay streams the golden jobs of `curvyo-laser-core/tests/fixtures/output/grbl/*.gcode` (every file of `0029` criterion 31) and a 20,000-line job with no overflow and in order, byte for byte equal to the prepared lines.
- G7. Given GRBL answers `error:<n>` to a line, then the connector sends no further line and ends the job as `Done { Failed }` after the stop of G12 (laser off, same steps), the app reads "Failed at line <n>: <GRBL's meaning> (error <n>)" (meanings and wording: UX notes section 5; unknown number: "Failed at line <n>: error <n>") and `jobs.log` records `Failed: <the same text>` (the log format of `0064` Q18 gains the text after `Failed:`; golden file updated). The meanings for GRBL 1.1's error numbers 1 to 38 are a table in `-io` (wording by the UX notes); an unknown number reads "error <n>". The failed line number is the job line GRBL rejected, not the number of acknowledged lines. Tested with a simulator that fails on a chosen line and one that fails a line while others are still in its buffer (lines after the failed one are never sent).
- G8. Given streaming, then `Status.job.line` is the number of lines GRBL has acknowledged, and the job ends as `Done { Completed }` only after the last line is acknowledged **and** GRBL reports `Idle` (its planner is empty), never earlier, so "Completed" never shows while the head still moves; `elapsed_ms` excludes pauses (as `0064` Q14). Tested with a simulator that keeps moving after the last `ok`.
- G9. Given a job whose first line is `$H` (home first, `0029`), then the connector waits for GRBL's `ok` for that line with no time limit (homing takes minutes), `?` polling and `Status` continue meanwhile (G4), and the loss rule of G15 is judged by the answers to `?`, not by the missing `ok`. Given `Stop` during homing, then the connector sends the soft reset without a feed hold (GRBL ignores `!` while homing), ends `Done { Stopped }` after the banner, and shows the alarm GRBL raises after the reset, if any (G14).

*Pause, resume, stop*

- G10. Given a running job, when `Pause` arrives, then the connector sends `!`, stops sending lines, and the state is `Paused` only when GRBL's status reports `Hold:0` (the head has stopped; `Hold:1` still reads `Running`); the line count stops once the lines already in GRBL's buffer are acknowledged (GRBL keeps parsing them during a hold). The laser is **off while held**, in laser mode and without it (`$32=0`, `M3`; the architect names the mechanism GRBL 1.1 offers, and the simulator models it, G22), and also with a GRBL build that leaves the laser on in a hold (`adrs.md` C7: the connector reads the report's `A:` field; tested with the simulator's laser-on-in-hold mode and `m3_constant_power.gcode`). `Pause` while already `Paused` stays idempotent (`0064` P17).
- G11. Given `Paused`, when `Resume` arrives, then the connector sends `~` and continues sending lines from where it stopped; the state is `Running` when GRBL reports `Run`; the line count continues from the same line; the laser comes back as the job's own state says, not otherwise.
- G12. Given `Stop` in `Running`, then the connector sends `!`, waits for `Hold:0` (at most 2 s, constant, injected), sends the soft reset (`0x18`), waits for GRBL's banner (at most 3 s), then writes `M5` and `M9`; the job ends `Done { Stopped }` exactly once, only after the banner. Given `Stop` in `Paused`, then it starts at the soft reset. Given the banner does not come, or no answer to `?` comes for 3 s while the stop waits for it (the 3 s rule of G15 holds here too), then the job does not end as a clean `Stopped`: the state is `NoController` with "Could not confirm the machine stopped" and the connector retries (G3). An `error:9` (G-code locked out) answer to `M5`/`M9` while GRBL is in alarm lock is not a failure. The soft reset after the hold keeps the position (GRBL does not alarm), so the next job needs no Home (Proposal; simulator models GRBL 1.1's rule: a reset while moving raises alarm 3). In every case the simulator's spindle and air are off when `Stopped` is reported (`M5`, `M9` or reset). Given any banner while a stop is pending, also during its hold step (the machine's reset button), then the stop ends there (`Done { Stopped }`), and a `Start` while a stop is pending starts nothing. Tested from `Running`, `Paused`, during the last line, with a banner that never comes, a controller that falls silent at the Stop, and a banner during the hold. Timing toward the app: see G30.

*Alarm and settings*

- G13. Given GRBL raises an alarm while a job runs (`ALARM:<n>` message or state `Alarm`), then the connector stops sending at once, discards every unsent line, sends the soft reset so that the spindle is off, ends in `Alarm` (not `Done`), and `Status.alarm` carries that text with the table of GRBL 1.1's alarm numbers 1 to 9 in `-io`, texts as in the UX notes section 6 (1 hard limit hit, 2 target beyond the soft limits, 3 reset while moving, 4 probe already triggered, 5 probe did not touch, 6 reset during homing, 7 door opened during homing, 8 homing pull-off did not clear the switch, 9 homing did not find the switch; an unknown number reads "Unknown alarm (alarm <n>)"); the text form is "<meaning> (alarm <n>)" (UX notes V11), so the app frame reads "Alarm: Hard limit hit, position may be lost (alarm 1)"; "Locked, not homed" for GRBL's alarm without a number at power-up (G14), "Locked" for a bare `Alarm` state; the first alarm's text stands until it clears; `jobs.log` has `Alarm: <that text>`; `SubmitJob` in `Alarm` keeps answering `Busy` (`0064` Q19). Tested with a simulator alarm injected during a job, during `Hold`, and while idle.
- G14. Given GRBL starts in alarm (homing enabled, `$22=1`, "ALARM:... '$H'|'$X' to unlock"), then after the connect the state is `Alarm` with GRBL's text and `Start` is not possible. The connector never sends `$X` or `$H` on its own. The way out is G33 (the Unlock button, Frage 239 B); the connector's terminal gets no unlock line and prints no prompt (Frage 241 B): it says only the alarm. The alarm clears (core's `AlarmCleared`) when GRBL reports `Idle`.
- G33. Given the state `Alarm` and a paired client, when the client sends the new command `Unlock` (additive `Command::Unlock`, protocol stays 0, golden file `command_unlock.json`; the connector answers with `Status`), then the connector writes `$X` once to GRBL, shows nothing else new, and the alarm clears by G14 when GRBL reports `Idle`; GRBL answering `ok` or `error:<n>` to `$X` is consumed as the answer of that write (G28 does not fire). Given any state other than `Alarm`, `Unlock` writes nothing and answers `Status` unchanged. `Unlock` has no start semantics: it never starts, resumes or re-sends a job (a job dropped by G13 or G15 stays dropped), and it is allowed under `--require-local-start` (G18). It works from every paired client with no input at the connector's computer. Every unlock writes one line `Unlock: <client name>` to `jobs.log` (grammar and golden file by the architect; the old goldens stay) and one terminal line "Unlock sent by <client name>". In the app, the **Unlock** symbol button (UX notes section 6) sits in the Connector row, is shown only in `Alarm` and is busy until the alarm clears or 5 s pass. Tested: from the simulator's startup alarm, with a second paired client, with `Unlock` in `Idle` and in `Running` (nothing written, byte log), with `--require-local-start`; the log line is in the golden `jobs.log`. *(Amended by `0118`: the Unlock button sits in the Machine controls footer of the Operations tab, at the right of the alarm line.)*
- G19. Given a connected controller, then the connector reads `$$` after every identify (G2) and never writes a setting (G5). The Controller line shows, in words fixed by the UX notes: the name and firmware, the port and baud rate the connector uses, laser mode (`$32`), the S range maximum (`$30`) and the travel (`$130`, `$131`). When the machine profile's S-max or laser mode differs from what GRBL reports (a mismatch of S max scales every power by the ratio), the row shows one warning line and Start stays possible (Proposal). **Laser mode off is not a warning but a refusal, G34.** The settings travel as an additive, optional field of `ControllerInfo` and the used port and baud as an optional string and an optional number (golden files updated, protocol stays 0; the architect names the fields, the old golden files still decode).

*Safety*

- G34. Given the controller reports `$32=0` (laser mode off; GRBL then runs `M3` at constant power and a laser job makes no sense), then the connector refuses `SubmitJob` with the new additive reject reason `LaserModeOff` (`RejectReason::LaserModeOff`, protocol stays 0, golden file `reject_laser_mode_off.json`); no job is held, no byte reaches the controller, and the state does not change. The app reads "Laser mode is off ($32=0)" in the Output group's state line (UX notes section 2) and the Connector row; the terminal prints the same words once per identify. The decision uses `$32` as read at the latest identify (G19, G2); `$32=1` accepts as before. **When GRBL's `$32` is unknown** (the `$$` read failed or has no `$32`; architect review 2026-11-18, customer-approved rule "refuse; the fake controller keeps accepting") the connector refuses `SubmitJob` the same way with the additive reject reason `LaserModeUnknown` (golden file `reject_laser_mode_unknown.json`); the app and the terminal read **"Laser mode unknown ($32 not read)"** (33 characters). The fake controller reports no `$32` and is never refused. The GRBL controller refuses `Start` in both cases as a second guard. Given a job already held when a reconnect re-identifies, G3 has dropped it. No override, no flag (Proposal; the customer may ask for one at the demo). Tested with the simulator at `$32=0` and `$32=1`, and the fake controller.
- G15. Given the connection to the controller is lost (a read or write error on the port, the cable pulled, or no answer to `?` for 3 s, constant, injected), then the connector (a) stops sending at once, (b) tries to write `0x18` and `M5` and `M9` if the port still takes writes, (c) goes to `NoController` and, when a job was `Receiving`, `Ready`, `AwaitingLocalStart`, `Running` or `Paused`, drops it, (d) shows "Lost the controller at line <n>" (the line count of the job; a job not yet started says "Lost the controller"), (e) writes `Failed: controller lost at line <n>` to `jobs.log` (an unstarted job: no entry), (f) reconnects by G3 and does not resume. **No `Status` ever shows `Running` or `Paused` when no answer to `?` is younger than 3 s.** A client that connects after the loss reads the same text (`0064` P19). Tested with a simulator that closes the port mid-job, one that stops answering while staying open, and one that is unplugged during `Hold`; the test asserts the state at every status push.
- G16. Given the connector receives SIGINT or SIGTERM while a job runs or is paused, then it stops the job as in G12 (hold, reset, `M5`, `M9`), logs `Stopped`, and exits within 6 s (G12's limits of 2 s and 3 s plus `M5`, `M9`) with exit code 0; given no job runs it exits at once. `kill -9` and power loss cannot be handled; the PR says so (and that GRBL's own planner buffer keeps moving for a moment after a lost cable, which no software can undo).
- G18. Given `--require-local-start`, then no job byte is written to the port before the maker presses Enter on the connector's terminal (one of the two existing terminal exceptions of the design principle, Frage 242); only the identify of G2, `?`, the `$X` of G33 and the safety writes of G12 and G15 (`0x18`, `M5`, `M9`) may be written (checked on the simulator's byte log). Given the option off, `Start` streams at once. Unchanged for the maker.

*Rules added by the architect and the UX notes (all Proposals, vetoable at the demo)*

- G28. Given an `ok` or `error:<n>` arrives while no line is in flight (another program on the port, such as a ModemManager probe), then the connector stops the job by the sequence of G12 and ends it as `Done { Failed }` with "Unexpected answer from the controller", because a foreign answer would let the character count overflow GRBL's buffer. Given lines are in flight, a foreign `ok` is taken as the oldest line's answer; when `$10` makes GRBL report `Bf:`, the connector fails the job the same way once GRBL's receive buffer holds more (128 less the free bytes) than the bytes it has in flight plus owed `M5`, `M9` and `$X` (one byte of slack for GRBL's count). Without `Bf:` only the exclusive open and the ModemManager rule guard it (`docs/guides/connector-serial-linux.md`). Tested with a simulator that sends an extra `ok` mid-job, with and without lines in flight. (Proposal, `adrs.md` C4.)
- G29. Given a job runs or is paused and the machine's own reset button is pressed (a GRBL banner arrives that the connector did not ask for), then the job ends as `Done { Failed }` with "The controller was reset at line <n>" plus GRBL's alarm if it raises one; nothing is resumed. Given a `Pause` that GRBL does not confirm with `Hold:0` within the hold limit of G12 (2 s, the same injected constant; GRBL ignores `!` while homing), then the `Pause` is dropped and the state stays `Running`. Tested with the simulator. (Proposal, `adrs.md` C4.)
- G30. Given `Stop`, then the connector answers the command within 1 s, before the sequence of G12 ends: the answer is `Status` with the detail "Stopping" and the job state unchanged, and the end of the stop (`Done { Stopped }`, `NoController` or `Alarm`) follows as a normal status push. The app's 5 s wait for a command answer (`0064`) is not changed. Testable behaviour: a stop that takes up to 6 s (2 s hold plus 3 s banner plus `M5`/`M9`) never shows "Timed out", and the Stop button stays busy from the press until the end state (UX notes section 7). The implementer may instead raise the app's wait for `Stop` above 6 s only if the same test passes; the connector answer is the preferred way because it keeps the app's single timeout. (Proposal.)
- G31. Given `SIGHUP` (the terminal closed), then the connector does not handle it in this slice: the process dies as the operating system decides, like `kill -9` (G16); the PR says so. (Proposal, `adrs.md` C11.)
- G32. Given `deny.toml`, then it allows `MPL-2.0` for `serialport` (and it only; MPL-2.0 is a file-level weak copyleft licence, compatible with the project's AGPL-3.0-or-later use because it covers only the modified files of that crate, which Curvyo does not modify); **customer-approved 2026-11-18**, the comment in `deny.toml` says so; `cargo deny check licenses bans sources` is green; the PR description lists `serialport` 4.10.1 with licence MPL-2.0 and the reason (serial port, exclusive open and pty pair, `adrs.md` C1) and every other new lock entry with its licence (G25).

*Fake controller, trait, tests, build*

- G20. Given `--fake-controller`, then it behaves as in slice 2, every test of `0064` Q1 to Q22 and `0125` S1 to S19 still passes without a changed expectation (only `Status` and `ControllerInfo` literals in tests gain the new optional fields as `None`), and the `FakeController` and `GrblController` both implement the one `Controller` trait; there is no third implementation and no flag that mixes them.
- G21. Given the serial code, then the pure parts (line preparation G5, character counting G6, status-report parsing G4, error and alarm tables G7 and G13, the loss rule G15, the stop sequence G12) are functions or structs without port, clock or thread, unit-tested with table-driven cases and golden files in `tests/fixtures/grbl/` (status reports of GRBL 1.1 in both coordinate modes, banners, `$$` output, error and alarm lines); `unwrap` and `expect` follow `CLAUDE.md` §5; `curvyo-connector-core` is unchanged except for what G2, G5, G7, G10 to G12, G14, G15 and G19 need and still builds for `wasm32-unknown-unknown`.
- G22. Given the test suite, then a GRBL 1.1 simulator in `curvyo-connector-io/tests/common/` (plain struct, test support only) exists: a 128-byte receive buffer that fails visibly on overflow, `ok` and `error:<n>`, `?` reports (`Idle`, `Run`, `Hold:1`, `Hold:0`, `Alarm`) with work or machine position, `!`, `~` and `0x18` as real-time bytes (also inside a line, as GRBL does), the banner, `$I`, `$$` with settable values, spindle and air state, alarm injection, an error on a chosen line, a planner that keeps moving after the last `ok`, silent and garbage modes, and closing the port. Its time is driven by the test (line counts and a stepped clock), never by wall-clock sleeps. One test per behaviour runs over an in-memory byte channel; one end-to-end test (G23) runs over a real pseudo-terminal pair on Linux so that the real serial code path (open, baud, read timeouts) is exercised. `curvyo-connector-io/examples/grbl_pty.rs` starts the simulator on a pty and prints its path for the manual demo; it is not part of the shipped connector.
- G23. Given an integration test in `curvyo-connector-io/tests/` that starts `RunningServer` with the serial controller on the simulator's pty and drives a client through pair, test, send of the golden job `cut_line.gcode`, start, pause, resume, stop, a second send and run to `Completed`, an injected alarm, an unplugged port and the reconnect, then it passes in the quality gate; the simulator's byte log shows no overflow, no `!`, `~` or `?` inside a line and an off laser after every stop, alarm and loss.
- G24. Given the real laser (customer's own hardware, a GRBL 1.1 controller with a laser), then the customer runs once: connect (Controller line), Send to machine of a small page, Start with a safe setup (the last demo bullet), Pause, Resume, Stop (beam off at once), run to Completed; the PR states which of these were done by the customer and which only on the simulator (🟡 until then). Hardware is never asserted by the gate.
- G25. ## Questions

Fragen 238 to 241 are answered by the customer (2026-11-18). Frage 242 is open with a safe default; it does not block the build.

Frage 238 (GRBL-PORT): Who chooses the serial port and baud rate? **Answered: A.** The connector's command line only (`--serial`, `--baud`), like local start (`0064` Frage 3); a remote client cannot make the connector open another device. The profile's Controller port and Baud fields stay stored notes; the Controller line shows what the connector really uses. (B: the app sends them; C: flags with a profile override.)

Frage 239 (GRBL-UNLOCK): How does the maker leave a startup alarm before `0118` has a Home button? **Answered: B** ("this must go out on Curvyo"). An **Unlock** button in the Connector row sends `$X` to the connector in `Alarm` (G33); the terminal `unlock` line is dropped. Home comes with `0118`. (A: a terminal line; C: nothing.)

Frage 240 (GRBL-LASERMODE): With GRBL's laser mode off (`$32=0`), what does Start do? **Answered: B** (lasering makes no sense with `$32=0`). The connector refuses the job with a clear reason, "Laser mode is off ($32=0)" (G34), no warning line. (A: warn, Start works; C: confirm at the machine.)

Frage 241 (GRBL-UNLOCK-PROMPT): Does the connector's terminal say what to type while GRBL is in alarm? **Answered: B.** No prompt line: the terminal names the alarm only. The customer's remark became the design principle above.

Frage 242 (CONN-LOCALSTART-SERVICE): Local start for a connector that runs as a service
- Today `--require-local-start` needs Enter on the connector's terminal, which a systemd service does not have.
- A: a local command on the connector host, for example `curvyo-connector-server confirm`, that talks to the running service over a Unix socket in the state dir; works over ssh and replaces the terminal Enter.
- B: a physical button via GPIO later.
- C: keep the terminal Enter only, for people who run the connector in a terminal.
- Recommendation: A.
- Default if unanswered: C for this slice; A becomes its own slice together with the systemd unit file (follow-up).
