# Send to machine: a button in the Output group of a laser page that sends the job to the page's paired connector

Status: Done (PR #379)
Priority: Should
Origin: Customer (the machine connector, request of 2026-10-17; this is slice 3 of `0064`, order in `specs/0064-machine-connector/adrs.md`, "slice order for the rest of 0064"). Everything marked **(Proposal)** is the product owner's and vetoable at the demo.

## User value

As a maker with a laser on a connector in my workshop I want to press one button next to "Export job file" that sends exactly the job I see on my laser page to the machine, and then watch it wait, run and finish in the same group, so that a design reaches my laser without a file, a USB stick or a second program (`R-MFG-LASER-002`, `R-MFG-LASER-003`).

**What other tools do.** LightBurn sends the job to the controller from the same program and shows a progress window; Mainsail and OctoPrint accept an upload and show the print beside it. **We do better:** the send uses the same checks as the export (a blocked page cannot be sent either, and the cause is on the button), what is sent is byte for byte the file the export would write, and the state of the machine is a line in the group where the maker already looks, not a second window.

**One-line meaning (Proposal; the answer of Frage 2 of `0064`, CONN-SEND-MEANING A, stands):** *Send to machine* copies the job to the connector; the connector holds it and runs it only after *Start*. It does not start anything.

## What changes in the demo

- In the Output group of a laser page whose machine profile names a connector (`0064` slice 2), next to **Export job file** there is a second symbol button **Send to machine**. Pressed on a page that passes the checks, the job goes to the connector; the group shows one inline state line: "Sending <name>", then "Ready: <name>, 412 lines, 9.2 KiB" (sizes in binary units, as the Connector row).
- **Start**, **Pause**, **Resume** and **Stop** stay in the Connector row of the Machine block (`0064` Q14, Q15); the state line and a thin progress bar in the Output group follow the job ("Running 120 / 412", "Paused at line 120", "Completed, 412 lines").
- A page that fails the checks has both buttons disabled with the same cause; a profile without a connector shows no Send button; the browser build shows the button disabled with "Needs the desktop app" and Export keeps working.
- After the connector accepted the job, the page counts as lasered exactly as after an export: fixture jobs switch to "Output off" (the only notice: "Output turned off on N fixture jobs." when N is above 0; no notice for the send itself), test grids become Lasered (criteria S10 to S12).
- Try it: `curvyo-connector-server --fake-controller`, pair it in the Machine block (as in `0064`), open a laser page with a test grid, press Send to machine, then Start in the Connector row and watch both places. No laser moves.
- The project file does not change.

## Words (shown in the UI)

"Send to machine" (button name, tooltip and accessible name), "Output group" and "checks" as in `0029`, "Connector row" as in `0064`, "Lasered" as in `0112`. The connector's state words are those of `0064` Q13 to Q17 and Q19 and are not repeated here.

## Boundary (Proposal)

- **In:** the button, its enabling rule, building the job bytes with `job::write` of `curvyo-laser-core` (`0029`) and sending them through the connection of slice 2 (`SubmitJob`, chunks, `JobAccepted`/`JobRejected`; no new message), the inline state line and progress bar in the Output group, the Lasered commit on acceptance, the browser state.
- **Reuses, does not change:** the protocol (stays protocol 0, golden files unchanged), the connector program, the pairing and the credential record, the gate, the job writer, the Connector row with its own manual "Send job" of a text file (Q13; it stays for files that did not come from a page).
- **No new crate, no new dependency, no protocol change, no `format_version` change** (the architect confirms in the addendum; if the Lasered commit needs a stored field that `0112` does not already have, this slice says so before it is built; the criteria below expect none: the Lasered state and the fixture Output switches are the same fields criterion 28 of `0029` already writes).

## Acceptance criteria

Prefix `S`, so that the criteria of `0029` and `0064` keep their numbers. "Fake connector" means `curvyo-connector-server --fake-controller` on `127.0.0.1:0` driven by the integration tests of `curvyo-connector-io`.

*The button and when it works*

- S1. Given a laser page (extension on) whose machine profile copy names a connector address (`0064` Q11), then its Output group shows, directly after Export job file in the same row, a symbol button **Send to machine** (glyph chosen by the UX notes, no label text in the narrow panel, tooltip and accessible name "Send to machine"). Given a profile without a connector address, a page of another kind or a "Laser (off)" page, then there is no Send button.
- S2. Given the checks of `0029` criterion 4 block (no settings, geometry outside the work area, damaged machine copy, nothing runs), then Send to machine is **disabled but focusable** (`aria-disabled`, reachable by Tab) exactly when Export is, and its tooltip and accessible description is the first blocking cause in the words the checks show. Given the checks only warn, then Send is enabled. Test: for each blocking condition of criterion 4 a, b, c and d, Export and Send are disabled together; with the condition removed, both are enabled together.
- S3. Given the machine profile names a connector but the app holds no pairing for it (`0064` Q5, Q8 "key changed", Q9 "No longer paired"), then Send is disabled with the cause "Not paired" (or "No longer paired"; the key-changed case reads "This connector's key changed", the words of `0064` Q8), and the Pair field of the Connector row is the way on. Given the maker is paired, then reachability is not guessed: Send is enabled and a connector that does not answer is reported when pressed (S6).
- S4. Given the profile's output format, then only `grbl` sends: given a format the connector does not speak (none exists in this build; a later format), then Send is disabled with the cause "The connector does not speak <format name>" and Export is unaffected. A damaged or unknown format is already a block of the checks (`0029` criterion 4 c) and disables both.
- S5. Given the browser build (`R-SYS-005`), then Send to machine is shown disabled with the cause "Needs the desktop app" (the words of `0064`), and Export job file works as before (a download). Given the desktop app, then nothing in this slice is conditional on the platform beyond that.

*What is sent*

- S6. Given an enabled Send, when the maker presses it, then the app builds the job with `job::write(output_format, &job)` from the page as it is at that moment (the checks are evaluated again at that moment; a page that has become blocked sends nothing), and sends those bytes as the job with the **page's name** as the job name, a new job id for each send, the SHA-256 of the bytes and the chunking of `0064` P8, over a fresh connection. Test (fake connector): the bytes the connector holds are byte-identical to the file Export writes for the same page and settings (`0029` criterion 24 guarantees determinism); the connector's job log names the page.
- S7. Given the send fails, then the Output group shows exactly one inline text and nothing is committed (S10): "Sending <name>" while it runs; then on a refusal the connector's reason in the words of `0064` Q13 ("Connector busy", "No controller", "Not plain ASCII text", "Larger than 64 MiB", "Hash mismatch"); "Nothing answers at <address>" when it cannot be reached; the pairing texts of S3 for a connector that lost its pairing; "Machine in alarm: <text>" when the connector is in `Alarm` (`0064` Q19); "Timed out" when no answer comes within 5 s (as the Connector row, `0064`); "Not received" when the connection dropped and the re-read shows the job is not held (S11); "Timed out" also when the connection dropped after the job went out, the re-read fails too and no status of the sent job id is seen within 30 s of the press's answer (Proposal, vetoable at the demo; named constant `UNRESOLVED_SEND_MS`): nothing is committed by the timeout. The job text must be printable ASCII (`0064` P10); the GRBL writer already writes every character of the comment header outside printable ASCII as `_` (ADR 0064 decision 2, addendum B6 of `specs/0064-machine-connector/adrs.md`: "Küche" gives `; Curvyo job: K_che`), Send sends the bytes unchanged and the job name in `SubmitJob` is the page's name as it is. The test uses such a page; the send must not fail on it. No popup, no dialog.
- S8. Given a send in progress, then Send is disabled with the cause "Sending"; Export stays enabled. Given the connector holds a job that is not finished (Receiving, Ready, AwaitingLocalStart, Running, Paused), then a new send is refused by the connector with "Connector busy" and the held job is untouched (`0064` P13); the app does not discard a held job on its own. The maker ends it with Stop (Connector row), after which the next send is accepted. A send left unresolved (S7) leaves "Sending" after those 30 s: Send is enabled again, the watcher keeps following that job id (addendum B5), and a `Ready` or later state of that id that still arrives commits once (S10, S11) until the next send is handed out; a new press before that finds the job held and is refused "Connector busy".
- S9. Given the connector accepted the job (`JobAccepted`, the connector's `Status` is `Ready` with the sent job id, `0064` P20), then the Output group shows "Ready: <name>, <n> lines, <size>" and the Connector row shows the same job Ready with its Start enabled (`0064` Q14), without the maker picking a file. Given the maker presses Start there, then the job runs as in `0064` Q14 to Q17, including "Waiting for the start at the machine" under `--require-local-start`.

*Counting as lasered (the rule)*

- S10. Given `JobAccepted`, then in **one undo step "Send job to machine"** the app does exactly what criterion 28 of `0029` does for a successful export, with the same sub-rules: (a) every fixture job whose Output was on is switched off and shows "Output off", (b) the stored numbers beside every operation's material link are refreshed, never the overrides, (c) every test grid with at least one operation in the job gets the state **Lasered** in its material (`0112` criterion 11). Undo restores (a) and (b); **Lasered stays** (it records that a job was written to a machine, not a project state). **No notice for the send itself** (the state line turning to "Ready: ..." in the group is the result; the customer rule "No notice after a success"). Only when N fixture jobs were switched off (N above 0) one canvas notice "Output turned off on N fixture jobs." ("1 fixture job"), 3 s, 5 s with a second line as in `0029` criterion 27. Proposal (UX notes U11), vetoable at the demo; the fallback if vetoed is the export's two-line notice "Sent <name> to <connector name>." with the fixture line as second line, 3 s / 5 s, names cut to 70 characters per line.
- S11. Given anything other than `JobAccepted`, then nothing of S10 happens: not on the press, not while "Sending", not on a refusal (S7), not when the connection drops before the app has seen `Ready`, not on Start, Stop, completion or failure. Given the connection drops after the last chunk and the app reconnects, when its `Status` read (`0064` Q16) shows `Ready` or a later state of the sent job id, then S10 happens once for that id (a job id is committed at most once, tested with a replayed status); given the read shows `Idle`, `Receiving` (a transfer that dropped), `NoController`, `Alarm` or another job id, then nothing is committed and the Output group says "Not received" (Proposal, vetoable at the demo; the one text covers Receiving, NoController and Alarm).
- S12. Given a job that was accepted and then stopped before its first line or never started, then it still counts (Proposal: it is "accepted by the machine" like an exported file that is never opened; what counts is that the numbers left the page). Given a second send of an unchanged page, then (a) finds nothing to switch off, (b) is idempotent, and an unchanged grid keeps its test id (`0029` criterion 30); the second send is its own undo step only if it changed something, otherwise no step is added. Given a send that wrote no operation of a grid (its operations had Output off), then that grid is not Lasered (`0029` criterion 29).

*The state in the Output group*

- S13. Given a paired connector in the profile and the Output group shown, then below the buttons one **state line** shows the connector's current job in the words of `0064` Q13 to Q17 and Q19 with the job name cut with an ellipsis so a line stays within 70 characters: "Sending <name>", "Ready: <name>, <n> lines, <size>", "Running <line> / <lines>", "Paused at line <n>", "Waiting for the start at the machine", "Completed, <n> lines", "Stopped at line <n>", "Failed at line <n>", "Alarm: <text>", "Connection lost" (sizes in binary units: "812 B", "9.2 KiB", "3.5 MiB"). With an active job a thin progress bar sits under the line. With no job (Idle, or no connection made yet) the line is absent: the group does not reserve a row for it that stays empty (UX notes decide the exact layout; the state line never shifts the buttons). *(Amended by `0118`, Frage 262 A, 2026-11-19: the Output group has no state line or bar any more; the one state line of the Operations tab is the Machine controls footer's, in the `0064` form ("Running" with the bar and the counts line, the job's name in the counts line), and it shows every result of a Send to machine press. Send to machine keeps its disabled causes in its tooltip.)*
- S14. Given the Output group is shown and the connector has an active job (Receiving to Paused), then the app holds one connection and shows the status the connector pushes (at most 5 per second, `0064` Q14); given the connection drops it keeps the last values with "Connection lost" and retries every 5 s (`0064` Q16, one shared retry with the Connector row, not two). Given no active job, then the group reads the status once when it is first shown and does not poll. Test: the Output group and the Connector row show equal values at the same time for the same job (one status source in the app). *(Amended by `0118`, Frage 262 A, 2026-11-19: the Output group has no state line or bar any more; the one state line of the Operations tab is the Machine controls footer's, in the `0064` form ("Running" with the bar and the counts line, the job's name in the counts line), and it shows every result of a Send to machine press. Send to machine keeps its disabled causes in its tooltip.)*
- S15. Given the state line, then it has no buttons: Start, Pause, Resume and Stop live in the Connector row only (Proposal: one place for a command that moves a machine; the group is the overview). The Output group shows the line for any job the connector holds, also one sent from the manual "Send job" or from another paired app; the name (and the size in "Ready") is shown only for a job this app sent in this run (page send or manual "Send job"), matched by job id, since the connector's `Status` carries no name (protocol 0 stays; addendum B5). In the active and done states a job not sent from this page but known in this run adds " · <name>" (UX notes U6); a job sent by another app shows neither name nor size ("Ready, <n> lines", "Running 120 / 412"). *(Amended by `0118`: Start, Pause, Resume, Stop, Unlock and Home live in the Machine controls footer of the Operations tab, the one place for a command that moves a machine; the " · <name>" suffix is gone with the Output group's line.)*

*Build, tests and rules*

- S16. Given the code, then the domain logic that decides "enabled, with which cause" (S2 to S5, S8) and "what is committed when" (S10 to S12) is a pure function or struct in a `*-core` crate that already exists (the architect names it in the addendum), with unit tests for every cause and every transition in S11; the connection is `curvyo-connector-io` of slice 2 and the buttons are frontend wiring only. No new crate, no new dependency, no new trait, no change of a protocol golden file, no `format_version` change (the project and profile fixtures are byte-identical before and after; tested by saving a project before and after a send and comparing).
- S17. Given an integration test that drives the whole path without the UI (laser page with a test grid and a fixture job, fake connector, pair, Send, Start, Pause, Resume, Stop, a second send), then it passes in the quality gate; timing is by line counts, never by wall-clock sleeps (`CLAUDE.md` §5). A browser check by the tester drives the Output group once in the running app against the fake connector (S1, S2, S9, S10, S13, S14) and once in the browser build (S5).
- S18. Given the quality gate of `CLAUDE.md` §7, then it is green; `docs/design-system.md` gets the rows the UX notes name ("Send to machine button", "Connector state line").
- S19. Given a transfer that was cut mid-way (the client dropped after some chunks; the connector is left `Receiving` or has dropped the partial job), when the maker presses Send again, then the connector does not answer "Connector busy" from a stuck Receiving: the retry is accepted and the page commits once (S10, S11). Test through Send on the fake connector: cut the connection after N chunks, assert nothing is committed and the line reads "Not received", press Send again, assert the job is held and the commit happens once. The connector side (a disconnect mid-transfer ends Receiving) is fixed on the PR #375 branch; this slice only tests the retry.

## Out of scope

- A real laser: GRBL over serial is slice 4 of `0064`; this slice runs on the fake controller (the demo moves nothing).
- Reaching the connector through the relay, enrolling a machine, the browser sending (the browser build has no direct LAN route; it comes with slice 5 of `0064`), sharing with a workspace and the start rule for non-admins (slices 5 and 6).
- Start, Pause, Resume, Stop buttons inside the Output group; Home, jog, frame, focus (`0118`); a way to start the job from the send (Send to machine never starts a job).
- Sending anything but the job of a laser page (a file: manual "Send job" in the Connector row); other output formats; sending several jobs, a queue, scheduling.
- Changing what a job contains or what Export does; undoing a send on the machine (undo restores the project, not the connector).
- Sending the job of a cutting plotter, embroidery or CNC page (later machine families).
